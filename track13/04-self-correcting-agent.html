The self-correcting SQL agent

Start here

The first query a model writes sometimes fails, for example with a wrong column name.

The database's error message says exactly what went wrong.

A self-correcting agent hands that error back to the model and asks for a fixed query.

Cap the loop at two or three tries so it can't spin forever or run up a bill.

It can only fix errors; a query that runs but answers the wrong question needs other checks.

Everyday picture

It is like a spelling test where the teacher circles the exact wrong letter and lets you try again twice. With the circle you fix it almost every time; if the teacher just said "wrong, try again", you would probably make the same mistake.

In the pictureIn the real system
The teacher circling the wrong letterThe database error, e.g. “no such column: customer.country”
Trying again with the circle in viewThe retry prompt carries the error and the failed SQL
Only two more triesmax_tries = 3, then a polite “could not build a query”
A wrong answer with perfect spellingValid SQL that answers a different question: no error, no circle

Where the picture breaks. The database only circles mistakes that break the rules of SQL; a query that is valid but answers the wrong question gets no circle at all.

Going deeper

First tries fail: a wrong column name, a bad join, a dialect quirk. The trick that makes text-to-SQL feel reliable is letting the system read its own error and fix itself — the agent loop from Track 4, pointed at a database.

Why a single shot isn’t enough

Even with a good schema prompt, the model’s first query will sometimes fail: it references customer.country when the table is customers, or uses a function your dialect doesn’t have. A one-shot system just surfaces that error to the user, who has no idea what to do with no such column: customer.country. But notice: the database just told us exactly what’s wrong. If we hand that error message back to the model and ask it to try again, it fixes the mistake the overwhelming majority of the time. That single feedback loop is the difference between a brittle demo and something people trust.

This is precisely the agent loop (ReAct) from Track 4: act (run the SQL), observe (the result or the error), and decide (answer, or revise and retry). The tool here is your safe read-only query runner; the observation is either rows or an error string.

The loop, with guards

As with any agent (Track 4, and Track 11’s reliability patterns), the loop must be bounded: cap the retries so a query it can’t fix doesn’t spin forever or run up cost. Two or three attempts catches almost all recoverable errors; past that, fail gracefully and tell the user (or hand off to a human).

sql_agent.py
def answer_question(question, db_path, max_tries=3):
    messages = build_prompt(question)        # schema + question (Lesson 9.2)
    for attempt in range(max_tries):
        sql = llm(messages)                  # model writes a SELECT
        try:
            rows = run_readonly(sql, db_path)   # safe runner (Lesson 9.3)
        except Exception as err:
            # hand the DB's own error back and let it fix the query
            messages += f"\nThat query failed with: {err}\nFix it and return only SQL."
            continue
        return {"sql": sql, "rows": rows}   # success — return SQL too, for transparency
    return {"error": "Could not build a working query. Try rephrasing."}

Three things make this good: the loop is bounded (max_tries), it feeds the actual error back (not a generic “try again”), and on success it returns the SQL alongside the rows so the answer is auditable. Everything dangerous is still contained by run_readonly from the last lesson — the agent can retry freely because it can’t do harm.

Beyond errors: verify the result, and ask when unsure

Self-correction fixes queries that error. But recall the scarier failure: SQL that runs and returns the wrong number. Two habits help. First, sanity-check the result shape — if a “how many customers” question returns 40,000 rows instead of one number, something’s off; that mismatch can itself be fed back for a fix. Second, when a question is genuinely ambiguous (“best customers”?), the most reliable “agent” move is often not to guess but to ask a clarifying question — “by revenue or by number of orders?” A system that occasionally asks is far more trustworthy than one that confidently guesses wrong.

At real scale: What a 3-try loop buys on 1,000 questions, and what it cannot fix

Assumptions (measure your own): 82% of first-try queries run without error, each retry fixes 70% of the remaining errors, max_tries = 3 (one try plus two retries), 4,000 input and 200 output tokens per call, about 4,400 input on retries because they carry the error and the failed SQL, prices of $2 / $10 per million input / output tokens (Anthropic models overview, checked 2026-11-03).

  1. After try 1: 820 of 1,000 run; 180 error.
  2. After try 2: 180 x 0.7 = 126 fixed, 946 run (94.6%); 54 still failing.
  3. After try 3: 54 x 0.7 = 37.8 fixed, about 984 run (98.4%); about 16 give up gracefully with a message.
  4. Calls per question. 1 + 0.18 + 0.054 = 1.234 on average.
  5. Cost. First call = 4,000 x $2 / 1 M + 200 x $10 / 1 M = $0.010. Retry = 4,400 x $2 / 1 M + $0.002 = $0.0108. Average = $0.010 + 0.234 x $0.0108 = about $0.0125 a question, $12.50 per 1,000.
  6. The ceiling. Suppose execution accuracy against reference answers is 86%. Then 984 - 860 = 124 queries ran fine and returned the wrong result. The error loop cannot touch those: there was no error. They need result-shape checks, clarifying questions and the semantic layer.

So the loop takes "runs" from 82% to 98%, cheaply. "Correct" is a separate number that you must measure separately.

Key points
  • First-try SQL often fails; feeding the database’s error message back lets the model fix it — usually within one retry.
  • This is the ReAct agent loop (Track 4): act (run) → observe (rows/error) → revise.
  • Bound the retries (2–3) and fail gracefully — the safe read-only runner means retrying can’t cause harm.
  • Return the SQL with the answer for transparency and auditing.
  • Handle wrong-but-runs by checking result shape, and handle ambiguity by asking a clarifying question rather than guessing.
Practice

In the loop above, why do we pass the exact error string back to the model instead of a generic “that didn’t work, try again”? And why cap max_tries at a small number instead of looping until success?

▸ Show solution & reasoning

Exact error vs generic retry: the specific message localizes the fix. no such column: customer.country tells the model precisely what to change (the table is customers); near "GROUP": syntax error points at the clause to repair. A generic “try again” gives the model nothing new, so it’s likely to reproduce the same mistake — you’d be paying for another identical failure. Feeding back concrete observations is the core of what makes the agent loop work.

Why bound the retries: some questions can’t be answered from the schema (the data simply isn’t there), and without a cap the loop would retry forever, burning time and money on an impossible task — the runaway-agent failure from Track 11. A small cap catches the recoverable cases (the vast majority) and then fails gracefully with a helpful message, which is both cheaper and a better user experience than an infinite spinner. Bounded loops are non-negotiable in production.

A text-to-SQL system’s accuracy jumps sharply when one change is made. Which change, and why?

  • A) On a failed query, feed the database’s error message back and let the model revise (a bounded retry loop).
    Correct. Many first-attempt failures are small, fixable mistakes (a wrong column, a dialect function), and the database names the problem exactly. Returning that error for a revision fixes most of them on the next try — a large, cheap accuracy gain. It’s the ReAct loop: act, observe the error, revise.
  • B) Raise the model’s temperature so it’s more creative with queries.
    Higher temperature makes SQL less reliable, not more — you want deterministic, correct queries (temperature 0 is typical). Creativity is the opposite of what SQL generation needs.
  • C) Remove the schema from the prompt so the model isn’t constrained.
    Removing the schema removes the model’s knowledge of your tables and columns — accuracy would collapse, not improve. The schema is the most important context there is.
  • D) Run every query twice and compare.
    Running the same deterministic query twice yields the same result; it catches nothing and doubles cost. The valuable feedback isn’t repetition — it’s the error message from a failure driving a revision.

How does a self-correcting SQL agent recover from a bad query?

  • It feeds the database's error message back to the model so it can fix the query and retry.
    Correct. The error is a signal the model uses to repair its SQL.
  • It deletes the database and starts over.
    It repairs the query; it doesn't destroy data.
  • It raises the temperature until it works.
    That adds randomness, not correctness.
  • It gives up immediately.
    The whole point is bounded retry with the error as feedback.

Your loop sees the same error three times in a row: the model keeps producing identical SQL. What is the best change?

  • A) Remove the schema from retries to save tokens.
    The schema is exactly what the model needs to fix a wrong column. Removing it makes the fix less likely.
  • B) Detect a repeated query or error and stop early, or change the feedback (add the real column list for the table named in the error) before retrying.
    Retrying with the same input usually gets the same output. Either give the model new information, such as the actual columns, or stop and fail gracefully instead of paying for identical failures.
  • C) Raise max_tries to 10.
    If the model is stuck, more identical retries just cost more and delay the user.
  • D) Raise the temperature on retries.
    More randomness may change the SQL but not toward correctness, and many hosted models no longer accept temperature changes. New information is what helps.
Deep dive: this is the general pattern for “LLM + any tool”

The self-correcting SQL agent is a specific case of a pattern worth internalizing, because it recurs everywhere in applied GenAI: give a model a tool whose failures are legible, let it call the tool, and feed the tool’s response — success or a precise error — back into the loop. SQL is a beautiful example because databases return unusually good error messages, but the same shape works for calling an API (feed back the 400 and the validation message), running code (feed back the stack trace), or invoking any function with a schema (feed back “missing required field X”). The model becomes reliable not because it’s always right the first time, but because the environment tells it exactly how it was wrong and it can try again.

That reframes what you’re building across this whole course. An agent’s intelligence is only half the story; the other half is the quality of the feedback its tools give it. When you design a tool for an LLM, you’re also designing its error messages — and a tool that fails with a clear, specific, actionable message turns a model that “sometimes gets it right” into a system that “gets it right after a bounded, self-correcting loop.” That design instinct — engineering the feedback, not just the action — is what separates people who can make agents production-grade from people who can only demo them.

Exercises: warm-up, transfer, stretch

Warm-up. First-try success is 75% and each retry fixes 60% of remaining errors. With max_tries = 3, what fraction of queries end up running, and how many calls per question on average?

▸ Solution

After try 1: 75% run, 25% fail. Try 2 fixes 25% x 0.6 = 15%, total 90%, 10% fail. Try 3 fixes 10% x 0.6 = 6%, total 96%, 4% give up. Average calls = 1 + 0.25 + 0.10 = 1.35.

Transfer. Write three result-shape checks that would catch wrong-but-runs answers, and the feedback you would send to the model for each.

▸ Solution

(1) The question asks for one number ("how many", "total") but the result has many rows: "The question expects a single value but the query returned 4,210 rows. Aggregate it." (2) A count or sum is far larger than the table's row count or known totals, a sign of fan-out: "The sum is larger than the total of all orders; check for a join that duplicates rows." (3) An empty result for a question that names a value: "No rows matched country = 'DE'. Sample values for country are 'Germany', 'Canada'." Each turns a silent wrong answer into an observation the loop can act on, still bounded by max_tries.

Stretch. Design an experiment to show leadership what the self-correction loop is worth, honestly.

▸ Solution

Use the golden set (150+ questions with reference SQL). Run three configurations on the same questions and the same model: (A) single shot, (B) error feedback with max_tries = 3, (C) B plus result-shape checks and clarifying questions for flagged ambiguous ones. Report for each: ran-without-error rate, execution accuracy, average calls, p95 latency and cost per 1,000 questions. Use a paired comparison on the same questions (count questions fixed and broken between configs) to see whether gains beat noise. Expect B to raise the run rate a lot and execution accuracy less; C to close part of the remaining gap. Presenting both numbers stops anyone confusing "it runs" with "it is right".

Interview questions

Junior How does a self-correcting SQL agent work?

▸ Model answer

It runs the generated SQL with a safe read-only runner. If the database returns an error, the agent sends the exact error message and the failed query back to the model and asks for a fix, then tries again, up to a small limit such as three tries. On success it returns the rows and the SQL for transparency; on repeated failure it stops and tells the user. It works because databases give precise errors like "no such column", which tell the model exactly what to change.

Mid Why cap retries, and what else should stop the loop early?

▸ Model answer

Some questions cannot be answered from the schema at all, and a stuck model will produce the same failure again, so an uncapped loop burns time and money with no gain. Two or three tries catch most fixable errors. Stop earlier when the same SQL or the same error repeats, when a per-request token or time budget runs out, or when the error is not fixable by rewriting, such as a permission denied or timeout, which should go to the user or an operator rather than back to the model.

Senior Error-driven self-correction raised your run rate to 98% but users still find wrong numbers. What do you do next?

▸ Model answer

Recognize the loop only fixes queries that fail, so I measure execution accuracy separately and read the runs-but-wrong cases. Typical causes: fan-out joins, wrong filters, wrong metric definitions, and ambiguous questions. Fixes in order of leverage: a semantic layer with canonical metric views; result-shape and sanity checks fed back into the same bounded loop; clarifying questions when the question maps to several plausible queries; showing SQL and row counts in the UI; and a growing golden set from user-reported errors, gated in CI. The Self-Debugging and DIN-SQL papers show the feedback idea; the semantic layer is what makes answers right.
