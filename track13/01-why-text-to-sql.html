Structured Data & Text-to-SQL · Lesson 9.1

Why text-to-SQL (and where it breaks)

Most of the world’s valuable data lives in databases, and most of the people who need answers can’t write SQL. Text-to-SQL closes that gap — and it’s the single most natural place for a data engineer to shine in GenAI. This lesson frames the problem, the payoff, and the honest failure modes.

School-kid picture

Text-to-SQL is a translator between a manager and a filing clerk. The manager says "how much did Canada spend?"; the translator turns it into the clerk's exact instructions: which drawer, which folders, how to add up. A good translator knows the filing system cold. The analogy breaks because a human translator who is unsure asks "which Canada figure, gross or net?"; a model will usually just pick one and hand back a confident number.

The problem it kills

In every company there’s a queue: a marketer wants “revenue by region last quarter,” a support lead wants “tickets reopened more than twice,” an exec wants “top 10 customers by lifetime value.” Each of these is a five-minute SQL query — but only for the handful of people who know SQL and the schema. Everyone else waits on that bottleneck. Text-to-SQL is a system that takes a plain-English question, writes the SQL for it, runs it against the database, and returns the answer in words. It turns “ask the data team and wait two days” into “ask and get an answer now.”

This is enormous because it applies almost everywhere: analytics assistants, internal “chat with your database” tools, customer-facing reporting, and BI copilots are among the most-funded, most-built GenAI products right now. And — importantly for you — it’s a problem where knowing databases is the hard part, not knowing the LLM. That’s your home field.

What it looks like

Imagine a tiny sales database — the kind you’ll actually build in this track with SQLite (it’s built into Python, so there’s nothing to install and nothing to pay for). Two tables:

schema.sql
CREATE TABLE customers (
    id       INTEGER PRIMARY KEY,
    name     TEXT,
    country  TEXT,
    signup   DATE
);
CREATE TABLE orders (
    id           INTEGER PRIMARY KEY,
    customer_id  INTEGER,
    amount       REAL,
    created_at   DATE
);

A user asks: “How much did customers in Canada spend in total?” A good text-to-SQL system, given that schema, produces:

generated.sql
SELECT SUM(o.amount) AS total_spent
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.country = 'Canada';

…runs it, gets [(48210.5,)], and answers: “Customers in Canada have spent $48,210.50 in total.” The magic isn’t the English — it’s that the model had to understand the schema (which table has amounts, how to join customers to orders, that country lives on customers) to write correct SQL. Schema understanding is the whole game, and it’s exactly the next lesson.

Where it breaks (be honest in interviews)

Text-to-SQL demos beautifully and then meets reality. The failure modes are predictable, and naming them is a senior signal:

Ambiguity. “Show me our best customers” — best by revenue? order count? recency? The model has to guess, and may guess differently than the user meant. Schema misunderstanding. It may hallucinate a column that doesn’t exist, pick the wrong table when names are similar, or botch a multi-table join.

Wrong-but-runs. The scariest case: the SQL executes without error but computes the wrong thing (e.g., double-counts through a bad join), returning a confident, wrong number. Scale & dialect. Hundreds of tables won’t fit in the prompt, and SQL dialects differ (SQLite vs Postgres vs BigQuery).

Each of these has a mitigation you’ll learn — schema selection, validation, self-correction, and evaluation — but a system that ignores them is a liability, because a wrong number that looks right is worse than an error.

At real scale: Is text-to-SQL worth it for a 1,500-person company's analyst queue?

Assumptions: 1,500 employees, 300 ad-hoc data questions a week, 20 analyst minutes each, a model at $2 / $10 per million input / output tokens (claude-sonnet-5-5, Anthropic models overview, checked 2026-11-03), 4,000 tokens of schema context and 200 output tokens per call, 1.3 calls per question on average (retries).

  1. Today's cost in people. 300 x 20 min = 6,000 min = 100 hours a week, about 2.5 full-time analysts doing nothing but queue work.
  2. Model cost. One call = 4,000 x $2 / 1 M + 200 x $10 / 1 M = $0.008 + $0.002 = $0.01. With 1.3 calls, $0.013 a question, about $3.90 a week. Cost is not the decision.
  3. Correctness is. Suppose your golden set shows 85% execution accuracy. That leaves 15% x 300 = 45 wrong answers a week. Some fail loudly (errors, empty results); the rest are wrong-but-runs, confident numbers in someone's slide deck.
  4. Design for the 45. Show the SQL and row count with every answer, send ambiguous questions back with a clarifying question, restrict the model to curated views, and route anything feeding finance or board reporting to an analyst for review.
  5. Realistic payoff. If 70% of questions are simple lookups the system handles well and analysts review the rest, the queue drops by about 70 hours a week, and analysts spend their time on the hard 30% and on the semantic layer that makes the easy 70% safe.
Key points
  • Text-to-SQL = English question → generated SQL → safe run → worded answer. It removes the analyst bottleneck.
  • It’s one of the highest-demand GenAI applications, and the hard part is databases — your advantage.
  • Correctness hinges on the model understanding the schema, not on fancy language.
  • Failure modes: ambiguity, schema misunderstanding, wrong-but-runs, scale/dialect. Each has a mitigation.
  • The dangerous failure is a confident wrong number — which is why validation and evaluation matter as much as generation.
Practice

For the two-table schema above, write (by hand) the SQL you’d want the model to produce for: “How many orders did we get in 2025?” Then name one way a text-to-SQL system could get this specific question subtly wrong.

▸ Show solution & reasoning 
SELECT COUNT(*) AS order_count
FROM orders
WHERE created_at >= '2025-01-01'
  AND created_at < '2026-01-01';

A subtle way it goes wrong: the model might write WHERE strftime('%Y', created_at) = '2025' — correct in SQLite but broken in other dialects — or, worse, use created_at <= '2025-12-31', which silently drops orders with a time component late on Dec 31 (since '2025-12-31 14:00' > '2025-12-31'). Both run and return a plausible count, so no error surfaces — this is the “wrong-but-runs” trap. The half-open range >= start AND < next-year is the robust pattern, and noticing this is exactly the kind of data-engineering judgment that makes your answers stand out.

Why is a text-to-SQL query that runs successfully but returns the wrong number considered more dangerous than one that throws an error?

  • A) An error is visible and gets fixed; a wrong-but-plausible number is trusted and acted on.
    Correct. Errors are self-announcing — someone sees them and investigates. A query that silently double-counts or misfilters returns a confident number that looks right, so it flows into a decision or a report unquestioned. Undetected wrong answers erode trust in the whole system, which is why validation and evaluation (later lessons) matter as much as generation.
  • B) Errors crash the database, while wrong numbers don’t.
    A failed SELECT doesn’t crash a database — it just returns an error to the caller. The danger of the wrong number isn’t about stability; it’s that no one knows it’s wrong.
  • C) Wrong numbers are always caused by SQL injection.
    Injection is a separate security concern. Wrong-but-runs errors usually come from bad joins, ambiguous questions, or filter mistakes — logic problems, not attacks.
  • D) They aren’t more dangerous; both are equally easy to catch.
    They’re not equally catchable — that’s the whole point. An error is caught immediately; a plausible wrong number can go unnoticed indefinitely, which makes it the more dangerous outcome.

Where does text-to-SQL most often break?

  • When the model guesses table/column names it wasn't given — schema grounding prevents it.
    Correct. Without the real schema, generated SQL references columns that don't exist.
  • When the database is too fast.
    Speed isn't the failure mode.
  • When temperature is 0.
    Deterministic output helps, not hurts.
  • When the question is in English.
    Plain-English questions are exactly the use case.

The model answers "total revenue per customer" with SUM(o.amount) after joining orders to order_items (several items per order). What goes wrong?

  • A) The database raises an error because amount is ambiguous.
    With the o. prefix the column is not ambiguous. The query is valid SQL; its logic is wrong.
  • B) Nothing; joins never change sums.
    Joins to a finer-grained table multiply rows. Aggregating a coarse-grained column after that join double counts.
  • C) Only the row order changes.
    The totals change, not just the order. That is why understanding table grain matters.
  • D) Each order's amount is repeated once per item row, so revenue is inflated; the query runs fine and returns a confident wrong number.
    This is join fan-out. An order of $120 with 3 items becomes 3 rows of $120 and sums to $360. No error is raised, which makes it the wrong-but-runs failure.
Deep dive: why this is your unfair advantage

Text-to-SQL sits precisely at the intersection of LLMs and data engineering, and the LLM half is the easy half. Anyone can call a model and ask for SQL; almost no one applying for these roles can reason about join fan-out, null handling, date-boundary bugs, dialect differences, indexing, or how to give a model just the relevant slice of a 400-table warehouse without blowing the context window. Those are the things that decide whether the generated SQL is correct at scale — and they’re your bread and butter from a decade of pipelines.

There’s also a strategic idea worth carrying into interviews: the best text-to-SQL systems don’t point the model at raw tables. They put a semantic layer in between — curated views, clear column names, documented metrics (“revenue means SUM(amount) on paid orders”), and example query pairs. That turns an ambiguous natural-language problem into a constrained, well-labeled one the model rarely gets wrong. Designing that layer is data modeling, which is exactly what you already do. So when you frame text-to-SQL as “a data-modeling and correctness problem with an LLM on top,” you’re not learning a new field — you’re applying your field to a new interface.

Exercises: warm-up, transfer, stretch

Warm-up. Which of these questions are ambiguous, and what clarifying question would you ask? (a) "Orders last month" (b) "Our best customers" (c) "Revenue in Canada in 2025"

▸ Solution

(a) Slightly: calendar month or last 30 days, and count or value? Ask "Do you mean the number of orders in October 2026?" (b) Very: best by revenue, order count, margin or recency? Ask "Best by total paid revenue, by number of orders, or something else?" (c) Mostly clear, but gross or net of refunds and by billing or shipping country. A semantic layer that defines revenue once removes most of the doubt.

Transfer. orders(id, customer_id, amount) has order 55 with amount 120.00, and order_items(order_id, product_id, qty) has 3 rows for order 55. Write the wrong query a model might produce for "revenue from order 55", give its result, and write the correct one.

▸ Solution

Wrong: SELECT SUM(o.amount) FROM orders o JOIN order_items i ON i.order_id = o.id WHERE o.id = 55; returns 360.00, because the join produces 3 rows each carrying 120.00. Correct: SELECT amount FROM orders WHERE id = 55; returning 120.00. If you need item data too, aggregate items in a subquery first, then join one row per order. The rule: aggregate at the grain where the measure lives.

Stretch. Design the accuracy evaluation for a text-to-SQL system before launch. What do you compare, and what are the traps?

▸ Solution

Build a golden set of 150+ real questions with a reference SQL written by an analyst. Score by execution accuracy: run both queries and compare result sets, not SQL text, because many different queries are correct. Traps: (1) row order, so compare as multisets unless the question asks for an order; (2) floats, so compare with a tolerance; (3) extra columns, so decide whether to compare only the requested columns; (4) a query that matches on today's data by accident, so run against a second database snapshot or perturbed data; (5) ambiguous questions, so either rewrite them or accept several references. Slice results by difficulty (single table, joins, nested, date logic). Public benchmarks such as Spider and BIRD use execution-based scoring for the same reasons.

Interview questions

Junior What is text-to-SQL and what is its biggest risk?

▸ Model answer

Text-to-SQL takes a natural-language question, generates SQL against a known schema, runs it and returns the answer in words. It removes the bottleneck of waiting for someone who knows SQL and the schema. The biggest risk is not an error, which is visible, but a query that runs and returns a plausible wrong number, for example through a join that double counts or a filter that misses rows. Those get trusted and acted on, so validation, transparency (showing the SQL) and evaluation matter as much as generation.

Mid How do you measure text-to-SQL accuracy?

▸ Model answer

Execution accuracy on a golden set: for each question, run the generated SQL and a reference SQL and compare the result sets, allowing for row order and float tolerance. Comparing SQL text (exact match) is too strict, because many queries are equivalent. I also track how often the query errors, how often it needed a retry, and latency. And I slice by question type, since joins and date logic usually fail more than single-table lookups. Spider and BIRD are the public benchmarks to know, but my own schema's golden set is what decides.

Senior Leadership wants a "chat with the warehouse" tool across 400 tables next quarter. How do you scope it to succeed?

▸ Model answer

Narrow it first. Pick one domain, say sales, with 10 to 20 curated views in a semantic layer: clear names, documented metric definitions, joins baked in. Build a golden set of 150 real questions from that team's queue and measure execution accuracy before launch. Ship with guardrails: read-only role, timeouts, cost caps, SQL shown with each answer, clarifying questions for ambiguous asks, and analyst review for anything feeding finance. Expand domain by domain, each with its own views and golden set. The model is the easy part; the semantic layer and evaluation are the project.
