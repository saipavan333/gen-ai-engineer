Track 6 · Lesson 6.1

Why evals decide everything

Start here

An eval (evaluation) is a test that scores how good your AI system's answers are.

You keep a fixed list of questions with known good answers, and a rule for scoring each answer.

Every time you change something, you run the same list and compare the score with the old version.

Without this, you look at three answers, decide it “seems better”, and miss what broke.

Evals turn guessing into measuring.

Everyday picture

Think of a cook who tastes one spoonful and says the whole pot is perfect. A good cook keeps a fixed tasting list: soup, rice, curry, the spicy dish that always goes wrong. Every time the recipe changes, they taste the same list and write down a score. An eval is that tasting list.

In the pictureIn the real system
The fixed tasting list of dishesThe golden set: the same test cases on every run
The score the cook writes downThe metric: exact match, a rule, or an LLM judge
Last week's scoresThe baseline: the current version's results
Changing the recipe only if the scores holdShip the change only if it measurably helps

Where the picture breaks. Food tastes the same every time you sample it, but an LLM can answer the same question differently on two runs, so one taste per dish is not enough.

Going deeper

Every track so far ended with the same word: measure it. This is the track that makes measuring a first-class skill. Evals are the single biggest thing separating people who demo LLM features from people who ship reliable ones — and most teams underinvest here badly.

The problem: you can’t improve what you can’t measure

LLM outputs are non-deterministic and open-ended, so “does it work?” has no obvious answer. Without a way to measure quality, every change — a new prompt, a different model, a tweaked RAG setting — is a guess. You change something, eyeball a few outputs, decide it “seems better,” and ship. Then it silently regresses on cases you didn’t check. Evals replace that vibe-driven loop with a measured one: define what “good” means, score it on a fixed set of examples, and only keep changes that move the number.

Concept

An eval (evaluation) measures the quality of an LLM system’s outputs against some definition of “good.” The core ingredients: a golden set (examples with known-good answers, Lesson 6.2), a metric (how you score an output — exact match, a rule, or an LLM-as-judge), and a baseline (the current version, so you can tell if a change helped). Run the metric over the golden set, compare to baseline, decide.

Worked example — a 12-line eval harness (free)

You don’t need a framework to start. This compares two prompt versions on a fixed set — the seed of every eval system.

# golden set: inputs with a known-correct answer/keyword
cases = [
    {"q": "What's the refund window?",   "must_include": "30 days"},
    {"q": "How do I reset my password?", "must_include": "Settings"},
    {"q": "Do you ship to Antarctica?",  "must_include": "don't know"},   # edge case
]

def score(system_fn):
    passed = 0
    for c in cases:
        out = system_fn(c["q"]).lower()
        if c["must_include"].lower() in out:
            passed += 1
    return passed / len(cases)

print("prompt v1:", score(answer_v1))   # e.g. 0.67  (baseline)
print("prompt v2:", score(answer_v2))   # e.g. 1.00  → keep v2

Crude keyword checks are just the start (Lesson 6.3 adds LLM-as-judge for fuzzy quality), but even this turns “v2 feels better” into “v2 scores 1.00 vs 0.67.” That’s the whole leap.

At real scale: Catching a hidden regression in a bank assistant serving 50,000 chats a day

Assumptions (stated, not measured): a retail bank's support assistant handles 50,000 conversations a day across 10 intents. The "card blocked" intent is 8% of traffic.

  1. The change. A prompt tweak makes billing answers friendlier. Nobody notices that it also drops the "call this number to unblock" step for blocked cards.
  2. Damage in real traffic. Card-blocked chats per day: 50,000 x 0.08 = 4,000. If the regression breaks 15% of them, that is 600 customers a day who get a wrong answer.
  3. Why the blended number hides it. 600 / 50,000 = 1.2 points off the overall pass rate. If billing improved by 1 point at the same time, the overall score barely moves. The team ships.
  4. The eval that would have caught it. A 300-case golden set stratified by intent, with 40 card-blocked cases, scored per category. A 15-point drop on that slice is 6 of 40 cases flipping from pass to fail.
  5. Is 6 of 40 real or noise? At a 90% pass rate on 40 cases, the standard error is sqrt(0.9 x 0.1 / 40) = 0.047, so a 95% interval is about +/- 9 points. A 15-point drop sits outside that band. A 3-point drop would not, which is why you compare per case (did the same case flip?) rather than only comparing two percentages.
  6. Decision. The gate reports "card_blocked 36/40 to 30/40, 6 cases regressed" and blocks the merge. Cost of the eval run: a few minutes. Cost of skipping it: 600 bad answers a day until a complaint trickles in.
Key points
  • LLM outputs are open-ended, so without evals every change is a guess.
  • An eval needs a golden set, a metric, and a baseline to compare against.
  • The loop: change → score → compare → keep or revert. Improvement becomes measurable.
  • Evals catch silent regressions you’d never spot by eyeballing a few outputs.
  • You can start with a 12-line harness — having any eval beats having none.

A teammate says “I improved the prompt — the three examples I tried look better, let’s ship.” What’s the most important pushback?

  • A) Three hand-picked examples aren’t a measurement — run it against a fixed golden set and compare the score to the current version before shipping.
    Correct. Eyeballing a few cherry-picked outputs can’t reveal regressions on the dozens of cases you didn’t check. A fixed golden set scored against the baseline gives an honest, repeatable comparison — the core discipline of evals.
  • B) Nothing — if it looks better on a few examples, it’s better.
    This is exactly the vibe-driven trap. A change can improve three cases while breaking ten others; only a representative, fixed eval set tells you the net effect.
  • C) Ask them to also raise the temperature.
    Irrelevant to the real issue, which is the lack of measurement. Temperature is a separate decoding choice, not a substitute for evaluating the change.
  • D) Require a bigger model before shipping any prompt change.
    Model size has nothing to do with whether this prompt change is an improvement. The missing thing is an eval against a baseline, not more compute.

What do evals turn 'I think it's better' into?

  • 'It is better' — a measurable comparison against a baseline you can defend.
    Correct. Evals replace guessing with measurement, which is what engineering is.
  • A faster model.
    Evals measure quality; they don't change speed.
  • A cheaper model.
    They measure quality, not cost.
  • A bigger context window.
    Unrelated to evals.

Your overall eval score went from 0.86 to 0.87 after a prompt change. What should you check before calling it a win?

  • A) Whether the model got faster.
    Latency is a separate guardrail metric. It says nothing about whether answers got worse on some cases.
  • B) Whether the prompt got shorter.
    Prompt length is not a quality signal. The question is which cases changed outcome.
  • C) Nothing. The number went up, so the change is better.
    A blended score is a sum of wins and losses. It can rise while a critical slice quietly breaks.
  • D) Which individual cases flipped from pass to fail, especially in small or critical categories.
    Correct. A tiny net gain can hide several regressions offset by improvements elsewhere. Per-case and per-category diffs show what actually changed.
Practice

1. Name three things that can silently regress when you “just tweak the prompt,” that eyeballing a few outputs would miss.
2. Why is comparing to a baseline essential, rather than just looking at the new version’s score?
3. Your eval is just keyword matching and a teammate calls it “too crude to bother.” Defend starting with it anyway.

▸ Show solutions & reasoning

1. Examples: edge cases (the “I don’t know” path now hallucinates), format consistency (it sometimes drops the JSON structure), tone/safety (it got more verbose or less careful), and previously-working categories (fixing billing answers broke technical ones). A few hand-picked happy-path examples reveal none of these — only a broad, fixed set does.

2. A score in isolation is meaningless — is 0.82 good? You only know if a change helped by comparing to what you had. The baseline is the reference point that turns a number into a decision (“up from 0.74 → keep; down → revert”). Evaluation is fundamentally comparative.

3. Because any measurement beats none, and a crude eval still catches the most important failures (missing the key fact, breaking an edge case) and gives a repeatable score to compare versions. It’s the foundation you improve incrementally — add an LLM-as-judge for fuzzy quality later (6.3). Perfect is the enemy of started; a crude eval today prevents shipping a regression today.

Deep dive: evals are the real moat

Here’s the uncomfortable truth that separates senior practitioners: in applied GenAI, your evaluation is more valuable and more defensible than your prompt or even your model. Prompts are easy to copy and models are a commodity everyone can call — but a well-built eval set that captures exactly what “good” means for your task, including your edge cases and failure modes, is hard-won institutional knowledge. It’s what lets you adopt a new model the day it launches (just re-run the evals), confidently refactor prompts, and prove to stakeholders that quality went up. Teams that move fastest aren’t the ones with the cleverest prompts; they’re the ones with the tightest measurement loop.

This reframes the whole job. “Building an LLM feature” is really “building the eval that defines the feature, then optimizing against it.” The flywheel: ship something, watch where it fails in production, fold those failures into the golden set, and now your eval is sharper and your next iteration is safer (Lessons 6.4–6.7 make each part concrete). Most teams skip this because writing evals is less glamorous than prompt-crafting — which is exactly why doing it well is a competitive advantage. Treat the eval set as a first-class, growing asset, and everything else in this field gets easier.

Exercises: warm-up, transfer, stretch

Warm-up. Your golden set has 50 cases and v1 passes 41. v2 passes 43. Two of the cases v1 passed now fail under v2. How many cases did v2 newly fix?

▸ Solution

v2 passes 43. It kept 41 - 2 = 39 of v1's passes, so it must have fixed 43 - 39 = 4 new cases. Net +2 hides 4 fixes and 2 regressions. You inspect the 2 regressions before shipping, because the net number alone would have let them through.

Transfer. A ticket-classification model is scored on 200 cases. A teammate says a change from 0.80 to 0.83 accuracy is clearly real. Give a quick sanity check on whether 3 points is outside noise.

▸ Solution

Standard error of a proportion near 0.8 on 200 cases is sqrt(0.8 x 0.2 / 200) = 0.028, so a 95% band is about +/- 5.5 points for each version on its own. Three points is inside that band, so the two scores alone do not prove much. A better test is paired: count cases that flipped each way (for example 10 fixed, 4 broken) and run a sign or McNemar test, because both versions ran on the same cases. If the flips are lopsided the change is real even when the raw percentages look close.

Stretch. Design the minimum eval for a new feature that drafts replies to supplier emails, before any golden set exists. You have one afternoon.

▸ Solution

1) Pull 40 real supplier emails from the last month, covering at least price queries, delivery delays, invoice disputes and one out-of-scope email. 2) For each, write 2-3 must-include checks (for example, the PO number is quoted, no promise of a date not in the source) and one must-not check (no invented discount). 3) Write a 20-line harness that runs the system and scores each check, printing per-category pass rates. 4) Record today's result as the baseline in a file under version control. 5) Agree with the team that no change merges if any must-not check fails. This gives you a baseline, a metric and a gate in an afternoon, and it grows from production failures later.

Interview questions

Junior What is an eval, and why can't you just test an LLM feature by trying a few prompts?

▸ Model answer

An eval runs the system on a fixed set of inputs with known-good answers or checks and produces a score you can compare across versions. Trying a few prompts by hand fails for two reasons. The outputs vary run to run, so a handful of samples tells you little. And a change usually helps some cases and hurts others, so the cases you happen to try are not the ones that broke. A fixed set plus a baseline turns 'it seems better' into 'it moved from 0.74 to 0.81 and these three cases regressed'.

Mid Two prompt versions score 0.82 and 0.84 on a 150-case set. How do you decide whether to ship?

▸ Model answer

First, the difference is small relative to noise: on 150 cases the standard error near 0.83 is about 3 points. So I would look at paired flips, the cases each version gets right that the other gets wrong, and run a McNemar test. Second, I would check per-category results and any must-pass cases such as refusals or safety. Third, I would check guardrails like latency and token cost. If flips favour the new version, no critical case regressed and cost is flat, ship it behind a gradual rollout. Otherwise, grow the set in the categories that matter before deciding.

Senior Your company has 12 LLM features and no shared eval practice. How would you set one up across teams?

▸ Model answer

I would start with a thin shared standard, not a platform. Each feature owns a versioned golden set in its repo with a category tag per case and a list of must-pass cases. A shared harness runs code checks plus an LLM judge that has been calibrated against human labels, and it emits per-case results in one format. CI runs the critical subset on every PR and the full set nightly, and posts per-category diffs. Production failures from tracing get triaged weekly into the sets. I would track two org metrics: share of features with a gate in CI, and time from incident to new test. Then I would invest in tooling only where teams hit the same pain repeatedly.
