Offline vs online evals

Start here

Offline evals test the system on your golden set before you ship. They are fast, cheap and repeatable.

Online evals watch real users after you ship.

An A/B test sends some users to the new version and compares results, like how many problems get solved.

Offline is a practice test; online is the real thing.

Use both, and turn online failures into new offline cases.

Everyday picture

Offline eval is a driving test in an empty car park: same cones every time, cheap, safe, and you can repeat it. Online eval is watching how the new driver does on real roads in rush hour. You would never skip the car park test, but passing it does not prove you can handle a bus cutting in.

In the pictureIn the real system
The car park test with the same conesOffline eval on a fixed golden set
Real roads in rush hourOnline eval on production traffic
A bus cutting inReal user queries your golden set never imagined
Comparing two learner drivers on the same roadsAn A/B test: two versions, real users, one metric chosen in advance

Where the picture breaks. A real learner driver gets better with practice, while your users keep changing what they ask, so the 'road' moves under you even if the system stays the same.

Going deeper

Your golden set tells you a change is good before you ship. Real users tell you if it’s actually good after you ship. Mature teams use both — and know the gap between them is where surprises live.

Two complementary measurements

So far we’ve done offline eval: run the system on a fixed golden set, score it, decide. It’s fast, cheap, and repeatable — perfect for gating changes. But a golden set is a proxy: it’s your best guess at what real usage looks like, and it can’t capture everything (new query types, real user behavior, edge cases you didn’t imagine). Online eval measures the system on real production traffic — via A/B tests, user feedback, and outcome metrics. It’s the ground truth, but it’s slower, needs live traffic, and risks exposing users to a worse version.

Concept

Offline evaluation scores the system on a fixed dataset (your golden set) before deployment — fast, repeatable, cheap. Online evaluation measures real production behavior: an A/B test sends some users to the new version and compares outcomes; user feedback (thumbs up/down, ratings, corrections) and outcome metrics (task completion, resolution rate, retention) reveal true impact. Offline is a proxy; online is ground truth.

Worked example — capture online feedback (free)

Online eval starts with logging the right things per request so you can measure real outcomes. No special service needed to begin.

import json, time

def log_interaction(request_id, version, query, answer, latency_ms):
    record = {
        "id": request_id, "version": version,        # which variant (for A/B)
        "query": query, "answer": answer,
        "latency_ms": latency_ms, "ts": time.time(),
        "feedback": None,                          # filled in when the user reacts
    }
    append_to_log(record)

def record_feedback(request_id, thumb):                 # user clicked 👍/👎
    update_log(request_id, {"feedback": thumb})

# later: compare versions on real traffic
# win_rate(version="B") vs win_rate(version="A")  → did B actually do better?

This is the raw material of online eval: every interaction tagged with its version, latency, and (when available) user feedback, so you can compare variants on the only data that ultimately matters — real usage.

At real scale: Sizing an A/B test for a shopping assistant with 200,000 sessions a day

Assumptions: an e-commerce assistant handles 200,000 sessions a day. The primary metric, chosen before the test, is resolution rate (the session ends without escalation to a human). Baseline is 62%. The candidate prompt already passed the offline gate.

  1. Smallest lift worth detecting. The team decides 2 points (62% to 64%) is worth shipping.
  2. Sample size per arm (95% confidence two-sided, 80% power): n = (1.96 + 0.84)^2 x (0.62 x 0.38 + 0.64 x 0.36) / 0.02^2 = 7.84 x 0.466 / 0.0004, about 9,100 sessions per arm.
  3. Exposure. Send 5% of traffic to each arm: 10,000 sessions per arm per day. You reach the sample size in about one day, but run seven days anyway so weekday and weekend behaviour are both covered. Decide in advance not to stop early just because day 2 looks good.
  4. Guardrails. p95 latency must stay under 3 s, cost per session within +10%, escalation of high-value orders must not rise. Any guardrail breach stops the test regardless of the primary metric.
  5. Thumbs signal. If 3% of sessions leave a rating, that is 300 ratings per arm per day, skewed toward angry users. Use them to find failure examples, not to decide the winner.
  6. Close the loop. Sample 200 failed sessions from the candidate arm, label them, and add the new failure types to the golden set so the next offline gate already knows them.

Note: the 1.96 and 0.84 values are the standard normal quantiles for 95% two-sided confidence and 80% power.

Key points
  • Offline (golden set) is fast, cheap, repeatable — use it to gate every change before shipping.
  • Online (A/B, feedback, outcomes) is the ground truth — use it to learn what actually works.
  • Offline is a proxy; the offline–online gap is where surprises (and learning) live.
  • Watch guardrail metrics (latency, cost, errors) alongside quality — a slow “better” answer isn’t better.
  • Feed online failures back into the golden set so offline gets more representative over time.

A prompt change improves your offline golden-set score by 8%, so you ship to 100% of users immediately. Why is that risky?

  • A) Offline is a proxy — the golden set may not represent all real traffic, so you should roll out gradually (A/B) and watch real metrics before going to 100%.
    Correct. An offline win is necessary but not sufficient: the golden set can miss query types, real user behavior, or trade-offs (e.g., latency). A staged rollout / A/B test lets you confirm the improvement on real traffic and catch regressions the proxy missed before everyone is affected.
  • B) It’s not risky — an 8% offline gain guarantees real-world improvement.
    No offline number guarantees online results; the golden set is an approximation. Shipping to everyone on offline evidence alone is how teams get blindsided by real-world regressions.
  • C) Offline evals are useless, so the 8% means nothing.
    Offline evals are very useful — they’re your cheap gate. The point isn’t to distrust them, but to confirm with online data before full rollout. Both matter.
  • D) You should have skipped offline and only tested online.
    Skipping offline would expose users to untested changes — the opposite of safe. Offline gates first, then online validates; you want both in sequence, not online alone.

Offline evals pass in CI but production quality dropped. Most likely cause?

  • Drift — the golden set is frozen, so only online evals on live traffic catch new failure modes.
    Correct. Offline proves no regression on known cases; online reveals the unknown ones.
  • The CI server is down.
    Passing offline evals with degraded prod is the drift signature.
  • The model got smaller.
    Nothing implies a model change.
  • Too many golden cases.
    Set size isn't the issue; coverage of new cases is.

On day 2 of a planned 7-day A/B test, the new version is ahead by 3 points with p = 0.04. The product manager wants to stop and ship. What is the problem?

  • A) 3 points is too large to be real.
    Large effects can be real. The issue is the stopping rule, not the size.
  • B) Nothing; p below 0.05 means the result is real.
    A p-value is only valid for the analysis you planned. Repeated peeking breaks that guarantee.
  • C) A/B tests should never use p-values.
    They usually do. The point is to use them as designed, with a fixed horizon or a proper sequential method.
  • D) Peeking and stopping early inflates false positives; the test was sized and scheduled for 7 days, including weekly patterns.
    Correct. Checking repeatedly and stopping at the first significant result makes 'significant' far more likely by chance. Stick to the plan or use a sequential test designed for peeking.
Practice

1. Give one thing offline evals catch that online can’t, and one thing online catches that offline can’t.
2. Why are thumbs-up/down ratings a biased signal, and how would you supplement them?
3. You ship a change that improves answer quality but quietly doubles latency. Which eval should have caught it, and how?

▸ Show solutions & reasoning

1. Offline catches regressions before any user is affected (cheap, repeatable, on known cases) — online can’t prevent harm before exposure. Online catches what your golden set never imagined — novel query types, real user behavior, and true outcomes (did they actually get helped?) — which offline, being a fixed proxy, structurally can’t see. They’re complementary by design.

2. Ratings are sparse and self-selected: most users don’t click, and those who do skew toward extremes (especially the frustrated). So they over-represent unhappy cases and miss the silent majority. Supplement with implicit signals (did they accept the answer, retry, escalate, complete the task?) and periodic structured surveys or human review of sampled interactions — triangulate rather than trust one noisy signal.

3. A guardrail metric on latency — measured both offline (you can time responses on the golden set) and online (monitor p95 latency per version). Quality evals alone would have shown a win and missed the regression. Always pair quality metrics with cost/latency/error guardrails so an improvement on one axis can’t silently wreck another (this is exactly Track 8’s concern).

Deep dive: closing the offline–online loop

The magic happens when offline and online feed each other. Online surfaces reality — a cluster of queries your bot handles badly, a new way users phrase things, an edge case you never tested. You harvest those failures, label them, and add them to the golden set. Now your offline eval is more representative, so the next change is gated against the real problems, and you catch them before shipping. Over months this loop drags your proxy ever closer to reality, which is why teams with strong observability (Lesson 6.5) improve so much faster: they have a firehose of real failures to learn from.

A few practical disciplines. Run A/B tests with a clear primary metric chosen in advance (resolution rate, task success, accepted-answer rate) and enough traffic to reach significance — don’t peek and stop early. Watch guardrail metrics (latency, cost, error/refusal rates) so a quality win can’t hide a serious regression. And remember the asymmetry: offline lets you fail safely and cheaply, online lets you learn truthfully but at the cost of real exposure — so the standard flow is offline gate → small online rollout → full rollout, never straight to 100%. Master this and “shipping an LLM change” becomes a controlled, measured process instead of a leap of faith.

Exercises: warm-up, transfer, stretch

Warm-up. A feature gets 40,000 sessions a day and 2% leave a thumbs rating. Of the ratings, 70% are thumbs-down. Does that mean 70% of sessions are bad?

▸ Solution

No. 40,000 x 0.02 = 800 ratings a day, and people who rate are self-selected, mostly the unhappy ones. The 70% describes raters, not all users. Use implicit signals on all 40,000 sessions (accepted answer, retry within 60 s, escalation) and a weekly human review of a random sample of, say, 100 sessions to estimate the true bad rate.

Transfer. Your offline golden set says v2 is better by 6 points, but the A/B test shows no difference in resolution rate. List three explanations and how you would check each.

▸ Solution

1) The golden set is not representative: compare its intent mix with last month's traffic; if it over-weights a category v2 improved, the offline gain will not show up live. 2) The metric gap: offline scores answer quality while resolution also depends on things like policy or UI; read 100 sessions where v2 answered well and still escalated. 3) The test lacks power for a smaller real effect: compute the minimum detectable effect from your traffic; if it is 3 points, a real 1-point gain is invisible. Then fold the live failure types into the golden set.

Stretch. Design the rollout plan for a new RAG model on a bank's internal policy assistant used by 8,000 staff, where wrong answers carry compliance risk.

▸ Solution

Stage 0, offline: full golden set plus a locked compliance set where every critical case must pass. Stage 1, shadow: run the new version on live questions without showing answers; a judge and a compliance reviewer compare 300 shadow answers with production answers. Stage 2, canary: 5% of staff, about 400 people, for one week, with guardrails on refusal rate, citation coverage and latency, plus a one-click 'wrong answer' report reviewed daily. Stage 3, 50/50 A/B for two weeks with a pre-registered metric such as answer acceptance without follow-up. Stage 4, full rollout with a rollback switch. Every reported wrong answer becomes a golden-set case before the next release.

Interview questions

Junior What is the difference between offline and online evaluation?

▸ Model answer

Offline evaluation runs the system on a fixed dataset, such as a golden set, before release. It is cheap, fast and repeatable, so it is the gate for every change. Online evaluation measures behaviour on real traffic after release, through A/B tests, user feedback and outcome metrics like resolution or task completion. Offline is a proxy and can miss new kinds of queries; online is the ground truth but is slower and exposes real users. You use offline to block obvious regressions and online to confirm the change helps real people.

Mid How do you choose the primary metric for an A/B test of an LLM feature?

▸ Model answer

It should reflect the outcome the business cares about, move within the test window, and be measured on every session. For a support bot that is often resolution without escalation; for a writing assistant, the share of drafts accepted with light edits. I would pick one primary metric before the test, size the test for the smallest lift worth shipping, and define guardrails such as latency, cost and complaint rate that can stop the test on their own. Thumbs ratings are a poor primary metric because they are sparse and skewed; I use them to find examples.

Senior Offline scores keep rising release after release, but customer satisfaction is flat. What do you do?

▸ Model answer

I would treat it as the proxy drifting away from reality. First, compare the golden set's distribution with current traffic: intents, languages, length, new products. Second, read a random sample of live sessions with low satisfaction and label why they failed; if those failure types are missing from the golden set, the eval has gone stale. Third, check whether the offline metric rewards something users do not value, like longer answers. Then fix the loop: a weekly job that samples production failures into the set, a locked set refreshed each quarter, and an online metric reported next to every offline score.
