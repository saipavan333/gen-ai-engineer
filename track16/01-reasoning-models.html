Reasoning models & test-time compute

A major shift in the field: instead of only making models bigger, we now let them think longer at answer time. Understanding “reasoning models” and “test-time compute” keeps you current and helps you choose the right model for a job.

School-kid picture

A standard model is a quiz contestant who must hit the buzzer immediately. A reasoning model is allowed to scribble on a notepad for a minute before answering. On a hard maths question the notepad wins; on 'what colour is the sky' it just wastes a minute. And you pay for every page of scribbling. The analogy breaks because the model's scribbling is not always shown to you, but you are still billed for it.

Two ways to make a model smarter

For years, the recipe for a more capable model was “train a bigger one on more data.” That still works, but there’s a second lever that reshaped the field: spend more compute when answering, not just when training. A reasoning model (sometimes called “o1-style,” after an early prominent one) is trained to produce a long internal chain-of-thought — working through a problem step by step, checking itself, exploring approaches — before it commits to a final answer. That extra deliberation at inference is called test-time compute: the model literally uses more tokens and time to think, and on hard problems that buys markedly better accuracy.

You already met the seed of this in Track 2: chain-of-thought prompting (“think step by step”) improves reasoning. Reasoning models bake that in and take it much further, having been trained specifically to reason at length and self-correct. The result is a model that’s dramatically stronger on math, coding, logic, and multi-step planning — the tasks where a single quick pass tends to slip.

When to reach for one (and when not)

Reasoning models aren’t a free upgrade — they’re a trade. Because they generate a long internal reasoning process, they’re slower and more expensive per answer (you pay for all those thinking tokens). So the choice is task-driven. For hard, multi-step problems — complex math, tricky debugging, planning, careful analysis — the accuracy gain is well worth the cost.

For simple, high-volume tasks — classification, extraction, straightforward Q&A, formatting — a standard (often smaller) model is faster, cheaper, and just as good; paying a reasoning model to “think hard” about a trivial task is waste. This is a natural extension of model routing from Track 8: send the genuinely hard requests to a reasoning model and everything else to a cheaper one.

The field moves fast — reason from principles

Specific model names, prices, and benchmarks change monthly, so don’t memorize them — memorize the principle: capability can come from more training or more inference-time thinking, and thinking longer trades cost/latency for accuracy on hard problems. That framing stays true no matter which model is on top this quarter. Always check current options before choosing.

Buy accuracy with compute

Increase the number of reasoning passes. Accuracy rises, then flattens, while cost and latency keep climbing in a straight line.

At real scale: Routing 1 million requests a day between a fast model and a reasoning model

Assume an assistant gets 1,000,000 requests a day, of which 5% are genuinely hard (multi-step debugging, calculations). A hard request uses about 4,000 thinking tokens when extended thinking is on. All numbers except prices are assumptions.

  1. Thinking is billed as output. Anthropic reports thinking as part of billed output tokens, visible in usage.output_tokens_details.thinking_tokens (extended thinking docs).
  2. Think on everything. On Claude Sonnet 5.5 at $10 per million output tokens (Anthropic models overview): 1,000,000 x 4,000 = 4 billion tokens = $40,000/day just for thinking.
  3. Think only on hard requests. 50,000 x 4,000 = 200M tokens = $2,000/day. Routing cuts the thinking bill by 95%.
  4. Price the router. A small classifier, or a cheap model call of about 200 input tokens, decides "hard or not". On a model priced from $0.10 per million input tokens, 1M x 200 = 200M tokens = about $20/day.
  5. Measure the misroutes. On a labelled set of 1,000 requests, suppose the router sends 15% of hard requests to the fast model. Those 7,500 a day get weaker answers. Add an escalation rule: if the fast model's answer fails a check (tests fail, numbers disagree), retry on the reasoning model.
  6. Latency. 4,000 thinking tokens at an assumed 80 tokens/second is about 50 seconds. Show progress, or move hard jobs to an async queue.
Key points
  • Capability comes from two levers: bigger training and more test-time compute (thinking longer at answer time).
  • Reasoning models generate a long internal chain-of-thought and self-correct before answering — much stronger on math/code/logic.
  • It’s the trained-in, supercharged version of Track 2’s chain-of-thought prompting.
  • They’re slower and pricier — use them for genuinely hard problems; use standard/smaller models for simple, high-volume tasks.
  • This is model routing (Track 8) by difficulty: hard → reasoning model, easy → cheap model.
Practice

Your product has two features: (a) categorize incoming support emails into 8 buckets, at high volume; (b) a “solve this multi-step engineering calculation” assistant used occasionally. Which should use a reasoning model, which shouldn’t, and how would you architect the choice?

▸ Show solution & reasoning

(a) Categorization → standard/small model. It’s a simple, high-volume classification task; a small fast model at temperature 0 nails it cheaply. A reasoning model here would multiply cost and latency for no accuracy benefit — you’d be paying it to deliberate over “is this billing or shipping,” which needs no deliberation.

(b) Multi-step calculation → reasoning model. This is exactly where test-time compute pays off: the problem has several dependent steps where a quick pass often slips, and the volume is low, so the higher per-call cost is affordable and the accuracy gain matters.

Architecture: route by task. The system knows which feature is calling, so it selects the model accordingly — cheap model for categorization, reasoning model for the calculator — rather than using one model for everything. That’s model routing (Track 8) applied to the reasoning/standard split, and it optimizes cost and latency without sacrificing quality where quality matters. You’d confirm the choice with evals: measure accuracy and cost per feature, and only pay for reasoning where it actually moves the number.

What is “test-time compute,” and why does it matter?

  • A) Compute spent while answering — the model generates a long internal reasoning process before responding, trading cost/latency for better accuracy on hard problems.
    Correct. Rather than only scaling training, reasoning models spend more compute at inference by “thinking” at length (many reasoning tokens) before the final answer. On hard math/code/logic this meaningfully improves accuracy, at the price of speed and money.
  • B) The time it takes to run your test suite in CI.
    Unrelated — that’s software testing. Here “test-time” means inference time (when the model is answering), as opposed to training time.
  • C) Compute used only during training to make the model bigger.
    That’s train-time scaling, the older lever. Test-time compute is the other lever: extra thinking at answer time, independent of model size.
  • D) A way to make every model faster and cheaper.
    The opposite — spending more compute at answer time makes responses slower and more expensive. The point is that it buys accuracy on hard tasks, so you use it selectively.

What do reasoning models spend to get better answers on hard problems?

  • Test-time compute — sampling more, thinking longer, and checking their own work at inference.
    Correct. They trade extra inference-time computation for accuracy, with diminishing returns.
  • More training data, live.
    The shift is at inference time, not retraining.
  • A bigger context window only.
    It's about extra reasoning compute, not just window size.
  • Nothing — they're just larger.
    The key is spending compute to think, not raw size.

You give a reasoning model a 'think step by step, list every assumption' prompt on top of its built-in thinking. Tokens double, accuracy is unchanged. What is the best reading?

  • A) Double the thinking budget again until accuracy improves.
    If accuracy is flat, more tokens is likely to keep spending without gain. Find where the curve flattens first.
  • B) Reasoning models cannot follow instructions.
    They follow instructions; the issue is redundant prompting.
  • C) The model ignored the prompt, which means it is broken.
    It may have followed it; it just did not help. That is a result, not a fault.
  • D) The model already reasons internally, so the extra CoT instruction mostly added tokens; measure and drop it unless an eval shows a gain.
    Right. Reasoning models are trained to think before answering. Classic CoT prompting is often redundant on them, so it should earn its place on an eval.
Deep dive: why this changes how you build, not just what you buy

The rise of test-time compute has a few consequences worth carrying into interviews and design discussions. First, it adds a genuinely new dimension to the cost/latency thinking from Track 8: “which model” is no longer just big-vs-small, it’s also how-hard-should-it-think, and both are routing decisions driven by task difficulty and your quality bar. A mature system might triage a request — cheap model first, escalate to a reasoning model only if the task looks hard or the first answer fails a check — spending expensive thinking exactly where it earns its keep. That triage is an architecture choice you can design, not a property of any single model.

Second, it reframes some problems you’d otherwise solve with elaborate agent scaffolding. A lot of early agent work manually orchestrated “think, then act, then reflect” loops (Track 4, Track 11) partly to squeeze more reasoning out of models that answered too quickly. As models internalize deep reasoning, some of that scaffolding gets simpler — the model does more of the careful thinking itself.

But not all of it: agents still need tools, memory, and bounded loops, and reasoning models still hallucinate, still can’t know private facts, and still need grounding and evaluation. The durable lesson is that the field advances by giving models new ways to spend compute — more parameters, more data, more inference-time thinking, more tools — and your job is to compose those capabilities into reliable systems.

Knowing that reasoning is now a dial you can turn, at a price, is what lets you make that call deliberately instead of defaulting to the most expensive model for everything.

Exercises: warm-up, transfer, stretch

Warm-up. A reasoning model answers in 300 visible output tokens but the usage shows 3,300 output tokens. At $10 per million output tokens, what did the thinking cost per request and per 100,000 requests?

▸ Solution

Thinking tokens = 3,300 - 300 = 3,000. Per request: 3,000 x $10 / 1,000,000 = $0.03. Per 100,000 requests: $3,000. Always read the usage field; visible text underestimates the bill.

Transfer. Design a 'try cheap first, escalate if needed' flow for a coding assistant that writes unit-testable functions.

▸ Solution

Step 1: fast model writes the function and tests. Step 2: run the tests in a sandbox. Step 3: if they pass, return. If they fail, send the code, the failing test output and the task to the reasoning model. Step 4: run tests again; if they still fail, return the best attempt with the failure shown. Track the escalation rate and cost per solved task. The tests are the cheap, objective check that makes escalation safe.

Stretch. Snell et al. (2024) report that spending test-time compute well can beat simply using a larger model in some settings. What conditions make that more likely, and how would you test it for your workload?

▸ Solution

It is more likely when problems are of moderate difficulty for the smaller model, when there is a good way to check or score candidates (tests, verifiers), and when compute can be adapted per problem instead of spent evenly. Test it by building an eval set grouped by difficulty, then compare cost and accuracy for: small model once, small model with N samples plus a verifier, small model with reasoning on, and a larger model once. Plot accuracy against cost per task and pick the best point per difficulty group.

Interview questions

Junior What is a reasoning model?

▸ Model answer

It is a model trained to produce a long internal chain of thought before its final answer: working through steps, checking itself, trying other approaches. That uses more tokens at answer time, called test-time compute, and gives better results on hard maths, coding and planning. The cost is higher price, because thinking tokens are billed, and more latency. For simple tasks a standard model is cheaper and just as good.

Mid How do you decide whether a feature should use a reasoning model?

▸ Model answer

Run an eval on representative cases with both options and compare accuracy, cost per request including thinking tokens, and latency. Reasoning tends to pay off on multi-step tasks with a clear right answer and low to moderate volume. For high-volume simple tasks, use a fast model. Often the answer is both: route by difficulty, or try the fast model first and escalate when a check fails. Set thinking budgets and watch the usage field so cost does not surprise you.

Senior How does test-time compute change system design compared with the 'just pick a bigger model' era?

▸ Model answer

Compute becomes a per-request decision, not a fixed property of the deployed model. So you design routing, budgets and verification: a difficulty classifier or cascade, thinking budgets per feature, verifiers such as tests or rule checks to decide when more compute is worth it, and async flows for long jobs. Observability must track thinking tokens and latency separately. Some agent scaffolding gets simpler because the model plans more by itself, but tools, grounding, bounded loops and evals stay essential.
