Quantization

Quantization shrinks a model by storing its weights with fewer bits — making it smaller, faster, and runnable on cheaper hardware, with usually only a small quality cost. It’s why you can run capable models on a laptop (the free local stack of this whole course), and a key lever when you self-host.

Smaller numbers, smaller model

A model’s weights are numbers, normally stored at 16 bits each (fp16). Quantization stores them with fewer bits — 8 (int8) or even 4 (int4) — so the model takes proportionally less memory and runs faster, because there’s less data to move and compute. The trade-off is a small loss of precision in each weight, which usually causes only a minor quality drop. You already saw this in Track 5: QLoRA quantizes the base model to 4-bit so a big model fits on a free GPU.

Concept

Quantization reduces the number of bits used to store each model weight (e.g., 16-bit → 8-bit → 4-bit). Lower precision means less memory and faster compute, at the cost of some accuracy. The trade-off is usually favorable: 8-bit is often nearly lossless, and 4-bit is a popular sweet spot for running large models on modest hardware. Local runtimes like Ollama serve quantized models (often in the GGUF format) by default — which is how this course runs models for free.

School-kid picture

Imagine writing down everyone's height in a class. You could write 152.3847 cm, or just 152 cm. The short version takes much less paper and is almost always good enough. Quantization does that to a model's billions of numbers: it rounds them to fewer digits so the model fits in less memory. Where it breaks: rounding a height loses nothing you care about, but a few of a model's numbers matter a lot, so good quantization methods round those more carefully than the rest.

Worked example — quantized models, free (Ollama)

You’ve been using quantization all along — Ollama ships quantized models so they run on everyday hardware.

# Ollama serves quantized models by default — this is why it fits on a laptop:
$ ollama pull llama3.1:8b          # downloads a ~4-bit quantized build (~4-5 GB, not ~16 GB)
$ ollama run llama3.1:8b           # runs fast on CPU/modest GPU thanks to quantization

# You can choose a quant level when available (higher q = more bits = better quality, more memory):
$ ollama pull llama3.1:8b-instruct-q4_K_M    # 4-bit (small, fast)
$ ollama pull llama3.1:8b-instruct-q8_0       # 8-bit (bigger, closer to full quality)

The lesson: quantization isn’t exotic — it’s the default that makes free local models practical. When self-hosting, choosing a quant level is one of your main cost/quality dials.

At real scale: Fitting Qwen2.5-7B and its KV cache on a 24 GB GPU

Facts: Qwen2.5-7B-Instruct has 7.61B parameters, 28 layers, 4 key-value heads and hidden size 3,584 with 28 attention heads, so head dimension is 128 (model card and config). Locally, ollama show qwen2.5:7b reports quantization Q4_K_M and ollama list shows 4.7 GB. The 24 GB GPU and the traffic are our assumptions.

  1. Weights at each precision. bf16: 7.61B x 2 bytes = 15.2 GB. int8: 7.6 GB. The Q4_K_M file at 4.7 GB works out to 4.7e9 x 8 / 7.61e9 = about 4.9 bits per weight, not exactly 4, because k-quants keep scales and some tensors at higher precision.
  2. KV cache per token. 2 (K and V) x 28 layers x 4 KV heads x 128 dims x 2 bytes (fp16) = 57,344 bytes, about 56 KB a token.
  3. KV for real traffic. 16 concurrent conversations at 8,000 tokens each = 128,000 tokens x 56 KB = about 7.3 GB.
  4. Does it fit in 24 GB? bf16: 15.2 + 7.3 = 22.5 GB, leaving about 1.5 GB for activations and runtime overhead, which is too tight. Q4_K_M: 4.7 + 7.3 = 12 GB, leaving room to double concurrency.
  5. So quantization buys concurrency, not just fit. Every GB saved on weights is about 17,000 more tokens of KV cache, which means more users per GPU and a lower cost per request.
  6. The quality check. Before shipping Q4, run your golden set on bf16 (or the provider's full model) and on Q4. If the per-case regression list is short and not concentrated in one task type, ship it; if arithmetic or extraction cases cluster in the failures, try Q8 or AWQ/GPTQ builds and re-measure.

Trade precision for memory

Step down the precision and watch the model shrink. Somewhere on this slider is the point where a 7B model fits on hardware you already own.

Key points
  • Quantization stores weights with fewer bits (16 → 8 → 4), shrinking the model proportionally.
  • Result: less memory, faster, cheaper hardware — with a usually-small quality drop.
  • 8-bit is often near-lossless; 4-bit is the popular sweet spot for big models on modest hardware.
  • It’s the default that makes free local models (Ollama/GGUF) practical, and underpins QLoRA (Track 5).
  • When self-hosting, the quant level is a key cost/quality dial — measure the quality impact for your task.

You want to run a capable open model on a single modest GPU that can’t hold the full-precision version. What’s the standard move?

  • A) Use a quantized build (e.g., 4-bit) so the model fits in less memory and runs faster, accepting a small quality trade-off.
    Correct. Quantization is exactly for this: a 4-bit build cuts memory ~4×, letting a model that wouldn’t otherwise fit run on modest hardware, usually with only a minor quality drop. It’s why local runtimes ship quantized models by default.
  • B) Give up — you need a bigger GPU.
    You often don’t — quantization is designed to make large models fit smaller hardware. Reaching for more expensive hardware before trying quantization wastes money.
  • C) Lower the temperature to use less memory.
    Temperature is a decoding setting; it has nothing to do with model memory footprint. Quantization is what reduces memory.
  • D) Truncate the prompt to fit the model in memory.
    Prompt length affects the context/KV memory a bit, but it doesn’t shrink the model weights, which are what don’t fit here. Quantizing the weights is the right fix.

What does quantization trade, and why is it worth it?

  • A little accuracy for a large drop in memory — letting a big model run on modest hardware.
    Correct. Lower-precision weights shrink memory; int8 is near-lossless, int4 a small dip.
  • Speed for accuracy, with no memory change.
    The main win is memory (and often speed), by lowering precision.
  • Nothing — it's free with no downside.
    There's a small, measurable quality cost you should check.
  • It makes the model larger.
    It makes it smaller.

Ollama lists qwen2.5:7b (7.61B parameters, Q4_K_M) at 4.7 GB rather than the 3.8 GB that exactly 4 bits a weight would give. Why?

  • A) The file includes the KV cache for a full context.
    The KV cache is allocated at run time and depends on context length and concurrency; it is not in the model file.
  • B) k-quant formats store per-block scale factors and keep some sensitive tensors at higher precision, so the average is closer to 5 bits a weight.
    4.7e9 bytes x 8 / 7.61e9 is about 4.9 bits a weight. 'Q4' names the main block format, not the exact average.
  • C) Ollama stores two copies of the weights.
    There is one set of quantized weights; the overhead comes from scales and mixed precision.
  • D) Quantization does not really reduce size; the 3.8 GB number is a myth.
    bf16 would be about 15.2 GB, so 4.7 GB is a 3x reduction. The arithmetic is real; the overhead is just bigger than zero.
Practice

1. Roughly how much memory does a 13B-parameter model need at fp16 vs int4, and why?
2. When would you not want to go down to 4-bit?
3. Connect quantization to QLoRA from Track 5 — what role did it play there?

▸ Show solutions & reasoning

1. At fp16 (2 bytes/weight), 13B params ≈ 26 GB just for weights; at int4 (~0.5 byte/weight) ≈ 6–7 GB. (Real usage adds some overhead for activations/KV cache.) The footprint scales with bits-per-weight, so dropping from 16 to 4 bits is roughly a 4× reduction — the difference between needing a big GPU and fitting on a modest one.

2. When the quality drop matters for your task — e.g., high-stakes accuracy, complex reasoning, or a smaller model where 4-bit degradation is more noticeable. Aggressive quantization (4-bit and below) compounds with a model that’s already near its limits. The discipline: measure your task’s quality at each quant level (Track 6) and pick the lowest bits that still clear your bar — sometimes that’s 8-bit, sometimes 4-bit is fine.

3. QLoRA = Quantized + LoRA: it loads the frozen base model in 4-bit (quantization) to slash memory, then trains a small LoRA adapter on top. The quantization is precisely what let you fine-tune a large model on a single free GPU — same technique as here (shrink the model to fit cheap hardware), applied to training rather than serving.

Deep dive: where quantization fits in your serving strategy

Quantization matters most when you control the serving — i.e., you self-host an open model rather than calling a hosted API. (With a pay-per-token API, the provider handles the hardware; your levers are routing, caching, and token budgeting, not quant levels.) Self-hosting becomes attractive at scale (no per-token fees, just your hardware), for privacy (data never leaves — Track 7), or for customization (your own fine-tunes). In that world, quantization is a primary dial: it determines what hardware you need and how many requests one GPU can serve, directly shaping your cost per request.

The engineering nuance is that quantization quality isn’t uniform — it depends on the method (modern schemes like GPTQ, AWQ, and the GGUF k-quants preserve quality better than naive rounding), the model (bigger models tolerate quantization better; small ones degrade more), and the task (simple tasks barely notice 4-bit; subtle reasoning may).

So you don’t pick a quant level by reputation — you serve a couple of candidates and run your eval set (Track 6) to see the real quality-vs-memory trade-off for your workload, then choose the smallest that clears your bar. Combined with the rest of this track, the pattern for self-hosters is: quantize to fit cheap hardware, batch to keep it busy (next lesson), cache and route to avoid work, and budget tokens to keep every call lean. That stack is how teams run capable models affordably — and it’s the same stack that lets you run them for free on a laptop.

Exercises: warm-up, transfer, stretch

Warm-up. Estimate weight memory for a 32B-parameter model at bf16, int8 and 4-bit (assume 4.9 bits a weight for the 4-bit format).

▸ Solution

bf16: 32e9 x 2 = 64 GB. int8: 32 GB. 4-bit at 4.9 bits: 32e9 x 4.9 / 8 = 19.6 GB. So a 32B model goes from needing an 80 GB-class GPU to fitting, with modest KV room, on a 24 GB card.

Transfer. Using the Qwen2.5-7B KV figure of about 56 KB a token, how many concurrent 4,000-token conversations fit in the memory left on a 24 GB GPU after the 4.7 GB Q4 weights, keeping 3 GB for runtime overhead?

▸ Solution

Free memory: 24 - 4.7 - 3 = 16.3 GB. Per conversation: 4,000 x 57,344 bytes = about 229 MB. 16.3 GB / 0.229 GB = about 71 conversations. Serving engines like vLLM allocate the KV cache in pages so they can use this space efficiently; in Ollama, RAM scales with OLLAMA_NUM_PARALLEL x context length, so you set those two knobs within this budget.

Stretch. Your team proposes 3-bit quantization of a 7B model to double concurrency. Lay out how you would decide, and name the failure pattern you would watch for.

▸ Solution

Build three candidates (bf16 reference, Q4, Q3) and run the full golden set plus a task-specific stress set (long-context recall, arithmetic, JSON extraction) on each with fixed seeds. Compare per-case, not just averages, and compute the cost per request at the concurrency each fits. Watch for failures that cluster: low-bit models often degrade first on precise tasks such as numbers, code and long instructions while chat quality looks fine. Decide with a rule set in advance, e.g. 'no more than 2 points average drop and no task family drops more than 5 points'. If Q3 fails, consider a smaller model at Q4 or KV-cache quantization instead.

Interview questions

Junior What is quantization and what does it trade off?

▸ Model answer

Quantization stores a model's weights with fewer bits, for example 16-bit down to 8 or 4. Memory drops roughly in proportion, so a 7B model goes from about 15 GB in bf16 to under 5 GB at 4-bit. Less memory also means faster decoding because generation is limited by how fast weights move from memory. The cost is some lost precision, which usually means a small quality drop that grows at lower bit-widths and on smaller models. You measure that drop on your own eval set before choosing a level.

Mid Compare GPTQ, AWQ and GGUF k-quants at a high level. When would you pick each?

▸ Model answer

All three are post-training weight quantization. GPTQ quantizes layer by layer using second-order information from calibration data to minimise error. AWQ protects the small fraction of weights that matter most, found from activation statistics, by scaling them before quantizing. GGUF k-quants are the llama.cpp/Ollama family, with block-wise scales and mixed precision, built for CPU and consumer-GPU inference. I pick GGUF for local and edge serving, and GPTQ or AWQ builds for GPU serving engines like vLLM, choosing between them by running my eval set, since the winner depends on the model and task.

Senior You run a self-hosted 70B model at bf16 on multiple GPUs. Make the case for or against moving to 4-bit.

▸ Model answer

For: weights drop about 4x, so the model may fit on fewer GPUs, which cuts cost and removes cross-GPU communication; freed memory goes to KV cache, so concurrency and throughput rise. Against: quality risk, especially on precise tasks; some kernels at low precision can be slower at large batch sizes than bf16 on high-end GPUs; and the team must operate a second artefact. I would benchmark both on our traffic: quality per task family, tokens/s at our concurrency, and cost per 1,000 requests. If 4-bit holds quality within the threshold we agree on beforehand and lowers cost per request, ship it behind a canary.
