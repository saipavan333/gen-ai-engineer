Context windows & attention

Two ideas that decide what your model can actually do in practice: how much it can hold in mind at once (the context window), and how it figures out which of those words matter (attention). Get these and you’ll design prompts and systems that work with the model instead of against it.

Why there’s a limit at all

An LLM has no long-term memory of your conversation and no ability to “open” a file. The only thing it can use is the text you put in front of it right now. That text — everything the model can see in a single step — has a maximum size, measured in tokens. This is the context window. Understanding it explains why long documents need special handling (Track 3), why long chats start “forgetting” the beginning, and why some requests cost far more than others.

Concept

The context window is the maximum number of tokens a model can process at once — and crucially, it’s shared by everything: your instructions, any examples, the conversation history, any documents you paste in, and the model’s own response. If a model has a 8,000-token window and your input uses 7,900, there’s only room for ~100 tokens of answer.

School-kid picture

The context window is like the desk you study at. You can only work with the pages spread on the desk; anything still in the cupboard does not exist for you right now, and a bigger desk lets you spread out more pages. Attention is your eyes jumping between pages to connect 'it' on page 3 with 'the dog' on page 1. The analogy breaks because a person can get up and fetch a page from the cupboard, while the model cannot fetch anything on its own; your code has to put it on the desk.

A myth worth killing now

Chat assistants feel like they “remember” your conversation. They don’t, internally. Each turn, the app re-sends the entire conversation so far as input. The “memory” is just resent text — and it counts against the window and your bill every single turn. When a long chat gets vague, you’ve often quietly hit the window limit and early messages are being dropped.

The catch with “just use a huge window”

Windows have grown enormously: current frontier models offer a 1M-token window (Anthropic models overview, Nov 2026). That’s great, but bigger isn’t free:

  • Cost. You pay per token. Stuffing 100K tokens of documents into every request is expensive — often needlessly, when only a paragraph was relevant.
  • Latency. More tokens to process means slower responses (we’ll quantify this in Track 8).
  • “Lost in the middle.” Models reliably use information at the start and end of a long context, but can overlook things buried in the middle. More context can paradoxically mean worse answers.

This is the core motivation for RAG (Track 3): instead of dumping everything in, retrieve only the few relevant chunks and spend your token budget wisely.

How the model uses the context: attention

Within the window, how does the model know that in “The animal didn’t cross the street because it was tired,” the word “it” refers to the animal and not the street? Through attention — the central mechanism of the transformer (the neural-network architecture behind modern LLMs). For each token, attention lets the model look back at the other tokens and decide, with a learned weight, how much each one matters for understanding this token right now.

Two practical consequences fall out of this. First, position matters: the model is sensitive to where things appear, which is why instructions often work best at the very start or very end of a long prompt. Second, attention is what makes the context window so powerful and so costly — every token can attend to every other token, and that all-pairs comparison is the expensive part (see the deep dive).

Worked example — will it fit? (free, Colab)

Before sending a big prompt, you can check its size locally and decide whether to trim or retrieve. No API needed:

!pip install tiktoken
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")

system = "You are a helpful support assistant. Answer only from the context."
context = open_your_document_text   # imagine a long string here
question = "How do I export my data?"

prompt = system + context + question
n = len(enc.encode(prompt))
WINDOW, RESERVE_FOR_ANSWER = 8000, 1000

if n + RESERVE_FOR_ANSWER > WINDOW:
    print(f"Too big: {n} tokens. Trim or retrieve instead of pasting everything.")
else:
    print(f"Fits: {n} tokens, leaving {WINDOW - n} for the answer.")

This little guard is the seed of real production logic: measure, then decide whether to send, trim, or retrieve.

At real scale: Paste the whole contract, or retrieve? Pricing 10,000 questions a day

Assume a legal team asks 10,000 questions a day about a 300-page contract (about 150,000 words, so about 200,000 tokens). Current frontier models offer a 1M-token window, so it fits (Anthropic models overview). Should you paste it every time?

  1. Paste every time. On Claude Sonnet 5.5 at $2 per million input tokens: 200,000 tokens = $0.40 per question. x 10,000 = $4,000/day, before output.
  2. Paste with prompt caching. The contract is the same prefix every time, so it can be cached. Cache reads on Sonnet 5.5 cost 5% of the base input price: 200,000 x $2 x 0.05 / 1M = $0.02 per question, about $200/day plus cache writes. Caching changes the economics a lot.
  3. Retrieve instead. Send 8 chunks x 500 tokens + 1,000 tokens of instructions = 5,000 tokens = $0.01 per question = $100/day, and the prompt is 40x shorter, so latency drops too.
  4. Attention cost. Naive attention work grows with length squared: (200,000 / 5,000)^2 = 40^2 = 1,600x more attention compute per question for the pasted version. Real systems use optimised kernels, but long prompts still mean slower first tokens.
  5. Accuracy, not just money. Facts buried mid-context can be missed ("lost in the middle"). Test both setups on 100 real questions before choosing.
  6. Scale up. The firm's full archive of 2,000 such contracts is about 400M tokens. No window holds that. Retrieval is not optional at that size.

Key points
  • The context window is the max tokens a model handles at once — shared by instructions, history, documents, and the answer.
  • Chat “memory” is just the whole conversation re-sent each turn; it costs tokens and can overflow.
  • Bigger windows aren’t free: more cost, more latency, and the “lost in the middle” effect — which is why RAG retrieves instead of dumping.
  • Attention lets each token weigh how much every other token matters — this is how references and meaning get resolved.
  • Position matters: put key instructions where the model reliably looks (start/end), and budget tokens deliberately.

A user has chatted with your assistant for an hour. They say “summarize what we discussed,” but the summary ignores the first 20 minutes. What’s the most likely cause?

  • A) The conversation grew past the context window, so the earliest messages were truncated and aren’t in the model’s input anymore.
    Correct. Each turn re-sends the whole history, but only what fits in the window is actually seen. Once the chat exceeds the window, the oldest tokens drop off — so the model genuinely can’t summarize what it can no longer see. The fix is summarizing or retrieving earlier turns, not “reminding” it.
  • B) The model’s knowledge cutoff doesn’t cover the start of the chat.
    Knowledge cutoff is about training data, not your live conversation. The early messages were generated today, long after training — the issue is the window, not the cutoff.
  • C) Attention can only look at the previous 5 tokens.
    Attention can look across the entire context window, not just a tiny recent slice. The limit here is the window’s total size, not attention’s reach within it.
  • D) The model deleted the early messages from its memory to save space.
    The model has no persistent memory to delete from. It only ever sees the text re-sent this turn; the early messages were dropped by the window limit before they ever reached it.

Resolving 'it' to the right earlier noun in a sentence is the job of…

  • Attention — it lets each token weigh every earlier token to decide what matters.
    Correct. Attention is the mechanism that reaches back and uses relevant context.
  • The tokenizer.
    Tokenizing only splits text; it doesn't resolve references.
  • A larger context window alone.
    The window sets what's visible; attention decides what's actually used.
  • Temperature.
    Temperature shapes sampling, not reference resolution.

A model has a 1M-token context window. Your team concludes 'we can drop retrieval and paste our 5 GB document store into every request'. What is the strongest objection?

  • A) Large context windows only work for code, not documents.
    Long context works for any text. The objection is size, cost and accuracy, not content type.
  • B) Attention cannot reach tokens more than 8,000 positions back.
    Within the window, attention can reach any position. The issue is that the corpus is far bigger than the window.
  • C) The model will refuse inputs longer than 100,000 tokens.
    Models accept input up to their stated window. There is no such hidden 100K refusal.
  • D) 5 GB of text is roughly a billion tokens, about 1,000 times the window, and even if it fit you would pay for and wait on every token on every call.
    Right. At about 4 characters per token, 5 GB is around 1.25 billion tokens. A big window helps with one long document, not with a whole corpus, and cost and latency scale with every token you send.
Practice

1. Your model has a 16,000-token window. Your system prompt is 800 tokens, you want to reserve 2,000 for the answer, and each retrieved document chunk is ~500 tokens. How many chunks can you safely include?
2. Explain why pasting a 200-page manual into one prompt can give worse answers than retrieving the 3 relevant paragraphs.
3. You notice your assistant follows instructions early in a long prompt but ignores ones buried in the middle. Give two fixes.

▸ Show solutions & reasoning

1. Budget left for documents = 16,000 − 800 (system) − 2,000 (answer) = 13,200 tokens. At ~500 tokens/chunk that’s 13,200 ÷ 500 ≈ 26 chunks. In practice leave a safety margin (token estimates aren’t exact), so plan for ~22–24. The habit — subtract the fixed costs first, then divide — is exactly how you size a RAG prompt.

2. Two reasons from this lesson. First, lost in the middle: the relevant passage is now buried among hundreds of pages, where models attend less reliably. Second, signal-to-noise: the model must find the needle while attending over a huge haystack, and irrelevant text can pull its attention. Retrieving the 3 relevant paragraphs puts the signal front and center — usually more accurate and far cheaper.

3. (a) Move the critical instructions to the start or end of the prompt, where models attend most reliably. (b) Shorten the prompt (retrieve less, summarize history) so there’s less to get lost in. A third option: repeat the key instruction at the end as a final reminder.

Deep dive: self-attention, and why long context is expensive

Here’s a bit more of the machinery, kept intuitive. In self-attention, each token produces three vectors: a query (“what am I looking for?”), a key (“what do I offer?”), and a value (“what I’ll contribute if attended to”). To update a token, the model compares its query against every other token’s key to get attention weights (how relevant each is), then mixes their values according to those weights. That’s how “it” ends up mostly absorbing the “animal” token’s information. Models do this many times in parallel (“multi-head” attention) and stack it in many layers, which is where their depth of understanding comes from.

The cost consequence is important for Track 8. Because every token compares against every other token, the work grows with the square of the sequence length — doubling the context roughly quadruples the attention computation. That’s the deep reason long context is slow and pricey, and why a whole research area exists to make attention cheaper. For now, the engineering takeaway is simple: tokens are a budget, and attention makes long budgets expensive — so spend them on what’s relevant.

You now understand what the model can see and how it reads it. The last piece of the engine is the part you’ll tune most often: once the model produces its probability distribution, how do we choose the next token? That’s sampling and decoding.

Exercises: warm-up, transfer, stretch

Warm-up. A chat app re-sends the whole conversation each turn. Each turn adds 400 tokens (user + assistant). How many input tokens does turn 30 send, and how many input tokens did the whole 30-turn chat cost in total?

▸ Solution

Turn 30 sends about 30 x 400 = 12,000 tokens of history (ignoring the system prompt). Total over the chat is 400 x (1 + 2 + ... + 30) = 400 x 465 = 186,000 input tokens. Cost grows with the square of the conversation length, which is why long chats get summarised or trimmed.

Transfer. Design a history policy for a support bot with a 32,000-token window: system prompt 1,500 tokens, retrieved docs up to 6,000, answer reserve 1,500. What do you do when history exceeds the remaining space?

▸ Solution

Remaining for history = 32,000 - 1,500 - 6,000 - 1,500 = 23,000 tokens. Keep the last N turns verbatim (say 8,000 tokens), and replace older turns with a running summary (say 1,000 tokens) that is updated when turns fall out. Pin facts that must never drop (account id, the customer's stated problem) in a small structured block. Log when trimming happens so you can check quality on long sessions.

Stretch. Explain, with the query/key/value picture from the deep dive, why a KV cache makes generating token 1,001 cheaper than recomputing everything, and what it costs in memory.

▸ Solution

Each past token's keys and values do not change once computed, so the server stores them. To generate the next token it only computes the new token's query, key and value, and attends from that one query to all cached keys. Without the cache it would recompute keys and values for all 1,000 earlier tokens every step. The cost is memory: the cache grows linearly with context length, layers and heads, and for long contexts it often limits how many users one GPU can serve at once.

Interview questions

Junior What is a context window and what counts against it?

▸ Model answer

It is the maximum number of tokens a model can take in one request. Everything counts: the system prompt, examples, conversation history, retrieved documents, tool results, and the answer the model writes. If the input uses most of the window, the answer gets cut short. Chat apps re-send history every turn, so long chats fill the window and old messages have to be trimmed or summarised.

Mid Context windows are now 1M tokens on frontier models. Does that make RAG obsolete?

▸ Model answer

No. A big window is great for one long document or a small codebase. But you pay for every token on every call, latency grows with prompt length, and models can miss facts buried mid-context. Most corpora are far larger than any window, and they change, so you would rebuild the prompt constantly. Prompt caching softens the cost for a fixed prefix. My default is retrieval for large or changing data, long context for bounded material, and I decide with an eval on real questions.

Senior Why is long-context inference expensive, and what levers do you have as an application engineer?

▸ Model answer

Prefill attention grows roughly with the square of sequence length, and the KV cache grows linearly, which limits concurrency per GPU. Output tokens then attend over that whole cache. Levers: send less (retrieval, reranking, summarised history), reuse prefixes with prompt caching, put stable content first so the cache hits, cap output length, route long-context jobs to batch APIs, and measure time-to-first-token separately from decode speed. On self-hosted models, tune max context per deployment so you are not reserving memory for windows you never use.
