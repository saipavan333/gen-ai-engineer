Going Deeper · Lesson 11.2

Advanced agents

Start here

An agent is a model that takes many steps: think, call a tool, read the result, repeat.

Small mistakes add up: if each step is right 95% of the time, a 10-step task works only about 60% of the time.

Reliable agents make a plan first, check their own work and check every tool result.

They also have hard limits on steps, time and money, and hand over to a person when stuck.

To test an agent, grade the whole journey, not just the final answer.

Everyday picture

An agent is a new intern sent on a 10-step errand across town. If each step goes right 95% of the time, the whole errand only works about 60% of the time, because one wrong turn early sends every later step the wrong way. Good managers give the intern a checklist (plan), a phone to call when stuck (escalation), a spending limit (budget), and they check the receipts afterwards (trajectory eval).

Going deeper

Track 4 built an agent that calls tools and loops. This lesson is about making one reliable — the patterns that turn an impressive demo into something you’d trust to run unattended, and how to evaluate whether it actually works.

Why agents are hard to trust

An agent multiplies the unreliability of a single model call. If one step is 95% reliable, a ten-step task is only about 60% reliable, because errors compound and — worse — an early mistake gets carried forward as if it were true. Agents also fail in ways chatbots don’t: looping without making progress, calling the wrong tool, trusting a tool’s output blindly, or quietly burning time and money. The demo that dazzled on a clean example falls over on the messy 30% of real inputs. Advanced agent work is mostly engineering for that 30%: anticipating failure and designing so it’s caught, bounded, and recoverable.

The reliability toolkit

Reflection / self-critique. Before finalizing, have the agent check its own work against the goal (“does this answer the question? is each step justified?”). A cheap second look catches a surprising share of errors — especially format mistakes and skipped requirements.

Plan, then execute. ReAct interleaves thinking and acting, which is flexible but can wander. For complex tasks, having the agent produce a plan first, then execute the steps, yields fewer wasted tool calls and far more readable traces — and lets you validate the plan before any action runs.

Validate tool results. Never trust a tool blindly. Check the result’s shape and sanity before feeding it back (did the search return anything? is the number in a plausible range? did the API error?). Models will confidently build on garbage if you let them.

Bound the loop and the budget. Hard caps are non-negotiable in production: a maximum number of steps, a wall-clock timeout, and a token/cost budget per task. When a cap is hit, fail gracefully (return partial progress or escalate to a human) rather than spinning.

Here’s the skeleton, with the guards made explicit:

bounded_agent.py
def run_agent(goal, max_steps=8, token_budget=20000):
    used = 0
    for step in range(max_steps):                 # bound the loop
        action = decide_next_action(goal, history)
        if action.kind == "final":
            if reflect_ok(goal, action.answer):     # self-critique gate
                return action.answer
            history.append("critique failed, revise")
            continue
        result = call_tool(action)
        if not valid(result):                     # validate tool output
            history.append(f"tool error: {result}, try another approach")
        used += result.tokens
        if used > token_budget:                   # bound the cost
            return escalate_to_human(goal, history)
        history.append(result)
    return escalate_to_human(goal, history)        # graceful fail, not a spin

Evaluate the journey, not just the destination

The biggest mistake in agent evaluation is grading only the final answer. An agent can reach the right answer by a lucky or unsafe path (and will fail next time), or produce a wrong answer despite sound reasoning (an easy fix you’ll miss). So you evaluate the trajectory — the full sequence of thoughts, tool calls, and results — on a golden set of tasks.

Track task success rate as the headline metric, but also per-step measures: did it pick the right tool, were arguments well-formed, did it recover from errors, how many steps and tokens did it take. Tracing every step (Track 6) is what makes this possible — without traces, an agent is an unobservable black box and you’re debugging by vibes.

At real scale: Budgeting a ticket-triage agent at 20,000 tasks a day

Assumptions: 20,000 support tasks a day, 10 steps per normal task, input grows from 2,000 tokens by 800 per step as history accumulates, 200 output tokens per step, model at $2 / $10 per million input / output tokens (claude-sonnet-5-5, Anthropic models overview, checked 2026-11-03), 2% of tasks get stuck in a loop.

  1. Reliability. At 95% per step, 0.9510 = 0.60. If tool-error recovery rescues 60% of failed steps, per-step success becomes 0.95 + 0.05 x 0.6 = 0.98, and 0.9810 = 0.82.
  2. Normal task cost. Input = 10 x 2,000 + 800 x (0 + 1 + ... + 9) = 20,000 + 36,000 = 56,000 tokens: $0.112. Output = 2,000 tokens: $0.02. Total $0.132 a task, $2,640 a day.
  3. A runaway with no cap. Say it spins for 50 steps. Input = 50 x 2,000 + 800 x (0 + ... + 49) = 100,000 + 980,000 = 1.08 M tokens: $2.16, plus 10,000 output tokens: $0.10. About $2.26 each. 2% of 20,000 = 400 runaways a day = $904 a day, a third on top of the useful spend.
  4. With a 12-step cap. Input = 12 x 2,000 + 800 x 66 = 76,800 tokens ($0.154) plus 2,400 output ($0.024) = about $0.18 each. 400 x $0.18 = $71 a day, and those tasks escalate to a human instead of failing silently.
  5. Repeated-call detection stops most loops even earlier, at the second identical call.

The cap is a cost control and a reliability control at once: it turns an invisible spin into a visible escalation.

Key points
  • Agents compound per-step error; advanced work is engineering for the messy 30% that breaks demos.
  • Reflection catches errors before finishing; plan-then-execute reduces wandering and aids validation.
  • Validate tool results — models build confidently on garbage. Bound steps, time, and cost, and fail gracefully.
  • Evaluate the trajectory (tool choice, arg quality, recovery), not just the final answer; headline metric = task success rate.
  • Tracing every step makes agents observable — you can’t debug or improve what you can’t see.
Practice

Your agent works on most tasks but on about 20% it runs for many steps, repeats the same tool call, and sometimes never finishes — occasionally producing a large bill. Diagnose the failure and list the changes you’d make.

▸ Show solution & reasoning

Diagnosis: the agent is looping without progress — repeating a tool call means it isn’t incorporating the result (or the result is unhelpful and it has no other plan), and with no hard cap the loop only ends by luck or budget exhaustion, hence the occasional huge bill. This is a classic missing-guards failure, and it concentrates on the 20% of inputs where the first approach doesn’t work.

Fixes: (1) add a step cap and a token/time budget with graceful escalation — this stops the bills immediately. (2) Detect repetition: if the same action/args repeat, force a different approach or stop. (3) Validate tool results and feed failures back explicitly (“that returned nothing — try X”), so the agent adapts instead of retrying identically. (4) Add a reflection step to notice “I’m not making progress.” (5) For complex tasks, switch to plan-then-execute so there’s a path to follow rather than improvisation. Then measure: run your trajectory eval and confirm step-count and success-rate on the hard 20% improve.

Why this is right: you treated reliability as engineering — bound the blast radius first (caps/budgets), then attack the root cause (no adaptation on failure), then re-measure on the segment that was breaking. Guards aren’t a band-aid here; in production they’re mandatory.

Why evaluate an agent’s full trajectory instead of just checking whether the final answer is correct?

  • A) A right answer can come from a lucky or unsafe path (unreliable next time), and trajectory eval localizes where things actually go wrong.
    Correct. Final-answer-only grading hides how the answer was reached — an agent that stumbled into the right result via a wrong path will fail on the next input, and one with sound reasoning but a small final slip looks like a total failure. Scoring the trajectory (tool choice, arg quality, recovery, steps) reveals reliability and tells you which step to fix.
  • B) Final answers are impossible to grade automatically.
    They’re gradable (golden answers, LLM-judge). The issue isn’t that you can’t grade the final answer — it’s that the final answer alone doesn’t tell you whether the behavior is reliable or how to improve it.
  • C) Trajectory evaluation removes the need for a golden set of tasks.
    It still needs a golden set — you evaluate trajectories over representative tasks. Trajectory eval adds depth to each case; it doesn’t replace the dataset.
  • D) Because the final answer doesn’t matter, only the steps do.
    Overcorrection — the final answer absolutely matters (task success rate is the headline metric). Trajectory eval complements it by explaining and predicting that success, not by dismissing it.

Which technique most improves an agent's reliability (not just its demos)?

  • Reflection/self-critique plus validating tool results and bounding the loop.
    Correct. Designing for failure modes is the senior signal that separates reliable from demo-able.
  • A friendlier persona.
    Tone doesn't add reliability.
  • Higher temperature for creativity.
    That reduces predictability.
  • Skipping the eval harness.
    You measure task success rate, not vibes.

An agent's steps each succeed 97% of the time and failures are independent. Roughly how often does a 15-step task succeed?

  • A) It cannot be estimated.
    Under the independence assumption it is a simple product. Real errors are often correlated, but this is the right first estimate.
  • B) About 63%, because 0.97 to the power 15 is about 0.63.
    Success needs every step to succeed, so you multiply: 0.97^15 = 0.633. Long chains erode reliability fast, which is why recovery and shorter plans matter.
  • C) About 55%, because you subtract 3% per step.
    15 x 3% = 45% off would give 55%, but probabilities multiply rather than subtract. Subtracting overstates the loss at this size and breaks entirely for long chains.
  • D) 97%, because each step is 97% reliable.
    That ignores compounding. Each extra step is another chance to fail.
Deep dive: when multi-agent helps — and when it just adds failure points

Multi-agent systems are fashionable, and sometimes genuinely useful: when a task has clearly separable roles (a researcher, a coder, a critic), distinct tool/permission scopes, or benefits from an explicit critique step, splitting responsibilities can raise quality and keep each agent’s context focused. The common shape is a supervisor that decomposes a goal and routes sub-tasks to specialists, or a sequential pipeline where each stage hands off to the next. Done well, this mirrors a small team and can outperform one agent juggling everything.

But every additional agent is another thing that can misunderstand, hallucinate, or stall, and the handoffs between them are new failure surfaces where context gets lost and errors propagate. Coordination has real cost in latency, tokens, and debuggability — a five-agent system is five times the places to look when something breaks.

The honest default is to reach for multi-agent only when a single well-equipped agent with good tools, reflection, and guards has demonstrably hit a ceiling. Many “multi-agent” problems are really one agent that needed better tools or a clearer prompt. As with everything in this track, let the eval decide: if adding an agent doesn’t move task success rate on your golden set, it’s just added complexity and cost.

You can build agents that are bounded, observable, and measured. The thread running through both RAG and agents is evaluation — so let’s deepen that next: advanced evals.

Exercises: warm-up, transfer, stretch

Warm-up. Your agent averages 7 steps. What per-step success rate do you need for 90% end-to-end success, assuming independence?

▸ Solution

Solve p^7 = 0.90, so p = 0.90^(1/7). ln 0.90 = -0.1054; divided by 7 = -0.01505; e^-0.01505 = 0.985. You need about 98.5% per step. That target is why validating tool results and recovering from errors matter so much: they lift per-step success, and the gain compounds.

Transfer. Design a trajectory eval for a refund agent with tools lookup_order, check_policy, issue_refund (needs human approval). What do you score per task?

▸ Solution

Per task, from the trace: (1) final outcome correct (refund issued or correctly declined); (2) tool selection: was check_policy called before issue_refund; (3) argument validity: order id and amount match the lookup result; (4) safety: issue_refund never executed without approval and never above the policy limit, scored as pass or fail with zero tolerance; (5) efficiency: steps and tokens against a budget; (6) recovery: when a tool errored, did it adapt or repeat. Headline is task success rate, but a single safety failure blocks release regardless of the average.

Stretch. A teammate proposes splitting the agent into a planner, a researcher and a writer agent. How do you decide, and what do you measure?

▸ Solution

First, write down the failure the split is meant to fix (context overload, mixed permissions, missing critique). Then try the cheaper fix inside one agent: better tools, a plan step, a reflection step. If you still split, compare single-agent and multi-agent on the same golden tasks: task success rate with a confidence interval, p95 latency, tokens per task, and failures at handoffs (information lost between agents). Multi-agent usually costs more tokens and adds handoff failures, so it has to win clearly on success rate or on safety, for example by isolating a high-permission tool in its own narrowly scoped agent.

Interview questions

Junior Why do production agents need a step cap and a budget?

▸ Model answer

Because agents can loop: they repeat a tool call, keep retrying a failing approach, or wander, and each step costs tokens and time. Without a cap, a stuck task ends only when something external stops it, which shows up as a big bill and a user waiting forever. A maximum step count, a wall-clock timeout and a token budget bound the damage. When a cap is hit, the agent should stop cleanly and return partial progress or escalate to a human, so the failure is visible.

Mid Compare ReAct with plan-then-execute. When would you use each?

▸ Model answer

ReAct interleaves reasoning and acting one step at a time, deciding the next action from the latest observation. It adapts well to surprises but can wander and is harder to predict. Plan-then-execute produces a full plan first, then runs the steps, optionally re-planning on failure. It gives readable traces, fewer wasted calls and a point where a human or a validator can approve the plan before anything runs. I use ReAct for short exploratory tasks and plan-then-execute for longer tasks or any with side effects.

Senior How do you evaluate and monitor an agent once it is live?

▸ Model answer

Offline, a golden set of tasks with expected outcomes and safety rules, scored on full trajectories: success, tool choice, argument correctness, recovery, steps and cost. That suite gates every prompt, tool or model change. Online, I trace every run with spans per step and track success proxies (escalation rate, user corrections, tool error rate), cost per task, step-count distribution and loop detections, with alerts on shifts. I sample traces for human review weekly and turn failures into new golden tasks. Safety-relevant actions get hard checks in code, not just eval coverage.
