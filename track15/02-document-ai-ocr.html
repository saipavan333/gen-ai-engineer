Document AI & OCR

Turning documents into structured data — invoices, forms, receipts, contracts — is the highest-value multimodal use case in business, and one VLMs changed overnight. This lesson covers OCR, the new VLM-based approach, and how to make extraction trustworthy.

School-kid picture

OCR is like a friend who reads out every word on a receipt in order, perfectly, but has no idea which number is the total. A VLM is like a friend who glances at the receipt and says 'the total is 42 dollars', but might misread a digit. You want both friends: one to understand, one to double-check the exact characters. Where it breaks: friends can disagree and both be wrong, so for money you still need a sum check or a human.

The problem: documents aren’t data

A scanned invoice is a picture, not a database row. To use it — to pay it, audit it, total it — someone has to turn “this image” into “vendor: Acme, total: $4,210, due: 2025-07-01.” That translation, done by hand, is a vast amount of human labor across finance, insurance, healthcare, and logistics. Document AI is the task of doing it automatically: from a document image, produce clean structured fields.

The classic first step is OCR (optical character recognition) — detecting and transcribing the text in an image. Open tools like Tesseract do this for free. OCR gives you the raw words and roughly where they are, but not their meaning: it returns a wall of text, not “this number is the total and that one is the tax.”

The old way vs the new way

The old way: OCR the document, then write rules and regular expressions to find fields (“the total is the number after the word ‘Total’”). This is brittle — every vendor’s invoice has a different layout, so the rules break constantly and each new format is a new engineering project. Teams spent years on this.

The new way: hand the document image straight to a VLM and ask for structured output. The model reads the text and understands the layout, so it can find the total whether it’s top-right, bottom, or in a table — no per-vendor rules. You combine two things you already know: multimodal input (Lesson 10.1) and structured JSON output (Track 2), ideally validated against a schema (Track 7).

extract_invoice.py
import ollama, json
from pydantic import BaseModel

class Invoice(BaseModel):        # the shape we require back
    vendor: str
    total: float
    due_date: str

prompt = """Read this invoice. Return ONLY JSON with keys:
vendor (string), total (number), due_date (YYYY-MM-DD). No prose."""

reply = ollama.chat(model="llava",
    messages=[{"role": "user", "content": prompt, "images": ["invoice.png"]}])

data = Invoice(**json.loads(reply["message"]["content"]))   # parse + validate
print(data.vendor, data.total, data.due_date)

The pydantic model does real work: if the VLM returns a total as "$4,210" instead of a number, or omits due_date, validation fails loudly instead of passing bad data downstream — the “assume it’ll misbehave” discipline from Start Here, applied to extraction.

Best of both: OCR + VLM

For accuracy-critical fields, combine them. OCR is often more reliable at exact character transcription (an account number, a precise amount), while the VLM is better at understanding which field is which and handling layout. A strong pattern is to use the VLM for structure and OCR to verify the exact digits — cross-checking the two, and flagging disagreements for human review. This is defense in depth again: two imperfect readers catch each other’s mistakes.

At real scale: Extracting fields from 1.2 million invoices a year for an accounts-payable team

Assumptions (ours): 1.2M invoices a year over 250 working days, 2 pages each, rendered at 1000 x 1400 px. Token rule from Anthropic vision docs: ceil(w/28) x ceil(h/28). Prices: claude-sonnet-5-5 $2 / $10 per million (models overview); Batch API 50% off (batch docs).

  1. Daily volume. 1,200,000 / 250 = 4,800 invoices a day.
  2. Tokens per invoice. Per page: ceil(1000/28) x ceil(1400/28) = 36 x 50 = 1,800 tokens. Two pages: 3,600. Add a 600-token instruction and schema: 4,200 input. Output JSON with line items: 300 tokens.
  3. Model cost. 4,200 x $2/M + 300 x $10/M = $0.0084 + $0.003 = $0.0114 an invoice. 4,800 x $0.0114 = $54.72 a day, $13,680 a year. Invoices are not interactive, so batch them overnight: $6,840 a year.
  4. Checks before payment. (a) Schema validation, (b) the sum of line items plus tax equals the total, (c) OCR digits agree with the VLM on total and bank account, (d) vendor exists in the vendor master. Anything failing goes to a person.
  5. The real cost is people. If 6% fail a check (assumption): 288 reviews a day x 1.5 minutes = 7.2 hours, about one full-time reviewer, which costs more than the model. Cutting the false-flag rate from 6% to 3% saves half a person; cutting tokens by 20% saves about $1,400 a year.
  6. Measure field-level accuracy. On a 500-invoice golden set, report accuracy per field and per vendor layout, after normalising (4210 = 4210.00; dates to ISO). A 99% total but 85% due-date score tells you where to work.
Key points
  • Document AI = image of a document → clean structured fields; it’s the highest-value multimodal use case.
  • OCR (e.g. free Tesseract) transcribes the text but not its meaning; rules on top are brittle across layouts.
  • VLMs read text and layout, extracting fields with no per-vendor rules — multimodal input + structured JSON output.
  • Validate the JSON against a schema (pydantic) so bad extractions fail loudly, not silently.
  • For critical fields, combine OCR + VLM and flag disagreements for a human — defense in depth.
Practice

You’re extracting the total and account_number from utility bills to auto-pay them. Why is “VLM returns JSON” not enough on its own here, and what would you add before letting a payment go through?

▸ Show solution & reasoning

Why it’s not enough: this is high-stakes — a wrong total or account_number sends real money to the wrong place, and a VLM can misread a digit or hallucinate a plausible value with full confidence and valid-looking JSON. Schema validation confirms the shape (a number, a string) but not the correctness of the value.

What I’d add: (1) cross-check exact fields with OCR and require agreement on account_number and total; (2) sanity rules (total within an expected range, account number matches the expected format/length); (3) a confidence/uncertainty signal, and (4) a human-in-the-loop confirmation step for any payment above a threshold or any case where the checks disagree. The principle: the amount of automation should scale with how reversible and low-cost a mistake is — and irreversible money movement demands verification and, above a threshold, a human. This is exactly the judgment (Track 7, Track 1) that separates a safe system from a demo.

Why do VLMs largely replace the old “OCR + hand-written regex rules” approach to extracting invoice fields?

  • A) VLMs understand layout and meaning, so they find the right field across many different document formats without per-format rules.
    Correct. The brittleness of the old approach came from rules tied to specific layouts (“total is after the word Total”), which broke on every new vendor. A VLM reads the document holistically and identifies fields regardless of position, eliminating most of that per-format engineering.
  • B) VLMs never make mistakes, so no validation is needed.
    VLMs absolutely make mistakes (misread digits, hallucinated values), which is why schema validation and, for critical fields, OCR cross-checks and human review remain essential. The advantage is flexibility across layouts, not infallibility.
  • C) VLMs don’t need to read the text at all.
    They very much read the text — that’s the point. The improvement over pure OCR is that they also understand which text is which field, using layout and context.
  • D) OCR can’t run for free, but VLMs can.
    OCR has excellent free options (Tesseract). Cost isn’t the reason; the reason is that VLMs handle varied layouts and meaning without brittle per-format rules.

A vision model reads an invoice total as 1600.99 instead of 160.99, confidently. What catches it?

  • An independent cross-check — summing the line items and comparing to the stated total.
    Correct. A second, independent calculation beats a better reader.
  • A larger vision model.
    It would also report the misread confidently.
  • Raising the temperature.
    Irrelevant to extraction accuracy.
  • A longer prompt.
    Doesn't provide an independent check.

An extractor returns valid JSON: total 1,240.00, and line items that sum to 1,420.00. Schema validation passes. What should happen?

  • A) Retry with a higher temperature until the numbers match.
    Rerolling until numbers agree can produce a consistent but wrong pair. Use an independent check (OCR, human).
  • B) Flag it for review: the arithmetic check failed, so at least one number was misread.
    Valid shape is not correct content. Cross-field checks like sums catch digit swaps that a schema cannot.
  • C) Pay 1,420.00, since line items are more reliable than totals.
    Either could be the misread. You cannot pick one without evidence.
  • D) Pay 1,240.00, since the total field is what the schema asked for.
    The two numbers disagree; paying either one without checking risks real money.
Deep dive: how you evaluate an extraction system

Document extraction is a place where the evaluation discipline from Track 6 becomes very concrete, and interviewers love it because it’s measurable. You build a golden set of documents with hand-verified correct fields, then measure field-level accuracy — for each field (vendor, total, date), what fraction of documents did the system get exactly right?

Aggregate accuracy hides problems, so you break it down by field (maybe total is 99% but due_date is 80% because of date-format confusion) and by document type or vendor (one layout may be far worse). That breakdown tells you exactly where to invest — a better prompt for dates, an OCR cross-check for totals, a human step for the one bad layout.

Two subtleties make you sound experienced. First, define “correct” carefully: is 4210.0 equal to 4210.00? is a date correct in any format or only YYYY-MM-DD? Normalizing before comparison matters, exactly like comparing SQL result sets rather than strings (Track 9). Second, distinguish the cost of different errors: a missing field the system flags as low-confidence is cheap (a human fills it in), while a wrong field returned with confidence is expensive (it flows into a payment).

So you don’t just maximize accuracy — you tune the system to prefer “I’m not sure, please check” over confident wrong answers on the fields that matter. Designing extraction around calibrated uncertainty and human handoff, not just raw accuracy, is what turns a flashy demo into something a finance team will actually trust with their invoices.

Exercises: warm-up, transfer, stretch

Warm-up. How many Claude visual tokens is an A4 page scanned at 150 DPI (1240 x 1754 px)? Is it under the high-resolution tier limits?

▸ Solution

ceil(1240/28) = 45 (44.3 rounds up), ceil(1754/28) = 63 (62.6 rounds up), so 45 x 63 = 2,835 tokens. The long edge 1754 is under 2,576 px and 2,835 is under 4,784 tokens, so it is not resized on Claude 4.7+ models. On older standard-tier models (max 1,568 tokens) it would be downscaled, which can make small print harder to read.

Transfer. Your golden set shows 99.2% accuracy on total, 97% on vendor, but 81% on due_date. List likely causes and fixes.

▸ Solution

Causes: date formats differ by country (03/04 is March 4 or April 3), invoices print several dates (issue, delivery, due), and some give terms ('Net 30') instead of a date. Fixes: ask for the raw date string and the format you think it is, then normalise in code using the vendor's country; ask for due_date only when explicitly labelled and otherwise compute it from issue_date plus payment terms; add per-vendor hints for the worst layouts. Re-measure per vendor. The general point: break accuracy down by field, then fix the field-specific cause.

Stretch. Design the confidence routing for invoice auto-pay so that fewer than 1 in 10,000 paid invoices has a wrong amount, while keeping human review under 5%. What do you need to measure to know you hit it?

▸ Solution

Route an invoice to auto-pay only if all independent checks agree: VLM total equals OCR total, line items sum to the total, the amount is within the vendor's historical range, and the bank account matches the vendor master. Everything else goes to review. To prove the 1-in-10,000 target you need a big audited sample: with zero errors observed, the rule of three says you need about 30,000 audited auto-paid invoices to claim the error rate is below 1 in 10,000 at 95% confidence. Measure review rate weekly, and the error rate on a random audit of auto-paid invoices. If review exceeds 5%, find which check fires most and improve that reader, not the threshold.

Interview questions

Junior What is the difference between OCR and document AI?

▸ Model answer

OCR turns pixels into text: it finds characters and words and where they are, but it does not know what they mean. Document AI goes further and turns a document into structured fields, like vendor, total and due date, by understanding layout and context. Classic document AI was OCR plus rules per layout. Today a VLM can read the page and return JSON directly. In production you often use both: the VLM for structure and OCR to double-check exact digits.

Mid How would you evaluate an invoice extraction system?

▸ Model answer

Build a golden set of real invoices with hand-verified fields, covering many vendors and layouts. Measure exact-match accuracy per field after normalising formats, and break it down by vendor and document quality. Separate errors by cost: a missing field flagged for review is cheap, a confident wrong amount is expensive, so I track the wrong-and-not-flagged rate separately. I also measure review rate and time per review, because that is the operating cost. Every production correction goes back into the golden set.

Senior Your company processes 50 document types from thousands of vendors. Would you fine-tune a document model or use a general VLM with prompts? How do you decide?

▸ Model answer

Start with a general VLM plus schemas, because it covers the long tail of layouts with no training and lets us ship and collect labelled data fast. Measure per document type. For the few types with very high volume, a stable layout and accuracy or cost problems, a fine-tuned smaller model or a specialised extractor may beat the general model on cost and latency. The decision is per type, using the eval: accuracy, cost per document, latency and review rate. Corrections from human review are the training data, so the system can move types to cheaper models as evidence accumulates.
