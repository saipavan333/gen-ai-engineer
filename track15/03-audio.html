Audio: speech-to-text & TTS

Voice is how people most naturally communicate, and it’s now cheap to work with. This lesson covers turning speech into text, text into speech, and how they combine with an LLM to build voice applications — meeting notes, assistants, call analytics.

School-kid picture

A voice assistant is like a relay race with three runners: the first listens and writes down what you said (speech-to-text), the second thinks of an answer (the LLM), and the third reads it out loud (text-to-speech). If any runner is slow, the whole team is slow, and if the first runner writes down the wrong word, the others carry the mistake to the finish line. Where it breaks: in a real relay each runner waits for the baton, but good voice systems let the runners overlap, starting to speak before the answer is fully written.

The two halves of audio AI

Speech-to-text (STT, or automatic speech recognition) turns spoken audio into a transcript. The open model Whisper made this remarkably good and completely free — it runs locally or on free Colab, handles many languages, and is robust to accents and background noise. Text-to-speech (TTS) does the reverse: turns text into natural-sounding spoken audio, so your system can talk back. Free/open TTS options exist too. Neither is an LLM — they’re specialized audio models — but they’re the ears and mouth you bolt onto an LLM to make it conversational by voice.

Transcription with Whisper is a couple of lines:

transcribe.py
import whisper                       # open, free, runs on CPU or free Colab GPU

model = whisper.load_model("base")   # small model, no API, no cost
result = model.transcribe("meeting.mp3")
print(result["text"])              # -> the full transcript

The voice-app pipeline

Most voice applications are a pipeline of parts you now recognize, chained end to end: audio in → STT (transcript) → LLM (understand & respond) → answer text → TTS (audio out). A voice assistant hears you (Whisper), thinks (an LLM, maybe with RAG or tools), and speaks the reply (TTS). Because the middle is just an LLM taking text, everything you already know applies — prompting, RAG for grounding, agents for actions, guardrails, evaluation. Audio models simply convert between sound and text at the two ends.

This unlocks a lot with little new code: meeting transcription and summarization (Whisper → LLM “summarize and list action items”), call-center analytics (transcribe calls → classify sentiment, extract topics), voice assistants, and accessibility tools. A meeting-notes tool — record, transcribe, summarize into decisions and action items — is a genuinely useful weekend project built entirely from free parts, and a great portfolio piece.

What makes voice hard

Two honest challenges. Accuracy degrades on heavy accents, cross-talk, jargon, and noisy audio, and STT usually doesn’t know who spoke (separating speakers is “diarization,” a harder add-on). Errors in the transcript then propagate into everything downstream — a misheard word can flip a summary. Latency is the big one for real-time voice: a back-and-forth conversation feels broken if there’s a long pause, and now you have three models in series (STT + LLM + TTS), each adding delay.

Real-time voice agents fight hard for every millisecond — streaming each stage, starting the LLM before the user finishes, and speaking the reply as it’s generated. For non-real-time uses (transcribe a recording, summarize later), latency doesn’t matter and the whole thing is easy.

At real scale: Call analytics for 20,000 calls a day, and a 1-second voice-agent budget

All volumes, speeds and latencies below are our assumptions or round illustrative numbers; measure your own hardware. Prices: claude-haiku-5-5 from $0.10 / $0.50 per million (models overview).

Part A, batch analytics.

  1. Audio volume. 20,000 calls x 6 minutes = 120,000 minutes = 2,000 hours of audio a day.
  2. Transcription compute. If a Whisper-family model on one GPU runs at 50x real time (illustrative; faster-whisper's benchmarks are a good place to start), that is 2,000 / 50 = 40 GPU-hours a day, about 2 GPUs running around the clock.
  3. LLM cost. 6 minutes x 150 words a minute = 900 words, about 1,200 tokens, plus a 300-token prompt: 1,500 in, 200 out. 1,500 x $0.10/M + 200 x $0.50/M = $0.00025 a call, so 20,000 calls = $5 a day.
  4. Lesson. Here the speech model, not the LLM, is the cost and capacity driver. Optimise STT first: model size, voice activity detection to skip silence, batching.

Part B, real-time agent. Target: reply audio starts within 1.0 s of the user stopping.

  1. Budget. End-of-speech detection 300 ms + final transcript 150 ms + LLM TTFT 350 ms + first clause of 8 tokens at 50 tokens/s = 160 ms + TTS first audio 150 ms = 1,110 ms. Over by 110 ms.
  2. Cuts. Prompt-cache the system prompt to lower TTFT; stream partial transcripts so the LLM starts on the near-final text; start TTS on the first clause, not the full sentence. Shortening end-of-speech detection is the riskiest cut, because it makes the agent interrupt slow speakers.
Key points
  • Speech-to-text (Whisper — free/open) makes transcripts; text-to-speech makes audio replies. Neither is an LLM.
  • Voice apps are a pipeline: audio → STT → LLM → TTS → audio; the LLM middle uses everything you already know.
  • Big, easy wins: meeting notes, call analytics, voice assistants, accessibility — buildable from free parts.
  • Transcription errors propagate downstream; accents, noise, and speaker separation are real accuracy challenges.
  • Real-time latency is hard (three models in series) — stream each stage; non-real-time uses are simple.
Practice

Sketch a free “meeting assistant” that produces a summary and action items from a recording. What are the stages, and which single failure would most degrade the final summary — and why?

▸ Show solution & reasoning

Stages: (1) record/upload the audio; (2) transcribe with Whisper; (3) send the transcript to an LLM with a prompt like “summarize this meeting and list decisions and action items with owners”; (4) return the summary (optionally speak it with TTS). Every part is free and local.

The failure that hurts most: a poor transcript. Everything downstream reads the transcript, not the audio, so if STT mangles names, numbers, or key terms (common with accents, jargon, or cross-talk), the LLM will faithfully summarize the wrong words — a confident summary of a garbled input.

That’s why the transcription stage is worth the most care: use a good Whisper model size, clean the audio if possible, and for high-stakes meetings let a human skim the transcript before trusting the summary. It’s the same “garbage in, confident garbage out” lesson as document extraction — the model can only reason about what it’s given, so the quality of the conversion step (audio→text, or image→text) caps the quality of everything after it.

In a voice assistant built as STT → LLM → TTS, why does the transcription (STT) stage deserve special care?

  • A) Every later stage reasons over the transcript, so STT errors propagate — a misheard word can corrupt the LLM’s response and the spoken reply.
    Correct. The LLM never hears the audio; it only sees the transcript. If STT mishears “can’t” as “can,” the model reasons over the wrong input and produces a confident, wrong answer that TTS then speaks. Errors at the first conversion step cascade through the whole pipeline.
  • B) Because STT is the only part that uses an LLM.
    STT isn’t an LLM — it’s a specialized speech model (like Whisper). The LLM is the middle stage. STT matters because of error propagation, not because it’s the model.
  • C) Because TTS can’t work unless STT is perfect.
    TTS just speaks whatever text it’s given — it works regardless of STT quality. The issue is that poor STT feeds bad text into the LLM (and ultimately TTS), not that TTS fails.
  • D) It doesn’t — the LLM fixes any transcription mistakes automatically.
    The LLM can’t reliably recover information that was mistranscribed — it has no access to the original audio. It may even lend false confidence to the error by summarizing it fluently. STT quality genuinely caps the pipeline.

In a speech-to-text pipeline, why does a transcription error matter downstream?

  • Errors propagate — a misheard word can flip a summary or trigger the wrong action.
    Correct. Everything after the transcript inherits its mistakes.
  • It only affects the audio file.
    The error flows into every downstream step.
  • Transcripts are never wrong.
    They degrade on accents, noise, and jargon.
  • It makes the model faster.
    Errors don't speed anything up.

A meeting-notes product transcribes 1-hour recordings and summarises them overnight. Users complain summaries get names and numbers wrong. Where should you spend effort first?

  • A) A faster TTS voice.
    There is no speech output in this product, and TTS does not affect what the summary says.
  • B) A bigger LLM for the summary.
    A stronger LLM cannot recover words that were mistranscribed; it will summarise the wrong ones fluently.
  • C) Transcription quality: a larger STT model, a vocabulary or prompt with names and jargon, and checking the transcript itself against a few reference recordings.
    The LLM only sees the transcript. Wrong names and numbers usually enter at STT; measure word error rate on a reference set first.
  • D) Streaming the summary to the user.
    Latency is not the problem in an overnight batch job; accuracy is.
Deep dive: pipelines vs end-to-end, and the latency budget

The STT → LLM → TTS pipeline is the pragmatic, buildable way to do voice today, and it has a real virtue: each stage is separately swappable, testable, and gradable. You can evaluate transcription accuracy on its own, improve the LLM prompt without touching audio, and pick a TTS voice independently — the modularity that makes systems maintainable. Its cost is latency: three models in series, each adding delay, which is fine for batch jobs (transcribe a recording, summarize overnight) and challenging for live conversation.

The frontier is moving toward more end-to-end speech models that take audio in and produce audio out directly, cutting the hops and enabling near-instant, natural back-and-forth — worth knowing exists, and a good thing to mention as “where this is heading.”

For real-time voice specifically, think in a latency budget, which ties straight back to Track 8. Natural conversation wants a response within a few hundred milliseconds, and you’re spending that budget across capturing speech, transcribing, thinking, and speaking. The techniques are all streaming: transcribe incrementally as the person talks, detect when they’ve stopped, start the LLM immediately, stream its tokens into TTS so speech begins before the full answer exists, and keep prompts tight so time-to-first-token is low.

Designing a voice agent is largely a latency-engineering problem wrapped around an LLM — which, again, is systems work you’re well suited to. The lesson of this whole track holds: multimodal doesn’t replace your skills, it points them at richer inputs, and the winners are the people who can make the plumbing fast, accurate, and reliable.

Exercises: warm-up, transfer, stretch

Warm-up. A call centre records 3,000 hours of audio a day. If your STT setup processes audio at 30x real time per GPU, how many GPUs run around the clock?

▸ Solution

3,000 / 30 = 100 GPU-hours a day. 100 / 24 = 4.2, so 5 GPUs, with a sixth for headroom and failover. If you can run overnight only (say 10 hours), you need 100 / 10 = 10 GPUs, so the schedule is a capacity lever too.

Transfer. Design the evaluation for the transcription stage of a call-analytics system in Indian English and Hindi code-mixed speech.

▸ Solution

Build a reference set of a few hours of real calls, with human transcripts, covering accents, code-mixing, background noise and phone-line quality. Measure word error rate overall and per slice, plus a targeted metric for what the business needs: accuracy on names, numbers, product terms and Hindi words written in Latin script. Compare two or three model sizes and settings (language hint off vs on, a vocabulary prompt). Then measure the downstream effect: run the LLM classifier on human versus machine transcripts and compare labels. If downstream labels barely change, a cheaper STT model may be fine.

Stretch. Your voice agent's p50 response start is 0.9 s but p95 is 2.8 s. Name three likely contributors and how you would find out which dominates.

▸ Solution

Likely contributors: LLM TTFT tails (provider queueing, long prompts in long calls as history grows), end-of-speech detection waiting on hesitant speakers, and tool calls inserted before the reply (a CRM lookup). To find out, trace every turn with spans per stage (VAD end, STT final, LLM first token, TTS first audio, any tool span) and compare the span breakdown of p95 turns against p50 turns. Whichever stage grows most in the tail is the target: trim history for long calls, speak a filler phrase while a tool runs, or tune VAD per channel.

Interview questions

Junior How would you build a free meeting-summary tool from a recording?

▸ Model answer

Record or upload the audio, transcribe it with an open speech-to-text model such as Whisper running locally, then send the transcript to an LLM with a prompt asking for a summary, decisions and action items with owners. If the meeting is long, I would split the transcript into chunks, summarise each, then summarise the summaries. I would show the transcript alongside the summary so users can check names and numbers, because transcription errors flow straight into the summary.

Mid What is speaker diarization and when do you need it?

▸ Model answer

Diarization answers 'who spoke when': it splits the audio into segments and assigns each to a speaker label. Plain speech-to-text gives you words but not who said them. You need diarization when the speaker matters: action items with owners in meetings, separating agent from customer in call analytics, or compliance checks on what the agent said. It is a separate model step with its own errors, especially on overlapping speech, so I evaluate it separately, for example by checking speaker labels on a reference set.

Senior Would you build a voice agent as STT, then LLM, then TTS, or use an end-to-end speech model? What drives the choice?

▸ Model answer

The pipeline is modular: I can pick the best STT for my languages, any LLM with tools and RAG, and a TTS voice, and I can evaluate and log each stage, including the transcript, which helps compliance and debugging. Its cost is latency and lost prosody, since three hops add delay and the LLM never hears tone. End-to-end speech models cut latency and sound more natural, but are harder to ground, test, guard and audit, and there are fewer choices. For regulated or tool-heavy agents I would start with the pipeline and stream every stage; for casual conversation where latency and naturalness dominate, I would evaluate an end-to-end model.
