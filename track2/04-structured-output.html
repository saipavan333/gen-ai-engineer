Structured output & JSON

The moment you put an LLM inside software, you need its output in a shape code can read. This lesson is how you turn a chatty model into a reliable component — the bridge between “cool demo” and “shipped feature.”

Why structured output is non-negotiable for products

A human can read “the customer seems upset and wants a refund.” Your code can’t — not reliably. To route a ticket, update a database, or call another function, you need fields: intent="refund", sentiment="negative", urgent=true. Free-form prose forces fragile string-parsing that breaks the first time the model rephrases. Structured output — usually JSON — is what lets an LLM slot into a real system. It’s also the foundation of tool/function calling in Track 4, which is just structured output the model fills in.

Concept

Structured output means the model returns data in a fixed, machine-readable format — almost always JSON (JavaScript Object Notation: keys and values like {"urgent": true}). A schema is the contract describing the expected shape: which fields exist, their types, and allowed values. Validation is checking the model’s output actually matches that schema before you trust it.

School-kid picture

Structured output is like a form with labelled boxes instead of a blank page. 'Name: ___ Age: ___ Allergic to nuts: yes / no' gets answers a computer can file; 'tell me about yourself' gets a story someone has to read. Constrained decoding is like boxes that physically only accept digits where a number goes. The analogy breaks because a form cannot stop someone writing a wrong but valid answer, and neither can a schema: it guarantees the shape, not the truth.

Getting JSON reliably: four levers

Asking nicely isn’t enough on its own — models love to add “Sure! Here’s the JSON:” or a trailing explanation that breaks parsing. Use these together:

  1. Specify the exact shape in the prompt, ideally with a concrete example of the JSON (this is few-shot from 2.2 applied to format).
  2. Use a JSON/structured-output mode if your runtime has one. It constrains the model so the output is always valid JSON. Ollama supports this for free with format="json" (and can even take a JSON schema).
  3. Validate the parsed output against your schema — check fields, types, and allowed values, not just that it parses.
  4. Retry or repair on failure: send the error back and ask the model to fix it. This loop is what makes it production-grade.

Worked example — JSON mode + validation + retry (free, Ollama)

The whole pattern, end to end, with a free local model. pydantic defines the schema and validates types in one line:

!pip install ollama pydantic
import json, ollama
from pydantic import BaseModel, ValidationError

class Ticket(BaseModel):          # the schema, as a Python class
    intent: str
    sentiment: str
    urgent: bool

def extract(text, tries=2):
    prompt = f"""Extract fields from the ticket as JSON with keys
intent (refund/billing/technical/other), sentiment (positive/negative/mixed/neutral), urgent (true/false).
Ticket: "{text}" """
    for attempt in range(tries):
        resp = ollama.chat(model="llama3.2",
                           messages=[{"role": "user", "content": prompt}],
                           format="json")        # force valid JSON (free!)
        try:
            return Ticket(**json.loads(resp["message"]["content"]))   # parse + validate
        except (json.JSONDecodeError, ValidationError) as e:
            prompt += f"\nYour last output was invalid: {e}. Return ONLY valid JSON."   # retry w/ error
    raise RuntimeError("Model could not produce valid JSON")

t = extract("My card was charged twice and no one has replied in 3 days!")
print(t.intent, t.sentiment, t.urgent)   # -> refund negative True

Notice what makes this robust: format="json" stops the model adding prose, pydantic guarantees the types are right before you use them, and the retry loop feeds the error back so a one-off slip self-corrects. That’s the difference between a script and a feature.

At real scale: Extracting fields from 3 million invoices a month

Assume an accounts team processes 3,000,000 invoices a month and extracts vendor, invoice number, date, total and currency. Failure rates are assumptions to replace with your own measurements.

  1. Free-text prompting. Suppose 4% of replies fail to parse (prose around the JSON, trailing commas). 3M x 4% = 120,000 broken records a month.
  2. Constrain the shape. Pass a JSON schema as the format. Ollama accepts a schema in format (Ollama docs), and hosted APIs have their own structured output features (Anthropic docs). Parse failures drop to about zero.
  3. Now count value errors. Valid JSON can still be wrong: a date as "next Friday", a total that does not match the line items, currency "dollars" instead of an ISO code. Suppose 1.5% fail validation: 3M x 1.5% = 45,000 a month.
  4. Retry with the error. Send the validation message back once. Suppose 85% fix themselves: 45,000 x 0.85 = 38,250 recovered, at the cost of 45,000 extra calls (1.5% more volume).
  5. Human queue. The remaining 6,750 a month, about 225 a day, go to a reviewer. At 1 minute each that is under 4 hours a day: affordable, and every case becomes a test example.
  6. Design the schema to allow honesty. Make fields nullable where invoices really omit them, use enums for currency, and add a cross-check in code (sum of lines = total). A schema that forces every field pushes the model to invent values.
Key points
  • Software needs machine-readable output; JSON is the default, and it underpins tool calling (Track 4).
  • Get reliable JSON with four levers: specify the shape, use a JSON mode, validate, and retry on failure.
  • Validate values, not just syntax — check required fields, types, and allowed enums.
  • The production pattern is a generate → validate → retry-with-error loop; never trust raw output as data.
  • Tools like pydantic turn a schema into one-line validation; runtimes like Ollama’s format="json" make valid JSON free.

Your extraction endpoint works 95% of the time, but occasionally the model returns {"urgent": "yes"} instead of a boolean and a downstream service crashes. Best fix?

  • A) Validate the parsed output against a typed schema and, on failure, retry asking the model to correct it.
    Correct. Validation catches the wrong type before it reaches the downstream service, and the retry loop repairs the occasional slip. This is exactly the generate → validate → retry pattern that makes structured output production-grade.
  • B) Add a note to the prompt: “urgent must be a boolean” and hope it sticks.
    Helpful, but “hope” isn’t a safeguard — that 5% will still slip through eventually. Prompt wording reduces failures; only validation actually prevents a bad value from reaching production.
  • C) Wrap the downstream call in a try/except and ignore failures.
    That hides the symptom and silently drops data. You want to detect the bad output and fix it (retry), not swallow errors and lose tickets.
  • D) Raise the temperature so the model is less repetitive.
    Higher temperature adds variability — the opposite of what you want for consistent structured output. For extraction you want temperature 0 plus validation.

The model returns JSON with a chatty preamble. What's the robust production fix?

  • Extract the JSON substring, parse it, validate the schema, and retry once on failure.
    Correct. You engineer around imperfect output: extract, parse, validate, retry — not just reword the prompt.
  • Trust the string and call json.loads directly.
    A preamble makes a strict parse throw; you must extract first.
  • Raise the temperature.
    That makes format less consistent.
  • Ask again more politely.
    Politeness doesn't guarantee structure; validation does.

With schema-constrained decoding switched on, the model returns {"currency": "USD", "total": 1250.0} for an invoice whose real total is 1,520. What does this show?

  • A) The schema should use a string for total instead of a number.
    Changing the type does not make the value correct; it just removes a useful type check.
  • B) The temperature was too low.
    A higher temperature would add randomness, not accuracy.
  • C) Constrained decoding is broken and should be turned off.
    It did its job: valid JSON with the right types. Catching wrong values was never its job.
  • D) Constrained decoding guarantees valid shape and types, not correct values, so you still need value checks such as matching the total to the line items.
    Right. The output passes the schema but is wrong. Cross-checks in code and grounding are what catch value errors.
Practice

1. Design a JSON schema for extracting a calendar event from a message: title, date, start time, attendees (list), and whether it’s all-day. Which fields might legitimately be missing, and how do you represent that?
2. The model returns valid JSON, but "date": "next Tuesday" instead of an ISO date. Is this a parsing failure or a validation failure? How do you handle it?
3. Why is “the output parsed as JSON” not enough to trust it?

▸ Show solutions & reasoning

1. Something like: {title: str, date: str (ISO), start: str|null, attendees: list[str], all_day: bool}. Optional fields (a missing time, no attendees) should be represented explicitly — null or an empty list — and your schema should allow that (e.g., start: Optional[str]). Forcing every field to be present pushes the model to invent values; allowing nulls lets it honestly say “absent,” which you then handle in code.

2. Neither pure parsing nor a type error — it’s a semantic validation failure: the value is a string (correct type) but not the format you need. Handle it by validating the value (e.g., that date matches an ISO pattern), and either instruct the model to output ISO dates with an example, or post-process “next Tuesday” into a real date. Type-checking alone won’t catch this; value-checking will.

3. Because valid JSON only guarantees syntax, not meaning. {"urgent": "yes"} parses fine but is the wrong type; {"intent": "banana"} parses fine but isn’t an allowed value; a required field can be missing entirely. Trusting “it parsed” lets bad data into your system. You must validate fields, types, and allowed values — the shape and the contents.

Deep dive: how JSON mode actually guarantees valid JSON

“JSON mode” and schema-constrained output aren’t just a stern instruction — they change the decoding step from Track 1. Remember the model outputs a probability over every possible next token, and a sampler picks one. Constrained decoding adds a filter: at each step, it masks out any token that would make the output violate the grammar (or schema), so only tokens that keep the JSON valid can be chosen.

If the model is mid-string, a closing brace is forbidden; if a field expects a boolean, only true/false tokens are allowed. The result is output that is guaranteed to parse, by construction. Providers expose this as “JSON mode,” “structured outputs,” or “function calling”; libraries like Outlines and llama.cpp grammars do it locally.

Two caveats keep you honest. First, constrained decoding guarantees shape, not truth — the model can still fill valid fields with wrong values, so semantic validation and grounding still matter. Second, even with a JSON mode, keep the validate-and-retry loop: it’s your safety net for the value-level errors a grammar can’t catch (wrong enum, impossible date, hallucinated id). Shape from the decoder, correctness from your validation — use both.

You can now make outputs that software trusts. The last prompting lesson zooms out to the reusable patterns and anti-patterns — the playbook pros reach for, and the traps that quietly wreck prompts.

Exercises: warm-up, transfer, stretch

Warm-up. Write a Pydantic model for a support ticket with: intent (one of refund, billing, technical, other), urgent (bool), order_id (string or missing).

▸ Solution 

from typing import Literal, Optional
from pydantic import BaseModel

class Ticket(BaseModel):
    intent: Literal["refund", "billing", "technical", "other"]
    urgent: bool
    order_id: Optional[str] = None
Literal turns the allowed intents into an enum the validator enforces, and Optional with a default of None lets the model honestly report a missing order id instead of inventing one.

Transfer. Your retry loop sometimes runs 5 times on the same email and still fails, burning tokens. Improve the loop.

▸ Solution

Cap retries at 1 or 2. Make each retry message specific: quote the exact validation error and the field. If it still fails, stop and route the case to a fallback: a human queue, a stronger model, or a partial record with failed fields set to null and flagged. Log the input and errors so the case joins your test set. Also check the schema itself, because repeated failure on one field often means the schema demands something the input does not contain.

Stretch. Explain how a grammar-constrained decoder decides which tokens are allowed at each step, and why it can make some outputs slightly worse in quality.

▸ Solution

The decoder tracks where it is in the grammar (a state machine built from the JSON schema). At each step it masks every token that would lead to an invalid continuation, then samples from what is left, renormalised (Willard and Louf, 2023, describe an efficient indexed version). Quality can dip because the mask may force awkward tokenisations or cut off the path the model would have taken to a good answer, especially if the schema forces fields in an unnatural order. Mitigations: order fields so reasoning-like fields come before conclusions, keep schemas simple, and evaluate quality, not just validity.

Interview questions

Junior How do you get reliable JSON out of an LLM?

▸ Model answer

Describe the exact shape in the prompt with an example, use the runtime's structured output or JSON mode (for example passing a JSON schema as Ollama's format), parse and validate against a schema with something like Pydantic, and on failure retry once with the error message. Never pass raw model output to downstream code without validation.

Mid What is the difference between JSON mode, schema-constrained output, and function or tool calling?

▸ Model answer

JSON mode guarantees syntactically valid JSON but not your fields. Schema-constrained output restricts decoding to a specific JSON schema, so required fields, types and enums are enforced. Tool calling has the model fill in arguments for a named function defined by a schema; the same constraint idea, but framed as an action your code executes. In all three you still validate values, because a schema cannot know that a total is wrong or an id does not exist.

Senior Design the extraction pipeline for millions of documents a month, with an accuracy target of 99.5% per field.

▸ Model answer

Schema-constrained extraction with nullable fields and enums, code-level cross-checks (totals, dates, id formats, lookups against master data), one retry with the specific error, then routing to a stronger model or a human queue. Measure per-field accuracy on a labelled sample every week, not just parse rate. Version schemas and prompts together, and make downstream consumers handle nulls. Log every correction as a new test case. Use batch APIs for cost and keep a confidence or review flag in the record, so 99.5% is measured rather than assumed.
