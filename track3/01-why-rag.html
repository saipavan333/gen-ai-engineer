Why RAG exists

This is the technique that turns a general-purpose model into your expert — answering from your documents, your policies, today’s data — with citations you can check. It’s the single most common architecture in production GenAI, and it’s built entirely from things you already understand.

The problem RAG solves

From Track 1 you know three hard limits of a bare LLM: it has a knowledge cutoff, it can’t see your private data, and when it doesn’t know something it hallucinates a confident guess. So how do you build a support bot that answers from your help docs, or an assistant that knows this week’s numbers? You can’t retrain the model for every change, and you can’t fit a 500-page manual into one prompt. The answer is to stop relying on the model’s memory and instead fetch the relevant facts and hand them to the model at question time.

Concept

Retrieval-Augmented Generation (RAG) is a pattern where, for each query, you retrieve the most relevant pieces of text from a knowledge source and put them in the prompt, so the model generates its answer grounded in those pieces. The collection of source text is your knowledge base. Grounding means the answer is based on supplied evidence rather than the model’s memory. Retrieval is the act of finding the relevant pieces — which, as you’ll see, is just the embedding similarity from Track 1.3 at scale.

School-kid picture

A bare LLM is a student taking a closed-book exam: it answers from memory, and when memory fails it bluffs. RAG turns it into an open-book exam where a librarian hands the student the three right pages before each question, and the student must point to the line they used. The analogy breaks because a real librarian understands the question; the retriever only matches meaning numerically, so it can hand over the wrong pages with full confidence.

How it works, at a glance

The whole pattern is one loop: turn the question into a vector, find the nearest chunks in a vector store, paste them into the prompt, and let the model answer from them.

Worked example — “hello world” RAG in 20 lines (free, local)

This is a complete, runnable RAG system using a free embedding model and a free local LLM. We’ll reuse and grow it across the track.

!pip install sentence-transformers numpy ollama
import numpy as np, ollama
from sentence_transformers import SentenceTransformer
embed = SentenceTransformer("all-MiniLM-L6-v2")        # free, 384-dim

# 1) knowledge base — your chunks of text
docs = [
    "The X200 blender has a 3-year limited warranty.",
    "Returns are free within 30 days of delivery.",
    "The X200 motor is rated at 1200 watts.",
]
D = embed.encode(docs, normalize_embeddings=True)        # pre-embed once

def retrieve(q, k=2):
    qv = embed.encode([q], normalize_embeddings=True)[0]
    scores = D @ qv                                  # cosine (vectors are unit-length)
    top = scores.argsort()[::-1][:k]                  # highest first
    return [docs[i] for i in top]

def rag(q):
    chunks = retrieve(q)
    context = "\n".join(f"[{i+1}] {c}" for i, c in enumerate(chunks))
    prompt = ("Answer ONLY from the context. Cite as [n]. "
              "If the answer isn't there, say you don't know.\n\n"
              f"Context:\n{context}\n\nQuestion: {q}")
    return ollama.chat(model="qwen2.5:7b",
                       messages=[{"role": "user", "content": prompt}])["message"]["content"]

print(rag("How long is the warranty?"))   # -> "The warranty is 3 years [1]."

That’s genuinely it — retrieval is one matrix multiply (cosine), generation is one grounded prompt. Everything else in this track makes these two steps robust at real scale.

At real scale: Long context vs RAG for a bank's 40,000-document policy bot

Assumptions: 40,000 policy and product documents, about 2,500 tokens each, 50,000 questions a day, model priced at $2 per million input tokens and $10 per million output (claude-sonnet-5-5 list price, Anthropic models overview, checked 2026-11-03).

  1. Size the knowledge. 40,000 x 2,500 = 100 M tokens. The model's window is 1 M tokens, so "paste it all in" is not even possible: the corpus is 100 times the window.
  2. Pretend it fit anyway. A 1 M-token prompt costs 1 x $2 = $2 per question. At 50,000 questions that is $100,000 a day, before output.
  3. Now RAG. Retrieve 8 chunks of 400 tokens = 3,200 tokens, plus about 300 tokens of instructions and question = 3,500 input tokens. 3,500 / 1,000,000 x $2 = $0.007 per question, or $350 a day.
  4. Output is the same either way. 300 output tokens x $10 / 1 M = $0.003 per answer, $150 a day.
  5. Freshness. Say 500 documents change each week. You re-chunk and re-embed only those: 500 x 2,500 = 1.25 M tokens through a free local embedder. With fine-tuning you would retrain; with RAG you re-index a sliver.

Result: RAG is about $500 a day all-in against an impossible (or $100,000) long-context design, and every answer can cite the policy it came from. The catch, which the rest of this track handles, is that the bot is now only as good as the 8 chunks it fetched.

When to use RAG (and when not to)

RAG is the right tool when you need a model to use knowledge that is large, changing, private, or must be cited. But it’s one of three ways to give a model knowledge, and a senior engineer picks deliberately:

ApproachBest forWatch out
Long context (paste it all in)A handful of small docs that fit comfortably in the windowCost, latency, “lost in the middle” at scale (Track 1.4)
RAG (retrieve, then generate)Large/changing/private knowledge; you want citationsQuality is capped by retrieval quality (Lesson 3.8)
Fine-tuning (train the weights)Durable behavior, format, or style — not fast-changing factsCostly to update; wrong tool for fresh knowledge (Track 5)
The mantra

RAG is for knowledge; fine-tuning is for behavior. If the question is “how do I make it know X?”, reach for RAG. If it’s “how do I make it act like X?”, consider fine-tuning. Most “make it answer about our docs” problems are RAG.

Key points
  • RAG fixes the LLM’s cutoff/private-data/hallucination limits by supplying relevant facts at query time.
  • The loop: embed the query → retrieve nearest chunks → put them in the prompt → generate grounded.
  • It changes the input, not the weights — so updating knowledge is just re-indexing.
  • Choose among long-context, RAG, and fine-tuning: RAG for large/changing/private/cited knowledge.
  • RAG’s ceiling is retrieval quality — if the right chunk isn’t fetched, the answer can’t be right.

Your company’s product catalog changes weekly. You need a bot that answers questions about current products, with sources. Best approach?

  • A) RAG over the catalog: re-index when it changes and have the model answer from retrieved entries with citations.
    Correct. Weekly-changing factual knowledge that needs citations is the textbook RAG case. Updating is just re-indexing the catalog; the model always answers from the latest retrieved entries and can cite them.
  • B) Fine-tune the model on the catalog every week.
    Fine-tuning bakes knowledge into weights and would need re-running on every change — slow, costly, and it can’t easily cite sources. Fine-tuning is for behavior, not fast-changing facts.
  • C) Paste the entire catalog into every prompt.
    For a large catalog this blows the context window and budget, and invites “lost in the middle.” Long context only suits a few small documents; here you want to retrieve just the relevant entries.
  • D) Rely on the base model’s built-in knowledge.
    The base model has a training cutoff and never saw your private catalog — it would hallucinate. This is exactly the limitation RAG exists to remove.

What core problem does RAG solve that a bigger model alone doesn't?

  • Giving the model current, private, or changing facts it was never trained on — grounded in real sources.
    Correct. RAG supplies knowledge the weights lack, with provenance you can cite.
  • Making the model reason better.
    RAG adds knowledge, not reasoning ability.
  • Reducing the token cost of every call.
    RAG usually adds context tokens; it's about grounding, not cost.
  • Removing the need for prompts.
    You still prompt; RAG just adds retrieved context.

A teammate says: "Our new model has a 1 M-token window, so we can drop RAG and paste the whole 100 M-token knowledge base." What is the best reply?

  • A) It works if you raise the temperature so the model explores more of the context.
    Temperature only changes how tokens are sampled. It does not change what the model can read or how much fits.
  • B) Fine-tune the model on the knowledge base instead.
    Fine-tuning is for behaviour and format. It is slow to update, cannot cite, and is the wrong tool for a large, changing set of facts.
  • C) Fine, as long as you use prompt caching.
    Caching makes repeated prefixes cheaper but cannot make 100 M tokens fit in a 1 M window, and it does nothing for changing content or citations.
  • D) The corpus is 100 times the window, and even content that fits costs far more per question and suffers lost-in-the-middle; retrieve the relevant few chunks instead.
    Window size is a hard ceiling (100 M tokens will not fit in 1 M), and below the ceiling you still pay for every pasted token on every call. RAG sends a few thousand tokens and keeps citations.
Practice

1. Run the “hello world” RAG above, then ask it “What’s the motor wattage?” and “Do you ship to Mars?” What should each return, and why?
2. For each, pick long-context / RAG / fine-tune: (a) answer from a 2-paragraph email, (b) answer from 10,000 support articles, (c) always reply in your brand’s quirky voice.
3. Explain why RAG can cite sources but a bare LLM fundamentally cannot.

▸ Show solutions & reasoning

1. “Motor wattage” retrieves chunk [3] and answers “1200 watts [3].” “Ship to Mars?” retrieves the nearest chunks, but none contain shipping-to-Mars info, so a well-grounded model says “I don’t know” (because you told it to abstain when the answer isn’t in context). That contrast — confident when grounded, honest when not — is the whole value of RAG.

2. (a) long context — it’s tiny, just paste it. (b) RAG — far too much to paste; retrieve the relevant few. (c) fine-tune — that’s a durable behavior/style, not knowledge, so train it in (or a strong system prompt for a lighter touch).

3. Citations require knowing where a fact came from. A bare LLM generates facts from diffuse patterns in its weights — there’s no source to point to, so any “citation” it offers is itself generated (and often fake). RAG retrieves specific, identifiable chunks, so the system knows exactly which document each fact came from and can attach a real reference. Provenance comes from retrieval, not generation.

Deep dive: RAG is a systems problem, not a model problem

The seductive thing about RAG is how simple the core is — embed, search, stuff, generate. The reason it’s a discipline is that quality lives in the unglamorous parts around the model. Your answer can only be as good as the chunk you retrieved, which depends on how you split documents (Lesson 3.2), which embedding model you chose (3.3), how your index trades speed for accuracy (3.4), whether you rerank (3.5) or blend keyword and semantic search (3.6), and how strictly you ground and cite (3.7). And you won’t know any of it is working without measuring retrieval and answer quality (3.8). That’s the whole track.

A useful way to hold it: RAG moves the hard problem from “does the model know?” to “can I find the right text?” — and finding the right text is a search-and-data problem you can engineer, test, and improve incrementally. That’s a much better place to stand than hoping a model memorized your docs. The model becomes a reliable reasoner over evidence you control, which is exactly the relationship you want with a system that’s brilliant but an unreliable witness.

Exercises: warm-up, transfer, stretch

Warm-up. Write the four steps of the RAG loop for one query, naming what goes in and out of each step.

▸ Solution

  1. Embed the query: text in, one vector out (same model as the documents).
  2. Retrieve: query vector in, top-k chunk ids plus scores out.
  3. Build the prompt: numbered chunks, instructions (answer only from context, cite, abstain), and the question.
  4. Generate: prompt in, answer with citations out.
Why it matters: when an answer is wrong, these boundaries tell you where to look. Wrong chunks in step 2 is a retrieval bug; right chunks but wrong answer in step 4 is a grounding bug.

Transfer. An HR team has 30 policy PDFs (about 90,000 tokens in total) that change twice a year, and wants answers with page references. A colleague proposes a full vector-database RAG stack. Is that the right call?

▸ Solution

Probably not at first. 90,000 tokens fits comfortably in a 1 M-token window, so the simplest version is long context: paste all 30 PDFs with page markers and ask for page citations. Do the cost check: 90,000 tokens x $2 per million = $0.18 per question on a $2/M model, so at 2,000 questions a month that is $360 a month, and prompt caching can cut repeated-prefix cost further. Move to RAG when (a) the corpus grows past what is cheap to paste, (b) questions get frequent enough that $0.18 each hurts, or (c) quality suffers from lost-in-the-middle. The senior point: RAG is a tool for large or fast-changing knowledge, not a default.

Stretch. Your RAG bot answers "What is the overdraft fee?" with "$35 [2]", but chunk [2] says the fee is $25. List every place in the pipeline this could have gone wrong and the one check that tells you which.

▸ Solution

Candidates: (1) Generation blended chunk [2] with the model's prior (a common US fee figure), (2) stale index: the document changed to $25 but another chunk still says $35 and the model cited the wrong number, (3) chunking split a table so the $35 belongs to a different product row, (4) citation slip: the claim came from chunk [3] but was tagged [2]. The deciding check is to print the full prompt that was sent (all chunks) and search it for "$35". If $35 is nowhere in the context, it is a faithfulness failure in generation: tighten grounding and add a claim-vs-source check. If $35 is in some chunk, it is a data problem (stale or mis-chunked content) and the fix is upstream. Logging the exact retrieved context per answer is what makes this a two-minute diagnosis instead of a guessing game.

Interview questions

Junior What is RAG and why would you use it instead of just asking the model?

▸ Model answer

RAG, retrieval-augmented generation, fetches relevant passages from your own data at question time and puts them in the prompt, so the model answers from evidence instead of memory. You use it because a bare model has a training cutoff, has never seen your private documents, and guesses when it does not know. RAG fixes all three: the knowledge is current because you re-index when documents change, private because it lives in your store, and checkable because each answer can cite the passage it used. It changes the model's input, not its weights, so updating knowledge is cheap.

Mid How do you decide between long context, RAG and fine-tuning for a new use case?

▸ Model answer

I ask what kind of thing the model is missing. If it is knowledge that is small, I paste it (long context) because it is simplest. If it is knowledge that is large, changing, private or must be cited, I use RAG. If it is behaviour (a format, a tone, a classification style) I consider fine-tuning, or first just a strong system prompt and few-shot examples. Then I do the arithmetic: corpus tokens against the context window, tokens per call times call volume times price, and how often content changes. Often the answer is a mix: RAG for facts plus a light fine-tune or prompt for style.

Senior A RAG prototype looks great in demos but users complain it is wrong 20% of the time. How do you run the investigation?

▸ Model answer

First I stop changing things and build a labeled set: 200 to 300 real user questions, each with the passage that should answer it and a reference answer. Then I split the failure in two. Retrieval metrics (recall@k, MRR) tell me whether the right passage reached the prompt; generation metrics (faithfulness, answer relevance) tell me whether the model used it. If recall is low I work on chunking, embeddings, hybrid search and reranking. If recall is high but faithfulness is low I work on grounding, context order and citation checks. I also slice by query type, because the 20% is usually concentrated: identifiers, multi-hop questions, or stale documents. Every fix goes through the same eval before it ships.
