Data preparation

Start here

Fine-tuning data is a set of examples: an input and the exact answer you want back.

The model copies those examples, the good habits and the bad ones.

So the work is cleaning: remove duplicates, drop poor answers, and hide personal data.

Keep every example in the same format you will use when you call the model later.

Set some examples aside, never trained on, so you can check the result honestly.

Everyday picture

Preparing fine-tuning data is like choosing which past exam answers to give a younger student to study. If you hand over a pile with messy answers, wrong answers and the same question copied 50 times, they'll learn the mess. If you hand over 300 neat, correct, varied ones, they'll learn the pattern.

In the pictureIn the real system
Messy or wrong past answersLow-quality responses, which the model will imitate faithfully
The same question copied 50 timesDuplicates and near-duplicates, which overweight one pattern
300 neat, varied answersA few hundred clean, consistent, representative pairs
Keeping some exams back for the real testThe validation split, kept apart by customer and time to avoid leakage

Where the picture breaks. A student can tell a crossed-out wrong answer is wrong; a model copies whatever you show it, wrong answers included.

Going deeper

If fine-tuning fails, it’s almost always the data — not the algorithm. The dataset is the product of a fine-tune: the model becomes a mirror of the examples you show it. This lesson is how to build that mirror well.

Why data is the whole game

Training nudges the model toward your examples (Lesson 5.2), so whatever patterns live in your data get baked in — including the bad ones. Inconsistent formats teach inconsistency; a biased mix teaches bias; sloppy answers teach sloppiness. The hard, valuable work of fine-tuning is assembling a clean, consistent, representative set of examples in the exact shape you want the model to produce. Get this right and a simple LoRA run succeeds; get it wrong and no hyperparameter will save you.

Concept

A fine-tuning training example is an input paired with the desired output — for instruction tuning, an instruction → response pair, often expressed in a chat format (a list of role/content messages). You split your examples into a training set the model learns from and a validation set held out to measure honestly. The cardinal rule: the data’s format must match how you’ll prompt the model at inference.

The quality checklist

  • Consistent format. Every example in the same shape — the model copies the pattern, including inconsistencies.
  • High-quality outputs. The responses are exactly what you want produced. The model imitates them faithfully, warts and all.
  • Representative & diverse. Cover the real range of inputs, including edge cases, not 500 near-duplicates.
  • Deduplicated & clean. Remove duplicates, junk, and contradictions; they confuse training and inflate apparent performance.
  • No train/validation leakage. The same (or near-identical) example must not appear in both, or your evaluation lies to you.
  • Quality over quantity. A few hundred excellent, consistent pairs routinely beat thousands of mediocre ones.
Worked example — format & split a dataset (free)

The common modern format is a list of chat messages per example, saved as JSONL (one JSON object per line). This is just data wrangling — free, no GPU.

import json, random

# raw pairs you collected/curated
raw = [
    {"q": "How do I reset my password?", "a": "Go to Settings > Security > Reset password."},
    {"q": "What's your refund window?",    "a": "Returns are free within 30 days of delivery."},
    # ... a few hundred clean, consistent examples ...
]

SYSTEM = "You are Acme's support assistant. Be concise and accurate."
def to_example(row):                              # SAME shape you'll use at inference
    return {"messages": [
        {"role": "system",    "content": SYSTEM},
        {"role": "user",      "content": row["q"]},
        {"role": "assistant", "content": row["a"]},
    ]}

data = [to_example(r) for r in raw]
random.shuffle(data)
split = int(0.9 * len(data))
train, val = data[:split], data[split:]      # 90/10, never overlap

with open("train.jsonl", "w") as f:
    for ex in train: f.write(json.dumps(ex) + "\n")
print(len(train), "train /", len(val), "val examples")

Notice the system + user + assistant structure matches exactly how you’ll call the model later. If you train on one format and prompt with another, the model gets confused — train how you’ll serve.

At real scale: From 1.2 million support tickets to 8,000 training examples

Assumptions: a telecom company has 1,200,000 resolved support tickets with agent replies and wants a model that drafts replies in house style.

  1. Exact dedup. Normalise whitespace and case, then hash. Say 18% are exact duplicates (auto-replies, copy-paste macros): 1,200,000 x 0.82 = 984,000 left.
  2. Near-dup dedup. MinHash on word shingles removes templated replies that differ only in a name or date. Say 40% go: about 590,000 left.
  3. Quality filter. Keep tickets that were resolved on the first reply and rated CSAT 4-5. Say 15% pass: about 88,500.
  4. PII scrub. Replace phone numbers, account IDs and addresses with typed placeholders like [PHONE]. Drop tickets where scrubbing breaks the meaning. Say about 80,000 remain.
  5. Stratified sample. Production traffic is 30% billing, 25% network, 20% SIM and port-out, 25% other. Sample 8,000 in those proportions, capping any single intent at 5%, so a few common intents don't drown out the rest.
  6. Group split, not random split. Split 90/10 by customer and by month, so no customer and no week of tickets sits in both train and validation. Random splitting would leak a customer's repeated issues across the split and flatter the score.
  7. Human spot-check. Read 200 random examples (2.5%). If more than 5% are bad, fix the filter and rerun, rather than hand-patching rows.

Why stop at 8,000? LIMA got strong instruction-following from just 1,000 carefully curated examples (arXiv 2305.11206). Curation beats volume.

Key points
  • Data is the product of a fine-tune — the model mirrors your examples, good and bad.
  • Use a consistent format (instruction→response / chat messages) that matches inference.
  • Quality & consistency beat quantity; hundreds of clean pairs often beat thousands of messy ones.
  • Dedupe, diversify, and prevent train/validation leakage.
  • Always keep a held-out validation set — it’s your only honest measure (Lesson 5.6).

Your fine-tuned model scores 98% on your validation set but performs poorly in production. You later find many validation examples were near-duplicates of training examples. What happened?

  • A) Train/validation leakage — the model effectively saw the validation examples in training, so the 98% was measuring memorization, not generalization.
    Correct. When validation examples overlap (even near-duplicates) with training, the model has essentially memorized the answers, so validation accuracy is inflated and meaningless. Real, unseen production inputs reveal the truth. Dedupe across the split so validation stays genuinely held out.
  • B) The model is too small.
    Model size wouldn’t produce a high validation score that collapses in production — that gap is the signature of leakage giving a falsely optimistic measurement, not a capacity problem.
  • C) You needed more epochs.
    More epochs would worsen memorization. The issue isn’t undertraining; it’s that your validation set wasn’t actually independent, so it can’t tell you anything reliable.
  • D) The learning rate was wrong.
    Learning rate affects how training proceeds, not whether your validation set is contaminated. The 98%-then-fails pattern points squarely at leakage between train and validation.

For a fine-tune, why do data quality and dedup matter more than raw quantity?

  • The model learns the patterns in your data — duplicates and noise get memorized and amplified.
    Correct. Clean, representative examples beat a large noisy pile.
  • More data always overfits.
    Quantity isn't the enemy; low quality is.
  • Dedup speeds up inference.
    It affects training quality, not inference speed.
  • Quality doesn't matter if the model is big.
    Bad data harms even large models.

You randomly split 50,000 tickets 90/10. Many customers filed 5-10 near-identical tickets. Validation accuracy is 94%; on next month's tickets it's 78%. What is the most likely cause?

  • A) Group leakage: the same customers' near-identical tickets landed in both train and validation, so validation rewarded memorisation.
    Correct. Split by group (customer, thread, time window) so related examples stay on one side. Random row-level splits leak whenever rows are correlated.
  • B) Next month's tickets are harder; nothing is wrong with the evaluation.
    Possible but unproven. The correlated-rows setup makes leakage the first thing to rule out, and a time-based split would test this directly.
  • C) The model is too small for the task.
    A capacity problem would show low validation scores too. A high validation score that collapses on fresh data is the signature of leakage.
  • D) Too few epochs.
    More training would increase memorisation, widening the gap rather than closing it.
Practice

1. You have 5,000 support tickets but only ~300 have high-quality agent replies. Do you train on all 5,000 or the 300? Why?
2. Why must the training format match your inference prompt format exactly?
3. You’re short on data. Name one legitimate way to get more examples and one risk it carries.

▸ Show solutions & reasoning

1. Train on the 300 high-quality ones. The model imitates whatever you show it, so 4,700 mediocre replies would teach mediocrity and drown out the good pattern. Quality and consistency dominate; a few hundred excellent examples is a strong fine-tuning set. (You could also use the good ones to help generate/curate more — carefully.)

2. Because the model learns to produce the desired output given a specific input shape. If you train with a system message and a particular structure but prompt differently at inference, the model is now in an unfamiliar situation and behaves worse — you’ve broken the pattern it learned. “Train how you serve” keeps training and inference aligned.

3. One way: synthetic data — use a strong model to generate additional instruction/response examples for your task. The risk: it can introduce the larger model’s errors, biases, or a sameness that doesn’t reflect real inputs — so synthetic examples must be filtered and validated, not trusted blindly. (Other options: data augmentation, or mining more real examples.)

Deep dive: data is the moat

In a world where everyone can call the same base models, your data is what’s defensible. A thoughtfully curated set of examples for your specific task — your tone, your formats, your edge cases — is something competitors can’t copy from a model card. That’s why mature teams invest more in data pipelines than in clever training tricks: collecting real examples, cleaning and labeling them, generating and filtering synthetic ones, and continuously folding production failures back into the training set. The fine-tuning algorithm is a commodity; the dataset is the asset.

Two traps to internalize. First, silent format drift: a stray difference between training and serving (a missing system message, different delimiters, a different chat template) quietly degrades a model that looked great in evaluation — always serve in the exact shape you trained. Second, evaluation contamination: leakage between train and validation (or reusing your validation set so often that you implicitly tune to it) makes your numbers lie. The discipline is boring but decisive: clean data, consistent formatting, honest held-out splits. Do that and fine-tuning becomes reliable engineering; skip it and it becomes expensive guesswork.

Exercises: warm-up, transfer, stretch

Warm-up. You have 10,000 rows. 22% are exact duplicates; of the rest, 30% are near-duplicates; 20% of what remains fails your quality filter. How many examples are left?

▸ Solution

10,000 x 0.78 = 7,800. 7,800 x 0.70 = 5,460. 5,460 x 0.80 = 4,368. Each filter multiplies, which is why raw counts badly overstate usable data. Plan your collection around the final number.

Transfer. Your examples come from three teams: one writes 'Hi there,' and bullet lists, one writes formal paragraphs, one writes one-liners. You want one consistent house style. What do you do with the data?

▸ Solution

Pick the target style and write it down with 5 gold examples. Then either keep only the examples that already match (if there are enough), or rewrite the others into the target style, by people or with a strong model plus human review, and record which examples are rewritten. Mixed styles in training teach the model to pick a style at random, which looks like inconsistency in production. Check with a style rubric on validation outputs.

Stretch. Design a pipeline that keeps the fine-tuning set fresh: production failures should flow back in each month without contaminating the eval set.

▸ Solution

Log production outputs with user feedback and reviewer corrections. Each month, sample failures and corrections, scrub PII, and send them through the same dedup and quality filters. Before adding, run near-dup matching against the frozen eval set and drop any candidate too close to an eval item. Keep the eval set frozen and versioned, with a small new eval slice each quarter for drift, kept separately. Version the training set (hash plus manifest) per model release so any result can be reproduced, and track the training mix by intent so new data doesn't skew it.

Interview questions

Junior What makes a good fine-tuning dataset?

▸ Model answer

Consistent format that matches exactly how the model will be prompted in production, including the system message and chat template. High-quality target outputs, because the model copies them. Coverage of the real input distribution, including edge cases, without a few common cases dominating. Deduplicated and clean. And a validation split that is truly held out. A few hundred to a few thousand excellent examples usually beat a much larger noisy set; LIMA used 1,000.

Mid How do you prevent train/validation leakage in practice?

▸ Model answer

First, dedupe across the split, not just within it, with near-duplicate detection such as MinHash or embedding similarity, since exact hashing misses templated text. Second, split by group: customer, conversation thread, document or time window, so correlated examples stay together. For anything that will run on future data, a time-based split is the most honest. Third, freeze the eval set and check every new training batch against it. Finally, if the score looks too good, measure on a fresh sample of production data before believing it.

Senior You can buy 100,000 synthetic examples generated by a frontier model, or spend the same budget on 3,000 expert-written examples. How do you decide?

▸ Model answer

Run a small pilot of both against the same eval. Synthetic data is good for coverage and format but carries the generator's errors, biases and sameness, and some providers' terms restrict training on their outputs, so I'd check the license. Expert data is better for the hard, high-stakes cases. Often the best mix is a few thousand expert examples as the core, plus synthetic data that has been filtered and graded to fill coverage gaps, with every synthetic example passing an automatic check and a sample passing human review. The decision should come from eval results per slice, not from volume.
