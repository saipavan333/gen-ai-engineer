Evaluating a fine-tune

A fine-tune that feels better is worthless; you need proof. And the dangerous failure isn’t obvious badness — it’s a model that aced your task while quietly getting worse at everything else. This lesson is how to know, with numbers, whether you actually improved things.

Two questions every fine-tune must answer

After training, ask: (1) Did it get better at the target task? and (2) Did it get worse at anything else? The first is obvious; the second is where teams get burned. Fine-tuning hard on a narrow task can cause catastrophic forgetting — the model improves on your task but regresses on general ability (grammar, reasoning, refusing bad requests). You only catch this by measuring both, against the original base model, on data the model never trained on.

Concept

You evaluate against a baseline — the original base model — on a held-out set (examples never used in training). Measure a task metric (accuracy, exact match, or an LLM-as-judge score) and a general-ability check (a few diverse prompts or a small benchmark). Watch for overfitting (great on train, poor on held-out) and regression / catastrophic forgetting (better on the task, worse generally).

School-kid picture

Evaluating a fine-tune is like checking whether extra maths tuition helped a student. You don't ask the tutor; you give the student a test they haven't seen. You also check they didn't forget how to read while cramming maths. The analogy breaks because a student's school report covers many subjects for free; for a model, you only find out what got worse if you built a test for it.

Worked example — compare fine-tuned vs base (free)

The minimum honest evaluation: score both models on the same held-out task, and sanity-check general ability. Never deploy a fine-tune you didn’t compare to the base.

def accuracy(model, examples):
    correct = 0
    for ex in examples:
        out = generate(model, ex["input"])
        if matches(out, ex["expected"]):       # exact match, regex, or LLM-judge
            correct += 1
    return correct / len(examples)

held_out = load("val.jsonl")                 # NEVER trained on
general  = load("general_probe.jsonl")      # diverse, off-task prompts

print("target task — base:", accuracy(base_model, held_out))
print("target task — tuned:", accuracy(tuned_model, held_out))   # should be higher
print("general    — base:", accuracy(base_model, general))
print("general    — tuned:", accuracy(tuned_model, general))    # should NOT be much lower

If the target task rose and general ability held, ship it. If general ability dropped, you over-fit your task — train for fewer epochs, use more/diverse data, a lower learning rate, or a smaller LoRA rank, and re-measure.

At real scale: Is 0.60 to 0.91 real, and did general ability drop?

Assumptions: a held-out task set of 1,000 examples and a general-ability probe of 300 diverse prompts. Base model: 0.60 on the task, 0.82 on the probe. Fine-tune: 0.91 on the task, 0.76 on the probe.

  1. Task gain uncertainty. Standard error of a proportion = sqrt(p(1-p)/n). Tuned: sqrt(0.91 x 0.09 / 1,000) = 0.009, so the 95% interval is about +/-1.8 points. Base: sqrt(0.60 x 0.40 / 1,000) = 0.015, about +/-3.0 points. A 31-point gain is far outside both: real.
  2. General drop uncertainty. Base: sqrt(0.82 x 0.18 / 300) = 0.022. Tuned: sqrt(0.76 x 0.24 / 300) = 0.025. Standard error of the difference, treating them as independent, is about sqrt(0.022^2 + 0.025^2) = 0.033. The 6-point drop is about 1.8 standard errors: suggestive but not conclusive.
  3. Use a paired test. Both models answered the same 300 prompts, so count disagreements. Say 31 prompts flipped from right to wrong and 13 from wrong to right: net 18 / 300 = 6 points. McNemar's statistic = (31 - 13)^2 / (31 + 13) = 324 / 44 = 7.4, above 3.84 (the 5% threshold), so the drop is real.
  4. Diagnose. Read the 31 regressions. Say most are 'ignores instructions to answer in a list': the fine-tune overwrote format-following.
  5. Fix and re-measure. Mix 10% general instruction data into training, cut epochs from 3 to 2, and re-run both sets. Biderman et al. report LoRA forgets less than full fine-tuning, but it still forgets (arXiv 2405.09673).
Key points
  • Always compare to the base model on a held-out set — “feels better” isn’t evidence.
  • Measure the target task (should rise) and general ability (should not fall).
  • Watch for overfitting (train ≫ held-out) and catastrophic forgetting (task up, general down).
  • If general ability drops: fewer epochs, more/diverse data, lower learning rate, smaller rank — then re-measure.
  • Evaluation is what turns fine-tuning from a gamble into engineering.

Your fine-tune scores 0.91 on the target task (base was 0.60) — a clear win. What must you check before celebrating?

  • A) Whether general ability regressed — score both models on diverse off-task prompts to rule out catastrophic forgetting.
    Correct. A big target-task gain can hide a general-ability loss from over-specialization. Until you’ve checked the fine-tune didn’t get worse at off-task behavior (reasoning, formatting, safety), you don’t actually know it’s a net win. Always measure both axes.
  • B) Nothing — a big jump on the task is sufficient proof.
    A task jump alone can mask a regression elsewhere. Shipping on the task metric alone is exactly how teams deploy a model that’s great at one thing and worse at everything else.
  • C) Whether training loss reached zero.
    Near-zero training loss is a warning sign (memorization), not a goal. Held-out performance and general ability are what matter, not how low training loss went.
  • D) Whether the adapter file is small.
    Adapter size is an efficiency detail, irrelevant to whether the model is actually better overall. The real check is general-ability regression on held-out prompts.

You fine-tuned a model. What's the honest way to know it improved?

  • Measure it on a held-out eval set it never trained on.
    Correct. Only held-out data honestly measures generalization.
  • Check that training loss went down.
    Falling train loss can just mean memorization; use held-out eval.
  • Confirm it feels better in a demo.
    Vibes aren't evidence; measure on a real set.
  • See that it's faster.
    Speed isn't quality.

On 300 shared probe prompts, 25 flip from right to wrong after fine-tuning and 25 flip from wrong to right. What do you conclude?

  • A) The probe set is broken because results changed.
    Changing results are what a probe is for. The set isn't broken; you need to read the flipped cases.
  • B) Nothing changed; ship it.
    Totals can stay flat while behaviour changes a lot. Look at what flipped before shipping.
  • C) Net general accuracy is unchanged, but the model's behaviour changed on 50 prompts, so read those flips to see what moved.
    Correct. Equal flips give the same total, but a 17% change in which prompts pass is a real behaviour shift; the totals hide it. The 25 new failures may matter more (safety, key customers) than the 25 new passes.
  • D) The fine-tune is clearly worse.
    The counts are balanced; there's no net loss. Whether it's worse depends on which prompts flipped.
Practice

1. Why must your evaluation set be held out from training, and what goes wrong if it isn’t?
2. Your fine-tune is better on the task but noticeably worse at following unrelated instructions. Name two fixes.
3. Free-text answers make exact-match scoring brittle. What’s a more robust way to score them?

▸ Show solutions & reasoning

1. Held-out data is your only honest read on generalization. If evaluation examples were in training (or near-duplicates), the model may have memorized them, so your score measures recall of seen answers, not ability on new inputs — it’ll look great and fail in production. Independence of the eval set is what makes the number trustworthy.

2. That’s catastrophic forgetting from over-specialization. Fixes: train less aggressively (fewer epochs, lower learning rate, smaller LoRA rank) so you nudge rather than overwrite; and mix in some general/diverse examples with your task data so the model retains broad ability. Then re-measure both axes.

3. Use a more semantic check: an LLM-as-judge that reads the model’s answer and the expected answer (or a rubric) and scores correctness, or check key facts/fields rather than exact strings. This tolerates valid wording differences while still catching wrong answers — it’s the heart of Track 6 (Evals), which generalizes exactly this problem.

Deep dive: evaluate before you deploy, and keep evaluating

Fine-tuning makes a permanent change to a deployed behavior, so the discipline is stricter than for a prompt tweak. Before shipping: compare against the base on a frozen held-out set, check general-ability probes, and ideally run a small regression suite — a fixed set of prompts (including edge cases and safety checks) that must not get worse. After shipping: prefer an A/B test or a careful rollout, watching real-world quality and user signals, because offline metrics never capture everything. A fine-tune that wins offline can still lose on the messiness of production traffic.

This is the moment the whole course converges: evaluating a fine-tune is the same skill as evaluating a prompt or a RAG pipeline — define what “good” means, build a held-out set, measure against a baseline, and never trust a vibe. That’s why Track 6 (Evals & Observability) is next and arguably the most important track for shipping: it turns these per-technique checks into a systematic capability. If you remember one thing from fine-tuning, let it be this: the model you can measure is the only one you can safely ship.

Exercises: warm-up, transfer, stretch

Warm-up. Your held-out set has 200 examples. The base scores 0.70 and the fine-tune 0.75. Roughly how big is the 95% interval on each score, and is the gain convincing?

▸ Solution

SE(0.70) = sqrt(0.7 x 0.3 / 200) = 0.032, so about +/-6.4 points. SE(0.75) = sqrt(0.75 x 0.25 / 200) = 0.031, about +/-6.0 points. The intervals overlap heavily; a 5-point gain on 200 examples isn't convincing on its own. Run a paired test on the per-example flips, or grow the set. Small eval sets make fine-tunes look better or worse at random.

Transfer. Your fine-tune passes the offline eval, but after launch users report it refuses harmless requests more often. Which eval was missing, and how do you add it?

▸ Solution

A safety and over-refusal probe. Build two sets: harmful requests the model must refuse, and borderline-but-harmless requests it must answer (medical information, security education, fiction). Score refusal rates on both for base and tuned models, and gate releases on both: refusals of harmful requests must not drop, and refusals of harmless ones must not rise beyond a set threshold. Training data often contains many refusals or hedged replies that teach over-caution, so check the dataset for that too.

Stretch. Write a release gate for fine-tuned adapters that runs in CI. List the suites, the metrics and the pass rules.

▸ Solution

Suites: (1) frozen held-out task set; (2) general-ability probe; (3) safety: must-refuse and must-answer; (4) format and contract tests (valid JSON, schema, stops correctly); (5) a slice of last month's real traffic with reference answers. Metrics: task score with confidence interval, paired flips against the current production adapter, refusal rates, format failure rate, latency and tokens per answer. Pass rules: task score not lower than production (paired test), general probe net flips not significantly negative, harmful-refusal rate not lower, harmless-refusal rate up no more than 1 point, zero format regressions. Store all outputs so failures can be read, and require human sign-off for any rule override.

Interview questions

Junior How do you know a fine-tune actually helped?

▸ Model answer

I compare it with the base model, and with the best prompt-only setup, on a held-out set it never trained on, using a task metric that reflects what users need. I check that the gain is bigger than the noise for the set size, ideally with a paired comparison since both models see the same examples. Then I check it didn't get worse elsewhere: a general-ability probe, safety refusals and format compliance. Only if the target improved and the guardrail metrics held do I call it a win. After launch, I confirm with an A/B test or a staged rollout.

Mid What is catastrophic forgetting and how do you detect and reduce it?

▸ Model answer

It's when training on a narrow task makes the model worse at things it used to do: following general instructions, reasoning, formatting or safety behaviour. You detect it by running probes outside the target task on both base and tuned models and comparing per prompt, not just averages. To reduce it: train less aggressively (fewer epochs, lower learning rate), use LoRA, which Biderman et al. found forgets less than full fine-tuning, mix some general instruction data into the training set, and keep the rank modest. Then re-measure both axes.

Senior Leadership wants one number to decide if the fine-tune ships. What do you give them?

▸ Model answer

I'd push back gently: one number hides trade-offs. But I can give one decision with a short scorecard behind it. The headline is the change in the business metric's proxy, for example 'resolution-quality score up 9 points (95% CI 6 to 12) versus production'. Under it, three guardrails with pass or fail: general ability held, safety refusals held, cost and latency within budget. If any guardrail fails, the answer is no regardless of the headline. Then a rollout plan: 5% traffic for a week, watching live metrics, with automatic rollback.
