How training actually works

Fine-tuning stops being mysterious once you see what “training” really is: a loop that nudges numbers downhill to make the model less wrong. You don’t need the calculus — you need the mental model, because it explains data, overfitting, and every knob you’ll touch.

Training is just “guess, measure, adjust,” repeated

A model is a giant pile of numbers called weights (or parameters). Training shows the model an example, lets it predict, measures how wrong the prediction was, and nudges the weights a tiny bit to be less wrong next time — then repeats, millions of times. That’s the whole idea. Pre-training does this over the entire web (hugely expensive); fine-tuning does a little more of the same on your data (cheap), starting from an already-smart model.

Concept — the words you’ll hear

The forward pass is the model making a prediction. The loss is a number measuring how wrong it was (lower is better). The gradient points in the direction that increases loss, so we step the opposite way — this is gradient descent. Backpropagation is the efficient method for computing those gradients across all the weights. The learning rate is how big each step is. An epoch is one full pass over your training data. You split data into a training set (to learn from) and a validation set (held out, to check honestly).

School-kid picture

Training is like learning to shoot a basketball. You shoot, see how far you missed, adjust your arm a little, and shoot again, thousands of times. Big adjustments make you overshoot; tiny ones take forever. The analogy breaks because you adjust one arm, while the model adjusts billions of numbers at once, and it can 'get good' by memorising the exact shots in practice rather than learning to shoot, which is why you test it on shots it has never seen.

Roll the ball downhill

Here’s gradient descent on the simplest possible “model”: one weight, with loss = (weight − 3)². The lowest point is at 3. Take steps and watch it descend — then crank the learning rate too high and watch it overshoot. This is training, minus the billions of weights.

Live demo

Gradient descent

Worked example — gradient descent in 8 lines (free)

The loop above, in plain Python. No libraries, no GPU — just the mechanism.

w = -4.0            # the weight we're learning
target = 3.0
lr = 0.1            # learning rate (step size)

for step in range(20):
    loss = (w - target) ** 2          # how wrong we are
    grad = 2 * (w - target)         # direction loss increases
    w = w - lr * grad               # step the OTHER way
    print(f"step {step}: w={w:.3f}  loss={loss:.3f}")
# w marches toward 3.0 and loss toward 0 — that's learning.

Real training is this exact loop, but w is billions of weights, the loss is “how wrong was the next-token prediction,” and the gradient is computed by backpropagation. Same idea, more numbers.

At real scale: The training budget for a 7B model on 20,000 examples

Assumptions: you fine-tune Qwen2.5-7B (the model card lists 7.61B parameters, model card) on 20,000 instruction-response examples of about 600 tokens each, with an effective batch size of 32.

  1. Tokens per epoch. 20,000 x 600 = 12 million tokens.
  2. Optimizer steps. 20,000 / 32 = 625 steps per epoch. Three epochs = 1,875 weight updates. Each one is the loop from this lesson: forward pass, loss, backprop, nudge.
  3. Validation cadence. Hold out 2,000 examples (10%). Evaluate every 125 steps, giving 15 validation points across the run, enough to see where validation loss bottoms out.
  4. Memory for full fine-tuning. Hugging Face's memory guide counts about 6 bytes per parameter for mixed-precision weights, 8 for Adam's two optimizer states and 4 for gradients: 18 bytes per parameter before activations (HF memory anatomy). 7.61B x 18 = about 137 GB, more than any single consumer GPU, which is why Lesson 5.4 exists.
  5. Reading the curves. Say validation loss falls to 0.92 at step 1,000, then rises to 0.98 by step 1,875 while training loss keeps falling. Keep the step-1,000 checkpoint: that's early stopping, and stopping there would have saved nearly half the compute.
  6. Learning rate. TRL's SFTConfig defaults to 2e-5 for full fine-tuning, and its docs suggest about 1e-4 when training adapters, because only new parameters are learning (TRL SFT docs).
Key points
  • Training = predict → measure loss → nudge weights down the gradient, repeated.
  • Fine-tuning is just more of this on your data, starting from a pretrained model — so it’s cheap vs. pre-training.
  • The learning rate controls step size: too small = slow; too big = overshoot/diverge.
  • Watch training vs. validation loss: if training keeps dropping but validation rises, you’re overfitting.
  • You don’t need the math — you need the loop, because it explains every knob.

During fine-tuning, your training loss keeps dropping but your validation loss starts rising after a few epochs. What’s happening, and what do you do?

  • A) Overfitting — the model is memorizing the training set instead of generalizing. Stop earlier, use less data repetition, or add regularization.
    Correct. Falling train loss with rising validation loss is the textbook signature of overfitting: the model fits quirks of the training data that don’t generalize. Early stopping (stop when validation stops improving), fewer epochs, more/diverse data, or regularization all help. Validation loss is the honest signal.
  • B) The learning rate is too low.
    A low learning rate makes training slow, not this pattern. The diverging train/validation gap specifically indicates overfitting, regardless of step size.
  • C) It's working perfectly — training loss is going down.
    Training loss going down while validation loss rises is the opposite of working — the model is getting worse at unseen data. You care about validation, not training, performance.
  • D) You need more epochs.
    More epochs would make it worse — it would memorize the training set even harder. The fix is to stop sooner (or improve data), not train longer.

What is 'loss' during training?

  • A number measuring how wrong the model's predictions are; training adjusts weights to reduce it.
    Correct. Training is gradient descent on the loss.
  • The model's response time.
    That's latency, not loss.
  • How many parameters were dropped.
    Loss measures prediction error, not parameter count.
  • The cost in dollars.
    Loss is a training error metric, unrelated to billing.

You have 8,000 examples, batch size 16 and gradient accumulation 4. How many optimizer steps are in one epoch?

  • A) 8,000
    That would be one update per example (batch size 1). Batching averages many examples into each step.
  • B) 500
    That's 8,000 / 16. It ignores gradient accumulation, which combines 4 micro-batches into one optimizer step.
  • C) 125
    Correct. Effective batch = 16 x 4 = 64 examples per weight update, so 8,000 / 64 = 125 steps per epoch.
  • D) 2,000
    That's 8,000 / 4. Accumulation multiplies the batch, it doesn't replace it.
Practice

1. In the demo, set the learning rate very high (≈1.0+). Describe what happens to the ball and why.
2. In plain words, what is the “loss” when fine-tuning a language model on instruction/response pairs?
3. Why can fine-tuning work with a few hundred examples when pre-training needs trillions of tokens?

▸ Show solutions & reasoning

1. With too high a learning rate, each step overshoots the minimum and lands further up the other side, so the ball bounces back and forth with growing swings and the loss increases — it diverges instead of settling. This is why the learning rate is one of the most important knobs: too small wastes time, too big breaks training entirely.

2. It’s a measure of how far the model’s predicted next tokens are from the actual tokens in your “correct” responses. For each position, the model assigns probabilities to possible next tokens; loss is high when it gave low probability to the right token. Minimizing it nudges the model to make your desired responses more likely. So you’re literally teaching it “in this situation, this is the likely output.”

3. Because fine-tuning starts from a model that already learned language, facts, and reasoning during pre-training — you’re not teaching it to think, just to adjust its existing behavior toward your task. It only needs to learn the narrow pattern (your format/style/task), which a few hundred good examples can convey. Pre-training had to learn everything from scratch; fine-tuning stands on its shoulders.

Deep dive: the knobs, and why generalization is the goal

The loop has a handful of knobs you’ll meet in any fine-tuning tool. Learning rate (and its schedule) sets step size — usually small for fine-tuning, since you’re gently adjusting a good model, not reshaping it. Epochs set how many passes over the data; too few underfits, too many overfits, so you watch validation loss and stop when it stops improving (early stopping). Batch size is how many examples you average each step (bigger = smoother but more memory). You don’t tune these blind — you watch the train and validation curves and let them guide you.

The deepest idea here is that the goal isn’t low training loss — it’s generalization, doing well on data the model never saw. A model can drive training loss to near zero by memorizing, which is useless (it’ll fail on real inputs). That’s why the held-out validation set is sacred: it’s your only honest read on whether the model learned the pattern or just the answers. Everything in fine-tuning — data quality, regularization, early stopping, evaluation (Lesson 5.6) — is in service of generalization. Keep that north star and the knobs make sense: each one is a lever for “learn the pattern, don’t memorize the examples.”

Exercises: warm-up, transfer, stretch

Warm-up. Using the HF figure of 18 bytes per parameter for mixed-precision training with Adam, estimate memory (before activations) to fully fine-tune a 1.5B model and a 70B model.

▸ Solution

1.5B x 18 = 27 GB: tight even on a 24 GB GPU, so you'd need an 8-bit optimizer or a smaller batch. 70B x 18 = 1,260 GB: a multi-node job. Activations come on top and grow with batch size and sequence length. This arithmetic is why LoRA and QLoRA dominate applied fine-tuning.

Transfer. Your run's training loss is flat at 2.3 from step 0 to step 500. List three likely causes and how you'd check each.

▸ Solution

(1) Learning rate far too low, or the scheduler stuck in warmup: print the logged learning rate. (2) Nothing is actually trainable, for example adapters not attached or everything frozen: print the trainable parameter count (PEFT's print_trainable_parameters). (3) Labels are all masked, or the data is broken, for example every label is -100 or the prompts are empty: decode one batch of input_ids and labels and read them. A flat loss is almost always a plumbing bug, not 'the model can't learn'.

Stretch. Design the checkpoint and early-stopping policy for a 3-epoch run where each validation pass costs 4 minutes and the run takes 6 hours.

▸ Solution

Evaluate every ~10% of the run (about every 36 minutes), so roughly 10 validation passes = 40 minutes of overhead, about 11%. Save a checkpoint at each eval, but keep only the best 2 by validation loss plus the latest (save_total_limit) to bound disk. Stop when validation loss hasn't improved for 2 consecutive evals (patience = 2), and load the best checkpoint at the end. Also log a task metric on a small held-out sample at each eval, because validation loss and task quality don't always move together.

Interview questions

Junior What is the difference between training loss and validation loss, and why do you need both?

▸ Model answer

Training loss is measured on the examples the model is learning from; validation loss is measured on held-out examples it never trains on. Training loss almost always goes down, because the model can memorise. Validation loss tells you whether it is learning something that generalises. When training loss keeps falling and validation loss starts rising, the model is overfitting, and that's where I'd stop or pick the best checkpoint.

Mid Walk me through what happens in one optimizer step when fine-tuning an LLM.

▸ Model answer

A batch of tokenised examples goes through the model (forward pass), producing next-token probabilities at every position. Cross-entropy loss compares those with the actual next tokens, ignoring masked positions such as padding or prompt tokens. Backpropagation computes the gradient of the loss with respect to every trainable parameter. With gradient accumulation, gradients from several micro-batches are summed before updating. The optimizer, usually AdamW, uses the gradients plus its running averages to update the weights by an amount scaled by the learning rate, the scheduler adjusts the learning rate, and gradients are cleared.

Senior A fine-tune looks great on validation loss but the business metric didn't move. How do you reason about it?

▸ Model answer

Loss measures how likely the model finds the reference tokens, not whether outputs are useful. Possible gaps: the validation set doesn't look like production traffic, the metric depends on a few key tokens (a label, a number) that loss averages away, or the model learned the reference style without the substance. I'd build a task-level eval on real production samples, check the decoding settings and chat template used at serving match training, and look at failure cases by hand. Then I'd select checkpoints on the task metric, not just loss.
