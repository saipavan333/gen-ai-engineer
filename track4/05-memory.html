Memory

Start here

A model only remembers what is in its context window right now. That is short-term memory.

Long chats overflow the window, so older turns get squeezed into a short summary.

Long-term memory lives outside the model, in a database or a vector store.

When a new question comes in, the agent looks up the relevant memories and adds them to the prompt.

That lookup is RAG, pointed at the agent's own history.

Everyday picture

Agent memory is like a student's notebook during a long school year. You can't remember every word the teacher said, so you write down key points (summaries) and keep a labelled index at the back so you can find 'fractions' fast before a test (retrieval).

In the pictureIn the real system
What you can hold in your head in classShort-term memory: the context window

Where the picture breaks. A student notices when notes contradict each other; an agent will retrieve an old wrong note and trust it just as much as a new correct one unless you date and update memories.

Going deeper

An agent that forgets everything between steps — or between sessions — can’t accomplish much. Memory is how an agent holds onto what it has learned, despite a small context window. And the good news: you already know the core trick. It’s RAG, pointed at the agent’s own history.

Why memory is a real design problem

Recall from Track 1.4 that the model only knows what’s in its context window right now, and that window is finite. For a long agent run — dozens of steps, a multi-turn conversation, a task spanning days — the full history won’t fit, and re-sending everything is expensive and invites “lost in the middle.” So you need a strategy for what to keep in the window, what to store outside it, and how to bring the right past information back when it’s relevant. That strategy is memory.

Concept

Short-term memory is the information currently in the context window — the recent conversation and the current task’s trace. Long-term memory is information stored outside the model (a database or vector store) that you retrieve and inject when relevant. Within long-term memory, episodic memory recalls specific past events (“last time, the user preferred email”), while semantic memory holds distilled facts (“the user’s timezone is IST”). Writing to memory and reading from it are deliberate steps you build.

The two techniques you’ll actually use

Summarization (managing short-term memory). When the conversation grows past a budget, compress older turns into a running summary and keep recent turns verbatim. The summary preserves the gist while freeing tokens — a controlled forgetting.

Vector memory (long-term recall). Store facts/summaries as embeddings; when a new query arrives, retrieve the most relevant memories and add them to the context. This is RAG (Track 3) with the knowledge base being the agent’s own history — and it’s how an assistant “remembers” your preferences across sessions.

Worked example — summarize + retrieve memory (free)

Both techniques, minimal. Summarize to fit; store and retrieve to recall.

import numpy as np, ollama
from sentence_transformers import SentenceTransformer

def ask(prompt, system=None, model="qwen2.5:7b"):   # one chat call; returns the reply text
    msgs = ([{"role": "system", "content": system}] if system else []) + [{"role": "user", "content": prompt}]
    return ollama.chat(model=model, messages=msgs)["message"]["content"]
embed = SentenceTransformer("all-MiniLM-L6-v2")

# --- short-term: summarize old turns when the convo gets long ---
def compress(old_turns):
    text = "\n".join(old_turns)
    return ask(f"Summarize this conversation in 3 bullet points, keeping key facts:\n{text}")

# --- long-term: a tiny vector memory you write to and read from ---
memory, mem_vecs = [], None
def remember(fact):
    global mem_vecs
    memory.append(fact)
    mem_vecs = embed.encode(memory, normalize_embeddings=True)
def recall(query, k=2):
    if not memory: return []
    q = embed.encode([query], normalize_embeddings=True)[0]
    top = np.argsort(mem_vecs @ q)[::-1][:k]
    return [memory[i] for i in top]

remember("User prefers metric units and replies in the morning.")
remember("User is based in Bengaluru (IST).")
print(recall("what timezone should I schedule for?"))   # -> both facts (k=2 and there are only 2 memories); use k=1 for just the closest

That’s the whole idea: summarize to keep the window lean, store and retrieve to recall the right thing later. Long-term memory is just RAG whose corpus is the agent’s experience.

At real scale: Memory for an assistant serving 1 million calls a day

Assumptions: a banking assistant handles 1,000,000 model calls a day. A long-standing user has 300 past turns of about 150 tokens each. Prices: claude-sonnet-5-5 input at $2 per million tokens (Claude models overview).

  1. Naive: resend everything. 300 x 150 = 45,000 tokens of history per call. 45,000 x $2/1M = $0.09 per call. If even that were the typical user, 1M calls = $90,000 a day on history alone, and the model has to find one fact in the middle of 45,000 tokens.
  2. Short-term memory. Keep the last 6 turns verbatim (900 tokens) plus a running summary of older turns (600 tokens).
  3. Long-term memory. Extract durable facts ('prefers Telugu', 'salary account at Kukatpally branch') into a per-user store with timestamps. Retrieve the top 5 facts (about 150 tokens) per query.
  4. New context per call. 900 + 600 + 150 = 1,650 tokens = $0.0033. At 1M calls: $3,300 a day, about 27x cheaper, with the relevant fact placed where the model will see it.
  5. Storage. 2,000,000 users x 200 facts = 400M memories. With all-MiniLM-L6-v2 (384 dimensions, model card) at 4 bytes per float: 400M x 384 x 4 = about 614 GB of vectors. Partition by user, so each search scans only that user's 200 vectors.
  6. Privacy cost. Those 400M memories are personal data: you need retention limits, deletion on request, and a hard user_id filter on every retrieval.

Watch the model forget

Shrink the context budget and watch the earliest turns fall out of the conversation. This is exactly what users experience as the assistant “losing the plot”.

Key points
  • Short-term memory = the context window (fast, limited); long-term memory = an external store you retrieve from.
  • Summarize old turns to fit the window; store + retrieve facts for cross-session recall.
  • Long-term memory is RAG over the agent’s own history — the same embed/retrieve you already know.
  • Distinguish episodic (past events) from semantic (distilled facts) memory.
  • Memory is a deliberate write/read design, not something that happens for free.

A user tells your assistant “I’m vegetarian” in week 1. In week 3 they ask for dinner ideas and it suggests steak. What’s the fix?

  • A) Long-term memory: store the preference as a fact and retrieve relevant memories into the prompt for later sessions.
    Correct. Week-1’s message is long gone from the context window, so the model can’t “remember” it — you must persist it externally and retrieve it when relevant (here, on a food-related query). That’s vector memory: RAG over the user’s history.
  • B) Increase the context window so the whole history fits.
    Even a huge window won’t hold weeks of conversation indefinitely, and re-sending everything is costly and invites “lost in the middle.” Selective long-term memory (store + retrieve) scales; brute-force context does not.
  • C) Lower the temperature.
    Temperature affects randomness, not whether a week-old fact is available to the model. The information simply isn’t in the context — a memory problem, not a decoding one.
  • D) Fine-tune the model on this user.
    Fine-tuning per user is wildly impractical and is for behavior, not fast-changing personal facts. Storing the preference as retrievable memory is immediate, cheap, and updatable.

Why does an agent 'forget' earlier turns in a long chat?

  • Nothing persists between calls; when history no longer fits the context window, old turns get dropped.
    Correct. Each call resends history, and when it exceeds the window, something must go.
  • The model deletes memories to save money.
    It's a context-window limit, not a cost decision.
  • Memory is stored on the server forever.
    Nothing is remembered between calls unless you store it yourself.
  • Higher temperature erases memory.
    Temperature is unrelated to context retention.

A user said 'I moved to Pune' in March. In October your assistant still schedules in Bengaluru, because retrieval returns both 'lives in Bengaluru' (Jan) and 'moved to Pune' (Mar) and the model picks the first. What is the right fix?

  • A) Fine-tune the model on the user's history.
    Fine-tuning for a fact that changes is slow, expensive and impossible to update cleanly. Facts belong in a store you can edit.
  • B) Ask the model to be careful about old information.
    Without timestamps or supersession, the model has no way to know which fact is newer.
  • C) Treat memory as updatable facts: on write, find the conflicting fact, replace or supersede it, and keep timestamps so recency counts at retrieval.
    Correct. Memory is a curation problem. Appending every statement creates contradictions; a write path that updates the 'location' fact (and keeps the old one only as history) removes the conflict.
  • D) Retrieve more memories (k=20) so the model sees everything.
    More retrieved memories means more contradictions and more noise, not fewer. The store itself needs fixing.
Practice

1. Classify as short-term or long-term memory: (a) the last 3 messages, (b) “the user’s account ID,” (c) the current task’s tool trace, (d) “last month the user complained about slow support.”
2. Why summarize old turns instead of just dropping them when the window fills?
3. What could go wrong if you store everything a user ever says in long-term memory and retrieve aggressively?

▸ Show solutions & reasoning

1. (a) short-term (recent context), (b) long-term (a durable fact), (c) short-term (this run’s working state), (d) long-term (a past episode worth recalling). The line is roughly “needed for this immediate step” (short-term) vs “might matter again later” (long-term).

2. Dropping old turns loses information the agent may still need (a fact established early, a decision made). Summarizing preserves the gist and key facts in far fewer tokens, so you free window space without amnesia. It’s controlled forgetting — keep the essence, discard the verbatim bulk.

3. Several failures: the memory store fills with noise, so retrieval surfaces irrelevant or stale facts that derail the agent; privacy risk grows (you’re hoarding personal data — Track 7); and contradictions accumulate (an old preference conflicting with a new one). Good memory is curated: store distilled, useful facts; prune or expire stale ones; and retrieve precisely, not greedily.

Deep dive: memory is a curation problem

The hard part of agent memory isn’t storing — it’s deciding what’s worth remembering and when to surface it. Naively dumping every message into a vector store creates a swamp: retrieval returns near-duplicates, outdated facts, and irrelevant chatter that crowds the prompt. Mature memory systems do active curation: they extract salient facts (preferences, decisions, entities) rather than raw transcripts, deduplicate and update them (a new timezone overwrites the old), attach timestamps so recency can be weighed, and sometimes maintain a structured user profile alongside free-text memories. Retrieval then pulls a small, high-quality set rather than a noisy haystack.

Two more realities. First, memory inherits every RAG concern — chunking, embedding quality, retrieval evaluation — because it is RAG; if recall is poor, the agent “forgets” even though the fact is stored. Second, memory is where privacy and safety get serious: you’re persisting user data across sessions, so you need consent, retention limits, the ability to delete, and care that one user’s memories never leak into another’s context (Track 7). Treat the memory store as sensitive production data, not a convenience cache. Done well, memory is what makes an assistant feel like it actually knows you; done carelessly, it’s a liability that also gives worse answers.

Exercises: warm-up, transfer, stretch

Warm-up. A conversation is at 9,000 tokens and your budget is 4,000. The last 8 turns are 2,400 tokens. How big can the running summary be, and what goes into it?

▸ Solution

4,000 - 2,400 = 1,600 tokens, minus room for the system prompt and retrieved facts (say 600), leaves about 1,000 tokens for the summary. Into it go decisions made, facts the user stated, open tasks and constraints ('budget under 50k', 'no flights before 9am'). Out go greetings, abandoned ideas and anything already captured as a long-term fact.

Transfer. Your support agent shares one vector store across tenants. A customer of company A sees a memory from company B. What failed, and how do you design it so it cannot happen again?

▸ Solution

Retrieval relied on similarity alone with no hard tenant filter, so a semantically close memory from another tenant ranked high. Fix: every memory row carries tenant_id and user_id; the retrieval function takes those from the authenticated session (never from the model) and applies them as a mandatory filter before similarity ranking, or you use a separate index or namespace per tenant. Add a test that queries as tenant A for tenant B's unique strings and must return nothing. Treat this as a data breach: notify, purge, audit.

Stretch. Design the memory write path for a personal assistant: what gets stored, when, and how stale or wrong memories are handled.

▸ Solution

After each session (not every turn, to save cost), run an extraction call that outputs candidate facts as JSON: subject, attribute, value, source turn, confidence. For each candidate, look up existing facts with the same subject and attribute: same value, refresh the timestamp; different value, supersede the old one and keep it as history; new attribute, insert. Skip low-confidence or sensitive categories unless the user asked to be remembered. Give facts a time-to-live by type (a preference lasts longer than a travel plan). Expose a 'what do you remember about me' view with delete. Evaluate with a set of conversations and expected final memory states.

Interview questions

Junior What is the difference between short-term and long-term memory in an agent?

▸ Model answer

Short-term memory is what is in the context window right now: recent turns, the current task's trace and any summary of earlier turns. It is fast but limited, and you pay for it on every call. Long-term memory lives outside the model, usually in a database or vector store; you write facts or episodes to it and retrieve the relevant ones into the prompt when needed. It is basically RAG over the agent's own history. Short-term memory is managed with trimming and summarisation; long-term memory with extraction, retrieval and updates.

Mid Context windows are now 1M tokens on some models. Why not just keep the whole history in context?

▸ Model answer

Cost, quality and privacy. Cost: you pay for every input token on every call, so a 200k-token history resent 50 times a day is real money even with prompt caching. Quality: models get worse at finding a specific fact as context grows, and old contradictory statements sit next to new ones with nothing marking which wins. Privacy: you are resending personal data in every request. A large window is useful headroom, but a curated memory with summaries and retrieval of a few relevant facts is cheaper, more accurate and easier to govern.

Senior How would you evaluate a memory system?

▸ Model answer

Build scripted multi-session conversations with known ground truth: facts stated, facts later changed, facts that should be forgotten. Measure write quality (did the store end up with the right facts and no contradictions), retrieval quality (recall@k of the needed fact for probe questions), and end-to-end answers (does the assistant use the current fact). Add negative tests: cross-user leakage must be zero, and deleted facts must never come back. Track memory size per user and retrieval latency over time, because memory stores grow without limit unless you prune them.
