PII & privacy

Start here

PII (personally identifiable information) is anything that points to a real person: names, emails, phone numbers, card numbers, ID numbers.

AI apps copy text into many places: logs, traces, caches, search indexes and the model provider's servers.

Redaction swaps personal details for placeholders like [EMAIL] before the text is stored or sent.

Keep only the data you need, and delete it when you are done.

Redaction tools miss some names, so the stores still need locks and time limits.

Everyday picture

Handling PII is like a school nurse keeping medical notes. She writes down only what she needs, keeps the notes in a locked drawer, blacks out names before sharing a report with the head teacher, and shreds old notes at the end of the year.

In the pictureIn the real system
Writing down only what she needsData minimisation: collect and keep only what the task needs
The locked drawerAccess control on logs, traces and vector stores
Blacking out names in the reportRedaction: placeholders such as [NAME] and [CARD]
Shredding old notes each yearRetention limits and deletion requests (for example GDPR Article 17)
Notes copied into five foldersThe same data in logs, caches, vector stores and a provider's servers

Where the picture breaks. A paper note is in one place, but data in an LLM app gets copied into logs, caches, vector stores and maybe a model provider's servers, so 'shred it' means finding every copy.

Going deeper

LLM apps swim in user data — and they log it, send it to third-party models, and sometimes repeat it back. Mishandling personal information isn’t just bad hygiene; it’s a legal liability. This lesson is how to handle data responsibly without crippling your app.

Why privacy is a first-class concern here

Three things make LLM apps privacy-risky. They log heavily (you need traces to debug, Track 6 — but traces contain user data). They often call third-party model APIs (your users’ data leaves your servers). And they can echo data back (a model might surface one user’s info to another, or repeat sensitive input). On top of that, regulations like GDPR give you real obligations around personal data. So you must know what PII flows through your system and control it deliberately.

Concept

PII (personally identifiable information) is data that identifies a person — names, emails, phone numbers, addresses, government IDs, payment details. Redaction (masking) replaces PII with placeholders before storing or sending. Data minimization means collecting and retaining only what you actually need. Retention limits mean deleting data after it’s served its purpose. Together these reduce both risk and regulatory exposure.

Worked example — redact before logging (free)

Mask PII at the boundary. For production, a library like the free, open-source Microsoft Presidio detects far more than regex can.

import re

PATTERNS = {
    "[EMAIL]": r"[\w.+-]+@[\w-]+\.[\w.-]+",
    "[CARD]":  r"\b(?:\d[ -]*?){13,16}\b",
    "[SSN]":   r"\b\d{3}-\d{2}-\d{4}\b",
    "[PHONE]": r"\(?\d{3}\)?[ -]?\d{3}[ -]?\d{4}",
}
def redact(text):
    for tag, pat in PATTERNS.items():
        text = re.sub(pat, tag, text)
    return text

raw = "Email jane@x.com, card 4111 1111 1111 1111"
log(redact(raw))                 # "Email [EMAIL], card [CARD]"  → safe to store
# Redact at THREE points: before logging, before third-party API calls, and on outputs.
# For names/addresses and high accuracy, use Presidio (free) — a model-based detector.

Regex handles structured PII (emails, cards, IDs) well; names and addresses need a model-based detector like Presidio. The key habit is redacting at the boundary — the moment data would leave your control or land in a log.

At real scale: Redacting 300,000 call-centre transcripts a day before they reach an LLM

Assumptions: an Indian insurer transcribes 300,000 calls a day, about 1,200 words each, and sends them to an LLM for summaries and quality scoring. Each call mentions on average 3 person names, plus phone numbers, policy numbers and sometimes card numbers.

  1. Structured PII first. Regex for emails, phone numbers, policy IDs and cards. For cards, add a Luhn checksum test so a 16-digit policy number is not mislabelled as a card.
  2. Names and addresses need a model. Use a named-entity detector such as Microsoft Presidio (docs). Name mentions per day: 300,000 x 3 = 900,000.
  3. Plan for misses. If your measured name recall is 95%, then 900,000 x 0.05 = 45,000 names a day still get through. Redaction lowers risk; it does not remove it. So the downstream stores still need access control and retention limits.
  4. Pseudonymise, do not just delete. Replace each name with a consistent token per call ([PERSON_1], [PERSON_2]) so the summary still reads sensibly. Keep the token-to-name map in a separate, tightly controlled store for 30 days in case an agent must follow up.
  5. Redaction points. Before the transcript is logged, before it is sent to the model provider, and on the model's output before it is stored, because the model can still echo values that slipped through.
  6. Measure it like a model. Hand-label 500 transcripts, report recall and precision per entity type each release, and track the missed-entity count per day as a risk number leadership understands.
  7. Deletion requests. Under GDPR Article 17 (text) and similar laws, a customer may ask for erasure. Because every store is keyed by call ID, you can delete the transcript, its vectors, cached summaries and trace spans in one job.
Key points
  • LLM apps leak PII via heavy logging, third-party API calls, and echoing data back.
  • Redact PII before logging, before sending to third parties, and from outputs.
  • Practice data minimization and retention limits — don’t collect or keep what you don’t need.
  • Regex catches structured PII; use a model-based detector (e.g., Presidio) for names/addresses.
  • Privacy is a legal duty (GDPR, etc.), not optional hygiene — know your obligations.

Your support bot calls a third-party LLM API and logs full conversations for debugging. A privacy review flags it. What’s the right fix?

  • A) Redact PII before it’s logged and before it’s sent to the third-party API, retain logs only as long as needed, and restrict access.
    Correct. The two leak points are the logs and the outbound API call; redacting at both, plus minimizing retention and access, addresses the real exposure while keeping enough to debug. This is data minimization applied at the boundaries.
  • B) Stop all logging so nothing is ever stored.
    Killing observability removes your ability to debug and improve (Track 6) and is overkill — redaction lets you keep useful logs without storing raw PII. Don’t trade all visibility for privacy when you can have both.
  • C) Encrypt the logs and consider it solved.
    Encryption-at-rest helps but doesn’t address sending PII to a third party, nor over-retention, nor internal access to decrypted data. It’s one control, not the fix — redaction and minimization are still needed.
  • D) Ask the model not to repeat PII.
    That addresses only the echo-back path, unreliably, and does nothing about logging or the outbound API call. Privacy is handled by deterministic controls at the data boundaries, not by asking the model nicely.

Best defense against PII leaking to a third-party model API?

  • Minimize what you send and redact PII before the request — don't rely on the model.
    Correct. A prompt is a data transfer; send less and mask sensitive fields.
  • Ask the provider nicely not to store it.
    You can't enforce a third party's handling with a prompt.
  • Encrypt the prompt inline.
    The provider still receives readable content to process.
  • Use a longer context window.
    Unrelated to privacy exposure.

Your regex redactor catches 99% of emails and cards. A privacy reviewer still flags the logs. What is the most likely gap?

  • A) Emails should be hashed instead of masked.
    Hashing can be useful for joins, but it does not address the categories regex misses entirely.
  • B) The regex is too slow.
    Speed is not a privacy issue. The issue is what it cannot see.
  • C) Logs should be stored as JSON.
    The format does not change whether PII is in them.
  • D) Unstructured PII such as names, addresses and free-text health details, which regex cannot reliably detect.
    Correct. Structured identifiers have patterns; names and addresses do not. You need a model-based detector and still assume some misses.

A customer asks you to delete their data. It was used to fine-tune a model last quarter. What is true?

  • A) Asking the model to forget the person works.
    A prompt cannot change weights. At best it hides outputs, unreliably.
  • B) Fine-tuned models never memorise individual records.
    Models can memorise and reproduce rare strings from training data. You cannot assume they do not.
  • C) Deleting the training file is enough.
    The model's weights were already updated from it. The file is only one copy.
  • D) Removing it from the weights generally means retraining or re-fine-tuning without that data; deleting the source rows alone does not remove what the model learned.
    Correct. That is why personal data should be kept out of training sets in the first place, with clear lineage of what went in.
Practice

1. Name the three points in an LLM pipeline where you should redact PII.
2. Why is regex insufficient for redacting names and addresses, and what do you use instead?
3. A user invokes their “right to be forgotten.” What does that imply for your logs, vector store, and any fine-tune data?

▸ Show solutions & reasoning

1. (a) Before logging/tracing (so stored traces don’t contain raw PII), (b) before sending to a third-party model/API (so data doesn’t leave your control unnecessarily), and (c) on outputs (so the model doesn’t surface PII to the wrong person). Redaction lives at every data boundary.

2. Names and addresses have no fixed pattern — “Jane Doe” looks like ordinary words, and addresses vary wildly — so regex either misses them or over-matches. You use a model-based PII detector (named-entity recognition), e.g., the free Microsoft Presidio, which understands context to find person names, locations, and organizations. Use regex for structured tokens (emails, cards, SSNs) and a model for unstructured PII.

3. You must be able to actually delete that person’s data wherever it lives: remove or anonymize their entries in logs/traces, delete their documents and the corresponding vectors from the vector store (and re-index), and — critically — if their data was used to fine-tune a model, you generally can’t “unlearn” it from the weights, so you’d need to retrain without it. This is exactly why fine-tuning on personal data is risky and why minimization and good data lineage matter from day one.

Deep dive: privacy and observability must be designed together

There’s a real tension in this track: Track 6 told you to log everything for debugging and evals, and this lesson tells you to be careful what you store. The resolution isn’t to pick one — it’s to design them together. Redact PII before it’s written to traces (so your logs are useful but not a liability), keep raw data only transiently where you truly need it, set retention windows that auto-delete, and gate access to whatever sensitive data remains.

Done right, you get full observability over redacted data, which is enough to debug the vast majority of issues. When you genuinely need un-redacted data (a hard bug), pull it under stricter access controls and short retention.

Two broader points for production. First, the third-party question is often the biggest one: sending user data to an external model API means it leaves your infrastructure, so you must check the provider’s data-handling terms (do they train on it? how long do they retain it?), and for the most sensitive data, consider self-hosting an open model (the free local stack from this course) so nothing leaves at all.

Second, privacy is a legal and trust issue, not just technical — regulations like GDPR/CCPA carry real penalties, and users’ trust is hard to win back once lost. Treat personal data as something you’re borrowing, not owning: collect the minimum, protect it in transit and at rest, redact it from logs and outputs, delete it when done, and be able to honor deletion requests. That posture keeps you both compliant and trustworthy.

Exercises: warm-up, transfer, stretch

Warm-up. List every place a single customer chat might be copied in a typical RAG support app.

▸ Solution

The chat database, application logs, trace spans (prompt and answer), the LLM provider's request logs (check their retention terms), any semantic or exact-match cache, analytics events, the eval or golden set if someone copied it there, support tickets created from the chat, backups of all of the above, and the vector store if conversations are indexed. Each is a place where redaction, access control and deletion must apply.

Transfer. Your team wants to send customer emails to a hosted LLM API. List the questions you must answer before turning it on.

▸ Solution

What data categories are in the emails (identifiers, financial, health)? Does the provider train on API data by default, and how long does it retain requests? In which region is data processed, and does that meet your legal requirements? Can you redact before sending without breaking the task? Do you have a data processing agreement? Can you delete or exclude a specific customer's data later? Is there a self-hosted or in-region option for the most sensitive subset? Write the answers down with links to the provider's terms, and review when the terms change.

Stretch. Design a PII handling pipeline for an LLM-based analytics feature on a warehouse table with 50 million customer rows.

▸ Solution

1) Classify columns once with a scanner plus human review: direct identifiers, quasi-identifiers (pin code, birth date), free text. 2) Never send direct identifiers to the model; replace them with stable surrogate keys in a view. 3) For free-text columns, run batch redaction (regex plus NER) into a redacted copy, and log per-entity counts. 4) Grant the LLM job access only to the redacted view through a service account. 5) For aggregates, enforce minimum group sizes (for example, no group under 20 customers) to limit re-identification. 6) Outputs go through the same redactor before storage. 7) Deletion: a job keyed on customer ID removes rows from source, redacted copy, caches and indexes. 8) Measure redaction recall quarterly on a labelled sample.

Interview questions

Junior Where can PII leak in an LLM application?

▸ Model answer

In logs and traces, which often store full prompts and answers. In calls to third-party model APIs, where data leaves your infrastructure. In model outputs, where the model may repeat sensitive input or reveal data retrieved for another user. In caches and vector stores that hold copies of conversations or documents. And in training or fine-tuning data, where it can be memorised. OWASP lists this as LLM02:2025 Sensitive Information Disclosure. The basic defences are data minimisation, redaction at each boundary, access control, retention limits and the ability to delete.

Mid How would you evaluate a PII redaction system?

▸ Model answer

Build a labelled set of realistic texts, with every PII span marked by type, including hard cases such as Indian names, addresses written in mixed scripts and numbers that look like cards but are not. Measure recall and precision per entity type, because missing a card number is worse than over-masking a city. Report misses as an expected count at production volume, for example 45,000 names a day, so the residual risk is clear. Re-run on each change to patterns or the NER model, and sample production output to check for drift.

Senior A multi-tenant SaaS RAG product must guarantee one customer's data never appears in another's answers. How do you design for that?

▸ Model answer

Enforce isolation in retrieval, not in the prompt. Every chunk carries a tenant ID, and every vector query includes a mandatory tenant filter applied by the server from the authenticated session, never from model output. Consider separate indexes or namespaces for large tenants. Caches are keyed by tenant. Traces and evals are partitioned by tenant with access control. Test it: automated cross-tenant probes in CI that query tenant A with tenant B's secrets and expect nothing. Monitor for any retrieved chunk whose tenant does not match the session, and treat one occurrence as an incident. Then add output scanning as a second layer.
