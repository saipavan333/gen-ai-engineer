Defense in depth

Every guard in this track is imperfect on its own — moderation misses things, prompts get injected, models get jailbroken. The whole strategy is to layer them so that no single failure becomes a breach. This lesson assembles the pieces into a coherent defense.

Why one layer is never enough

You’ve seen that each defense is probabilistic or partial: prompt hardening reduces but can’t eliminate injection; moderation has false negatives; the model’s refusals can be jailbroken. If you rely on any single one, a single bypass is a full compromise. Defense in depth is the security principle of stacking independent layers so an attacker must defeat all of them, and so a failure of one is caught or contained by another. Combined with least privilege — giving the system only the access it needs — it shrinks both the chance and the impact of a breach.

Concept

Defense in depth uses multiple independent safeguards so that the failure of any one doesn’t cause a breach. For LLM apps the layers are: input moderation (block unsafe requests), prompt hardening (fence untrusted text as data), least-privilege tools (limit what the model can do), human-in-the-loop (approval for risky actions), output validation (sanitize before use), and monitoring (detect and respond to what slips through). Least privilege ensures even a fully-hijacked model can do little harm.

School-kid picture

Defence in depth is like the layers protecting a castle: a moat, then a wall, then a gate with guards, then a locked room for the treasure. An attacker who swims the moat still faces the wall. Where it breaks: castle layers fail for different reasons, but if all your LLM layers are themselves LLMs reading the same text, one clever trick can fool several at once, so the layers must be different kinds of things, not copies of each other.

Worked example — compose the layers (free)

A guarded request pipeline that stacks the defenses from this whole track:

def handle(user_msg, user):
    log("request", redact(user_msg), user.id)              # monitor + PII redaction (7.4)

    if is_unsafe(user_msg):                                # 1) input moderation (7.5)
        return refuse()

    prompt = [{"role":"system","content": SYSTEM_RULES},      # 2) prompt hardening (7.2)
              {"role":"user","content": f"<data>{user_msg}</data>"}]

    out = agent(prompt, tools=tools_for(user),               # 3) least-privilege tools (4.8)
                require_approval={"refund","delete"})            # 4) human-in-the-loop (4.8)

    out = validate_output(out)                            # 5) output validation (7.6)
    if is_unsafe(out):                                     # 6) output moderation (7.5)
        return refuse()

    log("response", redact(out), user.id)               # monitor
    return out

No layer here is trusted to be perfect. If moderation misses, the prompt is hardened; if the prompt is injected, the tools are least-privilege; if a risky action is requested, a human approves; if the output is unsafe or malformed, validation and output-moderation catch it; and everything is logged so you learn from whatever slips through.

At real scale: How much do stacked defences really cut 10,000 attack attempts a month?

Assumptions: a public support agent with a refund tool sees 10,000 injection or misuse attempts a month. The pass-through rates are example measurements from your own red-team runs.

  1. Input moderation lets 60% of attempts through (injections often look like normal text): 10,000 x 0.6 = 6,000.
  2. Prompt hardening and spotlighting stop most; 30% still steer the model: 6,000 x 0.3 = 1,800.
  3. Least-privilege tools. The agent can only refund the logged-in customer's own orders. Only 5% of the steered attempts ask for something inside that scope: 1,800 x 0.05 = 90.
  4. Hard limits and human approval. Refunds over a set amount need a human; reviewers reject 95% of suspicious ones: 90 x 0.05 = 4.5, so about 4 or 5 bad refunds a month, each capped at the approval threshold.
  5. The independence trap. Multiplying rates assumes the layers fail independently. If moderation and prompt hardening are both LLMs and the same phrasing fools both, the real number is higher. Measure end-to-end on the full pipeline, not only per layer.
  6. Make the last layer deterministic. The tool scope and amount cap are plain code. They do not get fooled by wording, which is why they carry most of the weight. Research designs such as CaMeL push this further by tracking data flow in code (arXiv 2503.18813).
  7. Monitoring closes it. Every blocked or approved-then-reversed refund is logged, reviewed weekly, and added to the red-team suite, so next month's numbers are measured against this month's attacks.
Key points
  • Every single guard is imperfect — layer independent defenses so one failure isn’t a breach.
  • The stack: input moderation → prompt hardening → least-privilege tools → human approval → output validation → monitoring.
  • Least privilege is the most powerful layer: a hijacked model that can’t do much can’t cause much harm.
  • Assume each layer leaks; design so the blast radius is contained.
  • Match the depth to the risk — an internal tool needs less than a public, action-taking agent.

Across this track, which single layer most reduces the impact of a successful prompt injection or jailbreak?

  • A) Least privilege — limiting the tools/data the model can access, so even a fully-hijacked model can do little harm.
    Correct. Injection/jailbreaks can’t be fully prevented, so the highest-leverage move is containment: if the model has no dangerous tools and minimal data access, a successful attack yields little. Least privilege caps the blast radius regardless of how the model was manipulated.
  • B) A longer system prompt.
    Prompt wording reduces the chance of some attacks but doesn’t limit the impact when one succeeds — and it’s itself bypassable. Containment comes from constraining capabilities, not from more instructions.
  • C) A bigger model.
    A bigger model is still injectable/jailbreakable and, if it has powerful tools, can still cause harm when manipulated. Capability doesn’t contain impact; least privilege does.
  • D) Higher temperature for variety.
    Temperature is unrelated to security and could make behavior less predictable. It does nothing to limit the damage of a successful attack.

You can add ONE defense to a public action-taking agent. Which gives the most protection?

  • Least privilege — cap its tools/data so even a hijacked model can do little harm.
    Correct. Containment beats persuasion; it limits the blast radius regardless of manipulation.
  • A longer, sterner system prompt.
    Bypassable and doesn't cap impact.
  • A bigger model.
    Still injectable; capability doesn't contain harm.
  • Higher temperature.
    Provides no protection.

Your pipeline uses an LLM for input screening, an LLM for prompt hardening checks and an LLM for output review. Red-team tests show one phrasing beats all three. What is the design flaw?

  • A) The layers are not independent; they share the same weakness, so they fail together. Add deterministic code-level controls such as tool scopes, allowlists and limits.
    Correct. Stacking only works when layers fail for different reasons. Code does not get persuaded by phrasing.
  • B) The models are too small.
    Larger models are also persuadable. The problem is correlated failure, not size.
  • C) You need a fourth LLM layer.
    Another layer with the same weakness adds cost but little protection.
  • D) Defence in depth does not work for LLM apps.
    It works when the layers are genuinely different in kind.
Practice

1. Trace what happens to an injection attempt as it passes through the layered pipeline above — where might each layer stop or contain it?
2. Why is “independent” the key word in “independent layers”?
3. Design the appropriate defense depth for (a) an internal employee Q&A bot vs (b) a public agent that can issue refunds. How do they differ?

▸ Show solutions & reasoning

1. Input moderation might catch an obviously abusive attempt; prompt hardening (fencing the text as data) may make the model ignore the injected instruction; if it doesn’t, least-privilege tools mean the model can’t do anything dangerous; a risky action it does attempt hits human approval; the output is validated (no unsafe markup/actions) and moderated; and the whole thing is logged so you detect the attempt and add it to your tests. The attack must beat every layer to cause harm — and even then, least privilege limits what “harm” can be.

2. Because layers that fail the same way give false confidence — if your input filter and output filter are the same model with the same blind spot, an attack that beats one beats both. Independence (different mechanisms: a classifier, code-level limits, a separate moderation model, human review) means an attacker must defeat genuinely different defenses, and a weakness in one doesn’t imply a weakness in another. That’s what makes stacking actually multiply security rather than just look thorough.

3. (a) The internal bot is low-risk (trusted users, read-only, no money/actions), so light defenses suffice: basic moderation, sensible prompt, PII care in logs, monitoring. (b) The public refund agent is high-risk (untrusted users, irreversible money-moving action), so it needs the full stack: input/output moderation, hardened prompts, strict least-privilege tools, hard code-level refund limits + human approval, output validation, and tight monitoring/rate-limiting. Match the investment to the assets and exposure — over-securing an internal tool wastes effort, under-securing a public action-taker is dangerous.

Deep dive: the security mindset for LLM products

The throughline of this entire track is a mindset shift: you cannot make the model safe, so you make the system safe around it. The model is a brilliant, gullible component that processes untrusted text and (often) takes actions; treat it like any untrusted, internet-facing component and apply decades of security wisdom — least privilege, defense in depth, validate everything crossing a boundary, assume breach, monitor and respond. None of the individual techniques are exotic; the skill is composing them appropriately and never trusting any single one (including the model’s good behavior).

Two closing principles. First, security is proportional: a careful threat model (Lesson 7.1) tells you which assets and exposures actually matter, so you can invest depth where it counts and avoid security theater where it doesn’t. Second, safety is continuous, not a checkbox: attacks evolve, so you red-team, fold successful attacks into your eval suite (Track 6), monitor production, and update defenses — the same flywheel that drives quality also drives safety.

Master this and you can put an LLM in front of real users, and even give it real capabilities, with justified confidence. That confidence — earned through layered, measured, evolving defenses — is what it means to ship a trustworthy AI product, which is the whole point of being an applied GenAI engineer rather than a demo-builder.

Exercises: warm-up, transfer, stretch

Warm-up. Put these controls in request order and mark which are deterministic code: output URL allowlist, input moderation classifier, tool permission check, spotlighting of retrieved text, human approval, trace logging.

▸ Solution

Order: input moderation classifier (model), spotlighting of retrieved text (prompt technique), tool permission check (code), human approval (human), output URL allowlist (code), trace logging (code, runs throughout). The deterministic ones are the tool permission check, the URL allowlist and logging; human approval is independent of the model. Those are the layers an injection cannot talk its way past.

Transfer. Red-team results: 2,000 attempts; 1,100 pass input moderation; 280 of those steer the model; 14 of those reach a tool call inside the allowed scope; 1 gets human approval. What is the pass rate of each layer and the end-to-end success rate?

▸ Solution

Moderation pass rate 1,100 / 2,000 = 55%. Steering rate 280 / 1,100 = 25.5%. In-scope tool rate 14 / 280 = 5%. Approval rate 1 / 14 = 7%. End to end 1 / 2,000 = 0.05%. Note that you measured end to end directly, which already includes any correlation between layers; that is more trustworthy than multiplying layer rates from separate tests.

Stretch. You have budget for one engineer-month to harden an existing agent. How do you decide where to spend it?

▸ Solution

1) Run the red-team suite end to end and record, for each successful attack, which layers it passed. 2) Rank by impact: a leak of customer data or money movement outranks rude text. 3) Look for the cheapest deterministic control that blocks the top paths: usually narrowing tool scopes, adding recipient or amount limits, or an output URL allowlist, each a few days of work. 4) Next, add monitoring for the attack patterns you saw, so new variants are noticed. 5) Only then tune prompts or classifiers. Re-run the suite after each change and report end-to-end success rate before and after, so the month's work has a measured result.

Interview questions

Junior What does defence in depth mean for an LLM app?

▸ Model answer

It means using several independent safeguards so one failure does not become a breach. A typical stack is input moderation, prompt hardening that marks untrusted text as data, least-privilege tools, hard limits and human approval for risky actions, output validation and moderation, and monitoring. Each layer is imperfect; together they make an attack need several things to go right. The most important layers are deterministic code controls like tool scopes and allowlists, because they cannot be talked around.

Mid Why is least privilege considered the strongest layer against prompt injection?

▸ Model answer

Because it limits the damage regardless of whether the model is fooled. Prompt defences and classifiers reduce how often an attack works, but none reach zero. If the agent can only read the current user's records and only send email to that user, a fully successful injection has little to steal and nowhere to send it. It is also deterministic code, so its strength does not depend on wording. In OWASP terms, it directly addresses LLM06:2025 Excessive Agency.

Senior How would you report the security posture of an LLM agent to a risk committee?

▸ Model answer

I would give a short threat model listing assets, entry points and the top risks with scores. Then measured numbers from the red-team suite: end-to-end attack success rate per risk category, current versus last quarter, with sample sizes. Then the controls per risk, marked as deterministic or probabilistic, and the worst-case impact if all probabilistic layers fail, for example 'maximum refund without approval is capped by code'. Production indicators: blocked attempts, approvals, incidents. And open gaps with owners and dates. Mapping each risk to the OWASP 2025 IDs helps the committee compare with other systems.
